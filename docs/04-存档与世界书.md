## 9. 存档系统

### 9.1 为什么用世界书存存档

前端没有自己的持久化存储（iframe 内无法可靠落盘、跨浏览器不可靠），所以选择把存档**写进 SillyTavern 的世界书条目**，随聊天/角色卡一起保存。这是这类卡片常见的存档策略。

### 9.1.1 存档库 = 当前聊天绑定的世界书（必要时新建并绑定）

"写进世界书"具体是写**哪一份**世界书（@841419 附近，save 模块闭包）：

```js
function i() { return getChatWorldbookName('current')?.trim() ?? '' }  // 当前聊天已绑定的世界书
async function l(e) { await rebindChatWorldbook('current', e); ... }  // 绑定到当前聊天
async function c() {  // = resolveWorldbookName()
  const t = i();
  if (t) return t;                        // ① 聊天已绑定 → 直接用（常规情况）
  // ② 未绑定 → 用前端配置的 worldbookName 尝试绑定
  // ③ 仍失败 → createWorldbook(n, []) 新建空世界书 → l(n) 绑定当前聊天
  //           （日志："已显式创建并绑定聊天世界书"）
}
```

- **常规情况**：直接用角色卡配套、当前聊天已绑定的世界书，**不新建**；
- **唯一新建场景**：聊天没绑定任何世界书时，`createWorldbook` 建**空**世界书再 `rebindChatWorldbook('current', n)` 绑上；
- 写入立即落盘：`SillyTavern.saveWorldInfo(name, data, true)` + `reloadWorldInfoEditor` + `updateWorldInfoList`（@841349 `s` 函数）。

> 这份世界书**同时承担两个角色**：① 存档载体（meta/chunk 条目，见 9.4）② 运行时状态注入（临时世界书条目 `area.current` 等，见 [11-临时世界书.md](11-临时世界书.md)）。这就是为什么它必须绑定到当前聊天。

### 9.1.2 物理位置（存档到底存在哪个文件）

```
SillyTavern 数据目录 / data / default-user / worlds / {世界书名}.json
```

- **存档 = 世界书文件里的若干条目**（`extra.source: 'tangquan-save-v1'` 打标的 `meta` + `chunk` 条目，见 9.4），文件整体是 ST 世界书 JSON（`{entries: [...], keys: ...}`）；
- 世界书文件名 = 聊天绑定的世界书名（`resolveWorldbookName`，常规即角色卡配套世界书，如 `未开之花.json`；未绑定时新建空世界书并绑定）；
- 写入链路：`replaceWorldbook(世界书, entries)`（@844437）→ `saveWorldInfo(name, data, true)`（@841349）→ 落盘 `worlds/{名称}.json`；
- **与聊天文件的关系**：存档不在聊天文件（`chats/{角色}/{聊天}.jsonl`）里，两者独立——聊天文件存楼层（§32 的 chatSnapshot 是存档内嵌的一份**楼层快照副本**），世界书文件存游戏状态+存档（含该快照）；
- 所以备份/迁移卡档 = 同时带走 `worlds/{世界书}.json`（存档）+ `chats/{角色}/{聊天}.jsonl`（聊天记录）。

### 9.2 存档标识与结构

| 项 | 值 |
|---|---|
| 正式存档名 | `tangquan-save-v1` |
| 暂存存档名 | `tangquan-save-v1-staging` |
| 存档位 | 多 slot（`slotId`），当前位由变量 `activeSlotId` 指定 |

存档条目本体是一个 JSON，schema（zod 校验）字段：

```js
z.object({
  slotId,       // 存档位编号
  label,        // 存档标签/说明
  mode,         // 存档时的经营模式（老板/游客/服务员）
  updatedAt,    // 更新时间
  version,      // 存档格式版本
  chunkCount,   // 分块数量（见 9.4）
  byteLength,   // 原始 JSON 字节长度（校验用）
  checksum,     // 校验和（防损坏）
  payload,      // 分块后的实际内容
})
```

### 9.3 快照内容（Cr() 生成）

快照函数（约 `Cr()`）生成存档主体，记录**当前聊天状态**：

```js
{
  version,        // 格式版本
  capturedAt,     // 捕获时间戳
  chatId,         // 当前聊天 ID
  messageCount,   // 消息数量
  messages,       // 消息内容（或摘要）
  // + 当前模式 / 变量快照等游戏状态
}
```

另有默认快照 `Sr()`，用于首次进入/无存档时的初始状态。

### 9.4 分块机制（为什么有 chunkCount）

世界书单条条目容量有限，大存档 JSON 必须**分块**存放：

- 写入时：把快照 JSON 序列化 → 按字节切成 N 块 → 每块作为一个世界书条目 → `chunkCount` 记录块数；
- 读取时：按 `chunkCount` 收集所有块 → 拼接 → 用 `byteLength` + `checksum` 校验完整性 → 反序列化；
- 损坏/缺块：校验失败则回退到暂存档（`tangquan-save-v1-staging`）或默认快照。

### 9.4.1 读档完整实现（代码级，回答"读档怎么把大量上下文恢复"）

读档不是只恢复变量——**它把存档里的聊天快照原样重建回聊天**。链路（全部 `index.js` 偏移证据）：

**① 读存档分块并校验**（`worldbookSave.readSlotData` → `u()` @845556）：

```js
// 从当前聊天绑定的世界书里，按 slotId 过滤出该存档的全部条目
const o = (await getWorldbook(r)).filter(e => ao(e, a));       // ao = extra.source==='tangquan-save-v1' && slotId 匹配
const s = o.find(e => 'meta' === e.extra?.kind);               // 找 meta 条目（存档索引）
const i = ro(s);                                               // 解析 meta → {slotId, label, mode, chunkCount, checksum, ...}
const l = o.filter(e => 'chunk' === e.extra?.kind)             // 收集全部 chunk 条目
           .sort((a,b) => a.extra.part - b.extra.part)         // 按 part 排序
           .map(e => e.content);                               // 取内容
if (l.length !== i.chunkCount) throw new Error(`存档分片数量不正确`);
const d = l.join('');                                          // 拼接全部分片 → 完整存档 JSON 字符串
if (Zr(d) !== i.checksum) throw new Error(`存档校验失败`);      // checksum 校验
const u = Qr.parse(JSON.parse(d));                             // zod 解析 → 存档对象（payload.data.chatSnapshot 等）
```

**② 提取聊天快照并恢复**（`loadSlot` @830300 → `Br` @823650）：

```js
// loadSlot 主流程
const r = await e.worldbookSave.loadSlot(t);                   // ① 读档（上面的 u()）
const o = r.payload.data.chatSnapshot;                         // ② 从存档 payload 取 chatSnapshot
await Br(o, { loading: n, log: e.log });                       // ③ 恢复聊天快照
const s = $r(r.payload);                                       // ④ 提取用户信息（员工档案等）
await e.userProfileWorldbook?.upsertProfile(slotId, s);        //    写回用户信息世界书条目
Dr({ activeSlotId, activeMode, ... });                         // ⑤ 更新运行时变量（activeSlotId 等）
e.beautifier?.applyNow('存档载入完成');                         // ⑥ 触发视觉镜像刷新
```

**③ Br 恢复聊天快照本体**（@823650，核心）：

```js
async function Br(e) {
  // a) 快照自身校验
  const n = Cr(e.messages);                                    // 对 messages 重算 checksum
  if (n !== e.checksum) throw new Error('聊天快照校验失败，已停止恢复');

  // b) 清空当前聊天（分批 deleteChatMessages，0..lastMessageId 倒序）
  const ids = _.range(lastMessageId + 1).reverse();
  for (分批) await deleteChatMessages(batch, { refresh: 'none' });

  // c) 重建楼层（分批 createChatMessages）
  for (分批) await createChatMessages(snapshot.messages.map(hr), { insert_before: 'end', refresh: 'none' });

  // d) 恢复楼层附加数据（swipes_data / swipes_info，逐条）
  // e) loadCurrentChat() 刷新界面显示
}
```

**快照条目 → 楼层转换**（`hr` @823007，**原样保留所有字段**）：

```js
function hr(e) {
  return { role: e.role, name: e.name, is_hidden: e.is_hidden,
           message: e.message,
           data: _.cloneDeep(e.data),     // Mvu 变量快照（variables[0]）
           extra: _.cloneDeep(e.extra) }; // sceneId/traceId 等（tangquanSceneGeneration）
}
```

**结论**：读档 = **先清空当前聊天全部楼层 → 再把存档里的全量快照（含隐藏楼层、extra、data、swipes）分批重建**。所以即使你玩了几百轮、上下文巨大，读档后聊天界面和游戏状态**完整还原**——上下文没有丢，只是存在世界书快照里（`worlds/{世界书}.json`），读档时搬回聊天文件（`chats/{角色}/{聊天}.jsonl`）。

> 注意：`chatSnapshot` 的楼层是**存档时刻**的副本；存档后新产生的楼层不在里面（它们只存在聊天文件）。恢复后 `lastMessageId` 从快照的 `lastMessageId` 起算，之后的楼层在聊天文件里仍存在但存档快照不含——这是"切档回旧状态"的语义。

### 9.5 写入队列与触发时机

为避免频繁写档卡 UI，写入走**队列**：

- 变更事件（模式切换、关键变量变化、每日结算）→ 入队 → 串行写世界书（`saveWorldInfo`）→ `reloadCurrentChat` 重载聊天使世界书生效；
- 读档：`loadWorldInfo` 按名取回 → 校验 → 恢复变量与楼层。

触发点主要有：`reloadCurrentChat`、`saveWorldInfo`、`loadWorldInfo` 调用位置。

### 9.6 多 slot 机制

- 支持多个存档位（slot），玩家可切换；
- 切换存档 = 改 `activeSlotId` 变量 + 重新读对应 slot 的世界书条目 + 恢复快照；
- 存/读路径都带 slotId，互不干扰。

## 10. 世界书结构与提示词注入

### 10.1 总览

| 项 | 值 |
|---|---|
| 条目总数 | 382 条 |
| 存储 | 卡内 `character_book` / 世界书 |
| 用途 | 角色设定、建筑设施、变量定义、输出格式指令、任务系统 |

### 10.2 条目分类（comment 前缀）

世界书条目通过 `comment` 前缀分类，格式 `[未开之花][分类] 标题`：

| 前缀 | 内容示例 | 作用 |
|---|---|---|
| `[未开之花][项目]` | 项目设定、整体世界观 | 基础设定 |
| `[未开之花][角色]` | 角色定义（老板/游客/服务员等） | 人物设定 |
| `[未开之花][建筑]` | 汤泉设施（澡堂、包厢、花园…） | 场景设定 |
| `[未开之花][变量]` | 变量列表 / 输出格式 | MVU 变量说明与格式要求 |
| `[未开之花][变量规则]` | 变量更新规则、限制 | MVU 更新约束 |
| `[未开之花][InitVar]` | 初始变量指令 | 初始化 `stat_data` |
| 其它 | 每日安排、经营日报、任务系统等 | 玩法指令 |

### 10.3 关键条目内容

**① 初始变量（InitVar）**：MVU 初始化指令，首次运行时把 `stat_data` 建好：

```xml
<UpdateVariable>
  _.set('stat_data.老板.金币', null, 1000)
  _.set('stat_data.老板.口碑', null, '普通')
  _.set('stat_data.模式', null, '未选择')
  ...
</UpdateVariable>
```

**② 变量列表**：枚举当前所有变量路径、含义、取值，注入给模型，让模型知道"有什么状态可改"。

**③ 输出格式**：要求模型生成时输出：

```xml
<UpdateVariable><Analysis>...</Analysis>_.set(...)</UpdateVariable>
```

**④ 变量规则**：约束更新条件（哪些变量可改、每次变化幅度、不可乱改的字段）。

### 10.4 注入方式

- **常驻注入（injection）**：核心设定 + 变量列表 + 输出格式条目使用世界书 injection 机制，每轮生成都进上下文；
- **场景触发（按需注入）**：`worldbookRuntime.syncModeEntries` 按当前模式/场景同步激活对应条目（游客场景注入顾客条目、老板场景注入经营条目）；
- **深度/位置**：设定条目置顶（靠近 system），变量规则紧随，保证模型最先读到。

### 10.5 任务系统（xiaobaix-tasks）

卡内 `extensions.xiaobaix-tasks` 记录了任务系统配置（小百/任务玩法），与世界书条目配合驱动任务流程。
