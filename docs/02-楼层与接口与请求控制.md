## 4. 楼层系统与三种经营模式

### 4.1 楼层（楼层 = 聊天楼层）是什么

SillyTavern 的聊天以"楼层"（message）为单位纵向排列。这张卡的 UI 也是"一个楼层"：
前端控制器把**完整的 Vue 单页应用**注入到 iframe 的 `srcdoc` 中，再把这个 iframe **挂到某个聊天楼层上**，于是玩家看到的是"聊天记录 + 可交互的游戏 UI 楼层"混排。

- 关键实现点：`getLastMessageId()` 找到当前最后一条消息楼层，把 iframe 挂在其后；
- iframe 与消息楼层**共存**：AI 消息是普通楼层，UI 是 iframe 楼层。

### 4.2 三种经营模式

模式由 `stat_data` 中的变量控制（zod 枚举，非法值回退 `'未选择'`）：

```js
z.enum(['未选择', '老板', '游客', '服务员']).catch('未选择')
```

| 模式 | 玩法 | 前端对应模块 |
|---|---|---|
| 老板 | 经营整个汤泉（经济系统、排班、设施） | `bossEconomy` |
| 游客 | 以顾客身份体验设施、触发经营事件 | `customerGame` |
| 服务员 | 打工：接单、服务、结算工资 | 服务员相关组件 |
| 未选择 | 初始状态，引导玩家选择模式 | 引导 UI |

模式切换通过写变量实现：`activeMode`、`activeSlotId`（当前存档位）、`lastSwitchAt`（切换时间戳）。前端监听这些变量变化，切换 Vue 组件树。

### 4.3 前后端状态同步

因为"UI 在 iframe 里，状态在酒馆的 `stat_data` 里"，前端与 MVU 之间需要**双向同步**：

- `scheduleBossMvuSync`：老板模式的 MVU 同步（定时/事件驱动把前端状态写回变量）
- `scheduleWaiterGeneratedResultSync`：服务员模式 AI 生成结果同步

同步方式本质：读 `stat_data` 渲染 UI → 玩家操作 → 写回 `stat_data` → MVU 广播 → 其它楼层（世界书提示词）也能读到最新状态。

## 5. 与酒馆的接口调用

### 5.1 调用通道

前端跑在 iframe 里，**所有酒馆 API 都通过 `window.parent` 访问**酒馆助手挂载的全局函数。这是整张卡唯一的外联通道。

### 5.2 上行（前端 → 酒馆：写操作）

| API | 用途 |
|---|---|
| `replaceVariables(...)` | 写 `stat_data` / `display_data` 变量（模式切换、状态上报） |
| `getVariables(...)` / `MvuData` 读取 | 读变量（启动时恢复状态） |
| `setChatMessage(...)` | 改写聊天楼层内容（把 AI 原始输出替换为解析后的正文） |
| `createChatMessages(...)` | 创建消息楼层（前端把 UI 楼层/结果消息插入聊天） |
| `setChatMessages(...)` | 改写聊天楼层（把 MVU 变量状态 data 写回楼层） |
| `createChatMessages(...)` | 创建消息楼层（前端手动插入用户/AI 楼层，见 [6](#6-玩家输入操控与请求控制)） |
| `getChatMessages(...)` / `getLastMessageId()` | 读取聊天楼层（重建 chat_history 时用，含 `include_swipes`） |
| `saveWorldInfo(...)` / `loadWorldInfo(...)` | 读写世界书（**存档的载体**，见 [04-存档与世界书.md §9](04-存档与世界书.md)） |
| `reloadCurrentChat(...)` | 重载当前聊天（写档后刷新） |
| `replaceWorldbook(...)` / `deleteWorldbookEntries(...)` / `getCharWorldbookNames(...)` | 动态启停临时世界书条目（见 6.2） |
| `generate({...})` + `getGenerationText(result)` | **唯一**的 AI 请求原语（见 [6](#6-玩家输入操控与请求控制)） |
| `updatePresetWith('in_use')` | 切换/启停当前预设的 prompts（见 6.3） |
| `getPreset(...)` / `getLoadedPresetName()` | 读取当前预设配置 |
| `appendInexistentScriptButtons(...)` / `getButtonEvent(...)` / `updateScriptButtonsWith(...)` | 注册/响应酒馆脚本按钮（如"打开未开之花"） |
| `runAction(...)` / `waitGlobalInitialized(...)` | 执行酒馆动作 / 等待模块就绪（MVU） |

> ⚠️ **核查事实**：`generateRaw(`、`injectPrompts(`、`uninjectPrompts(`、`sendMessageAs(`、`setGenerateMode(` 在 `index.js` 中**全部 0 命中**——前端不使用这些 API。提示词注入走 `generate({ injects: [...] })` 参数，发送走 `createChatMessages`，不存在 `sendMessageAs` 调用。

### 5.3 下行（酒馆 → 前端：事件与反馈）

前端没有"主动轮询酒馆回复"的简单做法，靠两类机制拿反馈：

**① 事件订阅**（`eventOn` / `tavern_events.*`）：

| 事件 | 触发时机 | 前端用途 |
|---|---|---|
| `MESSAGE_SENT` | 玩家消息发出时 | **仅视觉用途**：楼层高亮（beautifier）、把玩家输入镜像到游戏界面；不拦截、不改生成 |
| `MESSAGE_RECEIVED` / `GENERATION_STARTED` / `GENERATION_STOPPED` / `GENERATION_ENDED` / `STREAM_TOKEN_RECEIVED` | 生成生命周期 | 镜像模块把 AI 输出**流式镜像**到游戏界面并同步状态；不改生成 |

**② MutationObserver**：监听 `window.parent.document.querySelector('#chat')` 楼层 DOM，生成结束后同步页面状态（`syncCustomerGeneratedResults` 等）。

**③ 本地解析**：AI 回复中的标签（`<UpdateVariable>`、`<content>` 等）由前端**本地正则解析**，不依赖模型再回传（详见 [03-正文识别与变量更新.md §7](03-正文识别与变量更新.md) 与 [§8](03-正文识别与变量更新.md)）。

> 📎 监听层的**完整实现**（事件订阅机制、用户发送后回调流程、流式镜像、DOM 观察、清理链）见 [07-监听层.md](07-监听层.md)。

**④ 全局自由 API 清单**：`generate / getGenerationText / eventOn / tavern_events / getVariables / replaceVariables / getPreset / updatePresetWith / getLoadedPresetName / getChatMessages / getLastMessageId / createChatMessages / setChatMessages / deleteChatMessages / getCharWorldbookNames / replaceWorldbook / deleteWorldbookEntries / appendInexistentScriptButtons / getButtonEvent / updateScriptButtonsWith / waitGlobalInitialized / SillyTavern / runAction / Mvu` 全部来自酒馆/助手宿主（`window.parent`）。

## 6. 玩家输入操控与请求控制

> 这是理解"卡如何控制 AI"的关键章节。核心结论：**玩家输入由前端直接接管并重发，AI 请求由前端直接发起（`generate`），并通过预设切换 + 提示词注入 + 世界书同步三层来控制"带预设的请求"。**

### 6.1 玩家输入如何被操控

1. 玩家的输入框在**前端 iframe 内**（AIRP 现场互动输入框、游客联系人消息框等），提交的内容先到前端；酒馆**主输入框不被监听/拦截**。
2. 玩家输入文本**原样**作为 `user_input` 传给 `generate()`（不包裹 XML、不替换文本）：

   ```js
   const result = await generate({
     user_input: userText,        // 玩家原文本
     should_stream: true,
     overrides: { chat_history: { with_depth_entries: true, prompts: chatHistoryPrompts } },
     ...(customerInjects?.length ? { injects: customerInjects }
         : waiterInjects?.length  ? { injects: waiterInjects } : {}),
   });
   ```

3. 但**请求上下文被前端完全接管**：
   - **chat_history 覆盖**：`getChatMessages('1-${lastMessageId}', {include_swipes:true})` 取楼层消息，按 `message.extra.sceneId` 过滤出**同场景消息**重建 prompts——酒馆默认历史被替换；
   - **格式注入**：`injects` 注入 `{position:'in_chat', depth:1, role:'system', content:'[输出格式要求]…', should_scan:false}`（Galgame 短对话 / 完整 AIRP 正文 / 联系人消息三档）；
   - **前置状态**：`syncPresetOutputFormat` 切预设 + `replaceTemporaryEntries` 启停临时世界书条目（如 `area.current`、`character.current-employee`）。
4. 生成结果由前端**手动创建楼层**（不经酒馆发送流程）：

   ```js
   await createChatMessages(
     [ { role:'user',     message: userText, data: oldMvuData, extra: {...场景标记} },
       { role:'assistant', message: parsedMessage.displayText, data: newMvuData, extra: {...} } ],
     { insert_before:'end', refresh:'none' });
   ```

   用户消息带 `extra`（traceId/mode/kind/outputMode/sceneKey/speaker/participants 等场景标记，`makeSceneGenerationExtra`）；助手消息只写**剥离 XML 后的纯文本** `displayText`；MVU 变量状态（`data`）经 `setChatMessages` 写回楼层。

> 结论：输入文本本身不被清空/替换/追加，但**发送流程被前端拦截**——捕获输入 → 自行组装 chat_history + injects + 预设 + 临时世界书 → 调 `generate()` → 手动写楼层。

> 🔍 **核查事实（玩家输入零修改）**：
> - 全文件搜 `玩家输入` / `玩家输入：` 字面量：**0 处**——不存在"玩家输入：xxx"包装前缀；
> - `user_input` 在 AIRP 现场（`submitAirpInput`：`userText = inputBoxValue.trim()`）、联系人消息（`userText = payload.text.trim()`）、重 Roll（`getSceneMessageText(pair.userMessage).trim()`）都是**玩家原文本，只 trim**；
> - CoT（💭 思维链）在**预设**里、输出格式要求在 **injects** 里（`{position:'in_chat', depth:1, role:'system', content:'[输出格式要求]...'}`），二者是独立提示词段，**不拼在 user_input 前后**；
> - 实际发送结构 = 角色设定+世界书+预设(含思维链) + 同场景聊天历史 + injects(格式要求@depth:1) + **user_input(玩家原文，最后)**；
> - 唯一例外：每日安排/经营日报 `user_input:''`（空，卡直接发数据包）；AI 人才市场 `user_input` = 玩家操作 **JSON 序列化**（非聊天文本）。

### 6.2 请求时注入/替换的提示词（三层）

| 层 | 内容 | 实现 |
|---|---|---|
| 临时世界书 | 按当前模式/场景激活的规则条目（`area.current`、`character.current-employee` 等） | `replaceTemporaryEntries` / `worldbookRuntime.syncModeEntries` |
| 注入提示词段 | 输出格式要求、思维链要求、变量更新指令（`position:'in_chat', depth:0/1, role:'system'`） | `generate({ injects: [...] })` 参数 |
| 预设覆盖 | 输出格式预设（思维链版/简洁版） | `presetOutputFormat.setFormat()` → `updatePresetWith('in_use')` |

### 6.3 输出格式预设（预设 = 酒馆 preset）

`presetOutputFormat` 模块维护**5 种输出格式 prompt + 3 种思维链 prompt**，命名带 emoji：

```js
// 输出格式（ir 常量）：
'🎯 未开之花·Galgame输出'      // 短对话："角色名: 台词" 一行一页
'🎯 未开之花·AIRP正文输出'      // 完整正文：正文放 <content>
'🎯 未开之花·游客每日安排输出'
'🎯 未开之花·服务员每日安排输出'
'🎯 未开之花·老板经营日报输出'

// 思维链（lr/cr/dr 常量）：
'💭 思维链'                      // 通用
'💭 未开之花·每日安排思维'
'💭 未开之花·经营日报思维'
```

切换逻辑 `setFormat(t, reason)`：
- 只**启用目标输出格式 prompt**，其余输出格式 prompt 禁用（`updatePresetWith('in_use', ..., {render:'none'})` 直接改写酒馆**当前预设**的 prompts 启停，不污染全局配置文件）；
- `cr` 在游客/服务员每日安排时启用、`dr` 在老板日报时启用、`lr` 在非安排/日报场景启用；
- `inspect()` 用 `getPreset('in_use')` + `getLoadedPresetName()` 检查目标 prompt 是否存在，缺则跳过（不覆盖玩家手动改动）。

场景映射 `syncPresetOutputFormat`：story → `airp`、dialogue → `galgame`、无场景 → `none`。

### 6.4 各场景的请求

| 场景 | 触发 | 请求特点 |
|---|---|---|
| 每日安排（游客/服务员） | 手动跨日 / 休息到次日 | `setFormat('customerDaily'\|'waiterDaily')` + 构造 `<daily_input>` XML（员工/指名/项目/区域/住宿状态）+ **`makeDailyGenerationOverrides()` 清空全部上下文**（world_info/persona/char/chat_history 全空，只发注入内容） |
| 经营日报（老板） | 手动跨日 / 每日结算 | `setFormat('bossDaily')` + 冻结结算事实注入 + 同样全清 overrides；`applyBossDailyReport` 解析 `<boss_daily_report>`，失败用本地纪要 fallback |
| 顾客事件（AIRP 现场互动） | 游客游玩 | `setFormat('airp')` + 同场景历史重建 + 临时世界书替换 |
| 重 Roll | 重掷骰子 | `rerollLatestSceneGeneration`：取上一轮用户消息原文再次生成，结果作新 swipe |
| AI 人才市场 | 招聘/人设 | `setFormat('none', '严格 JSON')` + `user_input=JSON.stringify(input)` + 系统提示词注入；**最多重试 2 次**，失败后注入"重试提示词"（含上次 issues）重新生成 |

### 6.5 关于"重试额外模型解析"

卡内有一个"重试额外模型解析"按钮（变量 `重试额外模型解析` 相关），设计意图是：当 AI 第一次输出格式不标准时，用**第二次请求**把原始输出重新解析。经代码核查：

> **该按钮当前未实现**（只在卡 JSON 的脚本按钮清单中声明 `visible:false`，index.js 中 0 命中，无事件绑定）。同批声明的"快照楼层/重演楼层/重新处理变量/清除旧楼层变量"按钮也均未实现；index.js 只注册并响应了"打开未开之花"。

**实际存在的"第二次请求"只有两种（均为重新生成，非解析原始输出）**：
1. AI 人才市场重试：最多 2 次，失败后在 injects 追加重试提示词（含上次校验 issues）重新生成；
2. AIRP 重 Roll：同输入再次生成，结果作新 swipe。

**真正的解析全部是本地纯 JS**（无第二次模型调用）：`parseTangquanAiMessage`（见 [03-正文识别与变量更新.md §7](03-正文识别与变量更新.md)）+ 酒馆 `Mvu.parseMessage` 解析 `<UpdateVariable>`；`<customer_daily>/<waiter_daily>` 用 DOMParser 校验解析，失败走**确定性安排 fallback**，不会自动发起第二次模型请求。
