## 11. 避坑指南（少走弯路）

### 11.1 环境类

1. **酒馆助手是硬依赖**：前端所有外联都走 `window.parent` 的酒馆助手全局 API。没有它脚本连初始化都过不去。装好再测。
2. **`z`（zod）是全局自由变量**：`index.js` 与 `magvarupdate.js` 里的 `z` 都不 import、不定义、不挂载，依赖外部注入。这是最容易踩的坑——**别在本地加 `import { z }`**，要改就统一改所有使用点；也别依赖"某个 bundle 自带 zod"，要看运行环境是否真的注入了全局 `z`。
3. **MVU 变量是玩法地基**：变量更新靠 MVU 扩展，`<UpdateVariable>` 解析在 `magvarupdate.js` 里。改玩法时先确认 MVU 是否就绪（`waitGlobalInitialized('Mvu')`）。
4. **预设切换只动当前会话**：用 `updatePresetWith('in_use')`，不要改全局 preset 配置文件，否则会污染玩家其它聊天。

### 11.2 架构/代码类

5. **单行大文件无法用 grep/read_file 正常分析**：`index.js` 是无换行的 1.2MB 压缩 bundle，`grep` 按行匹配会失效（行长超限）。分析时用 python/脚本按字节定位，或把关键片段 `head -c` 分段。
6. **内嵌 import 字符串 ≠ 运行时依赖**：`import './customerGame'`、`import '../../runtime/mvuRuntime'` 等只是**内嵌 SFC 源码字符串**（模板字符串闭合，无 eval/new Function），没有运行时加载行为。排查"加载失败"时别往这上面找。
7. **UI 楼层与消息楼层混排**：前端是挂到聊天楼层里的 iframe（虚拟楼层 `data-tq-visual-zero` + `#tangquan-game-ui-host` 容器，克隆最后一条消息楼层并追加到 `#chat` 末尾）。改 UI 布局时注意它和 AI 消息楼层是"共存"关系，不是替代关系；克隆楼层会带 `mesid=0`、不参与聊天编号（详见 06 文档）。
8. **双向状态同步别漏**：UI 在 iframe，状态在 `stat_data`。只写变量不触发 UI 刷新、或只刷 UI 不写变量都会出问题。参考现成的 `scheduleBossMvuSync` / `scheduleWaiterGeneratedResultSync` 模式。
9. **思维链剥离清单要同步维护**：`parseTangquanAiMessage` 的剥离标签清单（`Ho`：信息判定/行为逻辑/心里话/思维链/思考/分析/元认知/thinking/analysis/reasoning/UpdateVariable/变量更新/mvu/status_update/variables）。新增标签类型时务必加进清单，否则思维链会漏进正文。
10. **"重试额外模型解析"未实现**：卡里有这个按钮的入口变量，但实际没有二次请求逻辑。不要依赖它兜底；容错靠本地解析的健壮性。
11. **分块存档的完整性**：世界书条目容量有限才分块（chunkCount/byteLength/checksum）。改存档结构时：
    - 改 schema 前先考虑旧档兼容（version 字段）；
    - 分块读回必须校验 checksum，失败回退暂存档/默认快照；
    - 写入走队列，别高频直接调 `saveWorldInfo` + `reloadCurrentChat`（会卡 UI）。
12. **临时世界书同步**：`worldbookRuntime.syncModeEntries` 按模式/场景切换注入条目。新增玩法时，要让新条目能按场景被同步激活，否则模型读不到。
13. **监听层防抖是双刃剑**：beautifier 用 120ms 防抖重算楼层高亮、App.vue 后台同步用 2800ms 防抖——**改监听回调时别去掉防抖**（克隆楼层会高频触发 MutationObserver，无防抖会卡）；但调试时防抖会"延迟生效"，先在控制台确认事件确实派发了再找 UI 没变的原因。
14. **克隆楼层会自己触发监听器**：前端克隆用户/AI 消息到零层（`data-tq-visual-zero`）会产生新 DOM，又触发 beautifier 的 MutationObserver 二次防抖——**这是正常设计**（保证高亮与属性一致），不是 bug。自己做镜像时要注意避免死循环（用 `data-tq-source`/`data-tq-preview` 标记过滤）。
15. **流式镜像用普通 eventOn 顺序注册**：zeroLock 的 `STREAM_TOKEN_RECEIVED` 监听是 13 个事件里**唯一**用普通 `eventOn`（不带 `eventMakeLast`）的，因为它必须**先于其它处理器**拿到完整 token 流。新增流式处理时注意注册顺序。
16. **所有监听器都要有清理出口**：事件用 `.stop` 收集、DOM 观察器记引用、window 监听配对称 `unbind`、入口统一 `dispose` + `pagehide` 兜底。**漏一个清理 = 酒馆页面残留**（重复初始化时会出现双份事件回调）。

### 11.3 制作同类卡的建议

1. **先画分层图再动手**：酒馆宿主 / 酒馆助手 API / MVU / iframe 前端 / 世界书，五层职责分开，别混在一个脚本里。
2. **格式约定提前定死**：思维链标签、正文标签（`<content>`）、变量更新段（`<UpdateVariable>`）、选项标签，这些是模型协议的一部分。世界书输出格式条目 + 前端剥离清单 + MVU 解析器三处必须一致。
3. **提示词三层控制**：临时世界书（场景规则）+ `injectPrompts`（临时指令）+ 预设切换（输出格式）。三层职责分离，改一处不牵连其它。
4. **存档与 UI 状态解耦**：存档只存"可恢复的最小状态"（快照 + 变量），UI 状态每次启动重建。
5. **多 slot 存档是加分项**：机制简单（slotId 分条目 + activeSlotId 切换），体验提升明显。
6. **测试环境准备**：本地跑通酒馆 + 酒馆助手 + MVU，脚本直接丢进角色卡 extensions.tavern_helper 引用即可联调。
