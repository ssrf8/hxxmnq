## 7. 回复正文识别与思维链剥离

### 7.1 问题背景

为了让模型"先想后答"，卡要求 AI 输出包含多种标签包裹的段落：

- 思维链/分析段：`<Analysis>...</Analysis>`、`thinking`、`reasoning` 等（模型内部推理，不应展示给玩家）
- 变量更新段：`<UpdateVariable>...</UpdateVariable>`（驱动游戏状态，见 [8](#8-cot-思维链与-mvu-变量更新)）
- 选项/分支：`<XX>...</XX>` 形式的格式包裹
- 真正的正文：玩家应该看到的对话/描述/结果

如果直接把 AI 原始输出当正文展示，玩家会看到一大坨思维链和标签。所以前端必须**识别并剥离**这些结构，只保留正文。

### 7.2 正文包裹协议：`<content>正文</content>`（回答"有没有正文包裹"）

**有。** 标准协议是 **`<content>正文</content>`**（另有 `<time>` / `<时间>` 可选），由前端 injects 与预设共同要求：

```js
// 前端 injects 的格式要求（minified lc → ic，index.js @951545 附近）
'正文放在 <content>...</content> 中。'
'<content> 内只写当前角色真正说出口的台词，每行格式：'
'角色名: 台词'
'变量更新放在 </content> 之后按已有格式输出。'
```

**协议分层（重要——正文协议不在世界书里）**：

| 协议 | 内容 | 位置 |
|---|---|---|
| **正文包裹协议** | `<content>正文</content>`、`<time>`、Galgame"角色名: 台词" | **前端 injects**（`lc`/`ic`）+ **预设**（🎯 输出格式 prompt 段） |
| **变量更新协议** | `<UpdateVariable><Analysis>思维链</Analysis><JSONPatch>[...]</JSONPatch></UpdateVariable>` | **世界书条目** `[未开之花][变量] 输出格式` |
| **变量更新规则** | 哪些变量可改、更新条件、幅度限制 | 世界书条目 `[未开之花][变量规则]` ×4 |

> 世界书里唯一的"输出格式"条目（`[未开之花][变量] 输出格式`）管的是**变量更新**格式（JSON Patch RFC 6902），与正文包裹无关。正文包裹是场景化的，由前端按模式（Galgame/AIRP/联系人）动态注入——这也是为什么它藏在 injects/预设里而不是常驻世界书。

#### 7.2.1 轻量注入的实现：`lc` / `ic` 三档格式（完整）

`lc`（= `makeCustomerGenerationInjects`，@951545）是**每请求动态生成**的格式要求注入器，产出 `generate({injects})` 的 `injects` 参数：

```js
function lc(e, t) {                    // e=outputMode（dialogue/story/message），t=当前说话人
  let n;
  switch (e) {
    case 'dialogue': default: n = ic(t || '');       // ① Galgame 短对话（游客现场默认）
    case 'story':   n = storyFormat(t || null);      // ② 完整 AIRP 正文
    case 'message': n = messageFormat(t || '');      // ③ 联系人线上消息
  }
  return [{ position:'in_chat', depth:1, role:'system', content:n, should_scan:false }];
}
```

**① Galgame 短对话（`ic`，@950356）——游客现场默认**

```
[输出格式要求]
当前互动类型：Galgame 短对话。

<content> 内只写当前角色真正说出口的台词，每行格式：
角色名: 台词

一行对应一页台词，可以有多行但保持简短。
当前说话人：${speaker}。

禁止：
- 旁白、环境描写、角色内心独白
- 信息判定、行为逻辑、思维过程
- 台词预演或多种可能
- 代替 <user> 说话或行动
- 正文开头的孤立符号如 -
- 把变量更新写进 <content>

变量更新放在 </content> 之后按已有格式输出。
```

**② 完整 AIRP 正文（story）**

```
[输出格式要求]
当前互动类型：完整 AIRP 正文。
正文放在 <content>...</content> 中。
使用当前已激活的地点、员工、项目和关系事实继续场景。
当前主要角色：${speaker}。
用户已输入的动作可以承接和描写结果。
禁止：思维链、分析、信息判定、行为逻辑、心里话
     - 代替 <user> 决定未输入的行动、心理和台词
     - 凭空加入没有激活的主要角色
     - 重复罗列变量或当前状态
     - 把变量更新写进 <content>
如果剧情确实推进时间，可在 </content> 后输出：
<time>YYYY年MM月DD日 星期X HH:mm</time>
没有明确时间推进时不要输出虚假的时间变化。
变量更新放在最后按已有格式输出。
```

**③ 联系人线上消息（message）**

```
[输出格式要求]
当前互动类型：联系人线上消息。
<content> 内只写当前员工发回的一条消息，格式：${speaker}: 回复内容
这是线上消息，不是面对面场景。
禁止：环境旁白或动作描写 / 代替用户回复 / 描写双方已经见面
     / 把员工当前位置写成用户所在地 / 写成长篇正文 / 把变量更新写进 <content>
回复长度符合聊天软件消息习惯。约会可以接受、犹豫、拒绝或商量时间，按人设和关系决定。
邀约成功只代表约定成立，不代表见面已经发生。
变量更新放在 </content> 之后按已有格式输出。
```

> 三个格式都：① 以 `[输出格式要求]` 开头；② 只规定 `<content>` 内放什么（正文/台词/消息）；③ 强制"变量更新放 `</content>` 之后"；④ 禁止把思维链/旁白/替 `<user>` 行动写进正文。这就是"预设 🎯 输出格式 prompt 段"的**轻量副本**——预设那段是完整版（常驻），injects 这段是精简版（每请求随 outputMode 换档）。两者共同保证模型遵守 `<content>` 协议。

#### 7.2.2 轻量注入的位置语义（in_chat depth:1 在玩家输入上面）

`lc` 返回的 injects 是 `{ position:'in_chat', depth:1, ... }`，与 `user_input`（玩家输入原样）一起传给 `generate()`（`submitAirpInput`@274693）。SillyTavern 组装 prompt 时 **depth 从聊天末尾往前数（0=最接近生成点）**，`user_input` 被追加为最后一条 user 消息。最终顺序：

```
[系统提示/角色卡/世界书/persona...]
[聊天历史 messages]            ← depth 从末尾往前递增
[injects · 输出格式要求(三档之一)] ← in_chat + depth:1，插在最后一条历史消息附近
[user_input · 玩家输入]          ← 最后一条（depth 0，最接近模型生成点）
```

即模型实际看到的是 **「历史 + [输出格式要求] + 玩家输入」**：先读规则、再读输入、然后生成回复。格式要求段**聊天界面完全不可见**（纯请求参数）。

前端诊断日志佐证（@273319-273500 附近 `submitAirpInput`）：

```js
// 生成诊断
{
  sceneId: identity.sceneId,
  inputSource, inputBoxValue,
  generateUserInput: userText,                        // 玩家输入原样（仅 trim）
  chatHistory: chatHistoryPrompts,                    // 覆盖后的聊天历史
  chatHistoryOverrideCount: chatHistoryPrompts.length,
  exactCurrentInputInHistory: chatHistoryPrompts.filter(p => p.content.trim() === userText).length,
  currentInputAppendCount: 1,                         // 前端知道：玩家输入会追加 1 次（user_input）
}
```

| 对比项 | 普通世界书/预设注入 | 这张卡的 `lc` injects |
|---|---|---|
| 载体 | 世界书条目 / preset prompt | `generate()` 参数，**每请求动态生成** |
| 内容 | 静态文本 | 按 outputMode 三选一，带 `${speaker}` 动态变量 |
| 位置 | 世界书 before/after 或 preset 段 | `in_chat` depth:1，贴近生成点 |
| 可见性 | 聊天界面部分可见 | 聊天界面完全不可见 |
| 失效 | 关闭世界书/预设 | 前端不传 injects 即消失 |

### 7.3 本地解析器：`parseTangquanAiMessage`

前端在 `MESSAGE_RECEIVED` / 生成结束时，对 AI 原始输出调用本地解析函数 `parseTangquanAiMessage`，完成：

1. **剥离思维链/内部推理段**——按标签清单逐段删除；
2. **提取结构化字段**——如 `<content>`（正文）、`<time>`（时间/时序）；
3. **生成最终正文**——用于 `setChatMessage` 替换楼层内容、或写入变量/UI。

### 7.4 剥离标签清单（`Ho` 列表）

代码中维护了一份**需要剥离的标签名清单**（中文 + 英文），命中即视为"非正文"：

```
信息判定 / 行为逻辑 / 心里话 / 思维链 / 思考 / 分析
元认知 / thinking / analysis / reasoning
UpdateVariable / 变量更新 / mvu / status_update / variables
```

> 含义：任何 `<信息判定>...`、`<思考>...`、`<thinking>...`、`<Analysis>...`、`<UpdateVariable>...` 等段都会被删除，**不进入正文**。其中 `<UpdateVariable>` 段不是删除就完事——它被 [8](#8-cot-思维链与-mvu-变量更新) 单独提取执行。

### 7.5 正文识别的完整链路

**`parseTangquanAiMessage`（minified `Ko` @870310）完整判定逻辑**：

```js
function Ko(e) {
  const t = e.trim();
  const n = Jo(t, Uo);                    // ① 提取所有 <content> 段
  const a = n.at(-1) ?? '';               //    取最后一个 content 段
  const r = 0 === n.length ? Xo(t) : '';  // ② 没有 content → 剥离法处理全文
  const o = a ? Xo(a) : r;                // ③ content 段（或剥离后全文）再清标签
  const s = o || '对方暂时没有继续回应。';  // ④ 兜底文案
  const i = (提取 <time>/<时间> 最后一个) ?? '';  // ⑤ 时间
  return { rawText: t, displayText: s, contentText: o, timeText: i,
           dialoguePages: es(s), usedContentTag: 1 === n.length,
           contentTagCount: n.length };
}
```

```
AI 原始输出（含思维链、变量更新段、正文）
        │
        ▼
Ko（parseTangquanAiMessage @870310）
  ├─ ① Uo 正则提取 <content> 段（取最后一个）
  ├─ ② 没有 <content> → 全文走 Xo 剥离
  ├─ ③ Xo 再清一遍 content 段残留标签
  ├─ ④ 兜底："对方暂时没有继续回应。"
  ├─ ⑤ Lo 正则提取 <time>/<时间>（取最后一个）
  ├─ ⑥ es @871450 按 "角色名: 台词" 分页 → dialoguePages
  └─ 返回 { rawText, displayText, contentText, timeText, dialoguePages,
            usedContentTag, contentTagCount }
        │
        ▼
displayText（剥掉 XML 后的纯文本）→ 经 createChatMessages 手动写入楼层
  + newMvuData = Mvu.parseMessage(message, parseBase) → 变量更新回调刷新 UI
```

**`Xo` 剥离函数（@870629）三层清理**：

```js
function Xo(e) {
  let t = e;
  // 第一层：按 Ho 清单，删 <思维链>...</思维链>、<thinking>...</thinking> 等整段
  //         同时支持 BBcode 语法 [thinking]...[/thinking]
  for (const e of Ho) {
    t = t.replace(new RegExp(`<([^<>/\s]*${e}[^<>/\s]*)[^>]*>[\s\S]*?<\/\1\s*>`, 'gi'), '');
    t = t.replace(new RegExp(`\[([^\]/\s]*${e}[^\]/\s]*)[^\]]*\][\s\S]*?\[\/\1\s*\]`, 'gi'), '');
  }
  // 第二层：删 <time>/<时间> 段
  for (const e of Lo) t = t.replace(new RegExp(e.source, e.flags), '');
  // 第三层：从最后一个思维链标签起把后面全删（标签未闭合的兜底）
  for (const e of Ho) {
    t = t.replace(new RegExp(`<[^<>/\s]*${e}[^<>/\s]*[^>]*>[\s\S]*$`, 'gi'), '');
    t = t.replace(new RegExp(`\[[^\]/\s]*${e}[^\]/\s]*[^\]]*\][\s\S]*$`, 'gi'), '');
  }
  // 收尾：剥所有 <> 标签、清行首破折号/星号/引号、压缩空行
  return t.replace(/<[^>]+>/g, '').replace(/^\s*[-–—>*`]+\s*$/gm, '')
           .replace(/\r?\n{3,}/g, '\n\n').trim();
}
```

**`es` 分页函数（@871450）——正文切成"角色名: 台词"页**：

```js
function es(e) {
  // ① 按行匹配 "角色名: 台词"（Yo 正则：1-24 字符名字 + 中文/英文冒号）
  let t = e.split(/\r?\n/).map(e => e.match(Yo)).filter(Boolean)
           .filter(e => !Qo.has(e[1].trim()))      // 过滤"信息判定:"等系统前缀行
           .map(e => ({speaker: e[1].trim(), text: e[2].trim()}));
  // ② 没有 "角色名:" 行 → 降级：提取 "台词"（引号内），speaker 留空
  return t.length > 0 ? t : Array.from(e.matchAll(/“([^”\n]+)”([^\n]{0,16})/g))
     .filter(e => !/^\s*(?:我|<user>)(?:问|说|答|回应|补充|笑|低声|轻声|开口)/i.test(e[2]??''))
     .map(e => ({speaker:'', text: e[1].trim()}));
}
```

### 7.6 兜底与容错

- 若模型**没按格式输出**（没有标签、标签残缺）：`parseTangquanAiMessage` 的解析结果退化为"整段当正文"或"尽力提取可识别片段"，保证玩家至少能看到回复，不会白屏；
- "重试额外模型解析"按钮当前**未实现**（见 02 文档 6.5），所以容错完全依赖本地解析的健壮性。

## 8. CoT 思维链与 MVU 变量更新

### 8.1 MVU 输出格式总览

MVU（MagVarUpdate）约定模型输出中带一段特殊标签：

```
<UpdateVariable>
  <Analysis>（思维链：逐变量分析是否满足更新条件，以及新值是多少）</Analysis>
  _.set('stat_data.老板.金币', 100, 250)
  _.set('stat_data.老板.口碑', '普通', '很好')
</UpdateVariable>
```

- `<Analysis>` 段 = **CoT 思维链**：模型在这里"思考"每个变量该不该变、变成多少；
- `_.set('路径', 老值, 新值)` 语句 = 具体的变量更新指令；
- 该段由 MVU 扩展（`vendor/magvarupdate.js`）解析执行，**不进正文**（前端本地解析时也按 Ho 清单把它从正文里剥离）。

### 8.2 变量更新执行链路（magvarupdate.js）

**更新执行**：`<UpdateVariable>` 由酒馆 **`Mvu.parseMessage(message, parseBase)`** 解析（index.js 在生成后调用，得到 `newMvuData`），MVU 内部正则提取 `_.set('路径', 老值, 新值)` 语句并更新 `stat_data` / `display_data`。完整链路：

```
AI 原始输出
   │
   ▼
MVU 正则提取 <UpdateVariable> ... </UpdateVariable>
   │
   ▼
解析 _.set('路径', 老值, 新值) 语句（正则匹配每条语句）
   │
   ▼
按路径更新 stat_data / display_data
（校验"老值"与当前值一致，避免覆盖并发变更；新值类型校验）
   │
   ▼
广播 MVU 事件 + 前端回调
```

关键点：

| 点 | 说明 |
|---|---|
| 路径 | 形如 `stat_data.老板.金币`，支持嵌套对象 |
| 老值校验 | `_.set('路径', 老值, 新值)` 中的老值用于并发冲突检测 |
| 事件 | MVU 更新前后触发事件（`mag_variable_update_started / _ended / _updated` 一类），前端订阅刷新 UI |
| 类型 | zod 参与变量 schema 校验（全局 `z`） |

### 8.3 前端如何消费更新后的变量

1. 前端订阅 MVU 变量更新事件（或 `MutationObserver` 监听 `stat_data`）；
2. 事件触发后读取最新 `stat_data`（`MvuData` / `getVariables`）；
3. 重渲染对应 UI 组件（金币、口碑、楼层状态、模式切换等）；
4. 若更新发生在"每日安排/经营日报"流程中，还会触发后续处理（`scheduleWaiterGeneratedResultSync`、`scheduleBossMvuSync` 等）。

### 8.4 世界书如何要求模型"先分析再更新"

世界书（见 10）中按 `[未开之花][变量]` 前缀维护：
- **变量列表**：告诉模型当前有哪些变量（路径、取值、含义）；
- **输出格式**：要求模型输出 `<UpdateVariable><Analysis>...</Analysis>_.set(...)</UpdateVariable>` 结构；
- **变量规则**：哪些变量可改、更新条件、每次更新限制（避免模型乱改数值）。

这些条目常驻注入（injection），保证模型每次生成都遵守格式。

### 8.5 完整链路一图流

```
玩家提交（iframe 内输入框） → 前端接管请求：chat_history 覆盖 + injects 规则 + 预设切换 + 临时世界书 → generate()（带思维链预设）
    → AI 输出（思维链 + <UpdateVariable> + 正文）
    → parseTangquanAiMessage 剥离思维链/标签 → 正文（displayText）手动写入楼层
    → Mvu.parseMessage 提取 <UpdateVariable> 执行 _.set → stat_data 更新
    → MVU 事件 → 前端刷新 UI → 世界书读到新状态 → 下一轮请求更准
```
