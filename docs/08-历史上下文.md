# 历史上下文机制：场景过滤、上下文清空与隐藏注入

> 本文档是架构文档的续篇，讲解：
> - 聊天历史对话是如何进入 AI 请求上下文的（是否被处理 / 是否原样发送 / 是否隐藏）
> - 角色卡内是否有隐藏正则（结论：没有，隐藏逻辑全在脚本里）
> - 4 个"对模型可见、玩家不可见"的隐藏上下文注入点

---

## 25. 总体结论（先看结论）

| 问题 | 答案 |
|---|---|
| 历史对话经过处理吗？ | **经过**。按"场景"过滤（只发当前场景的楼层），但**内容本身只 trim，不加前缀不精简** |
| 是原样在酒馆 API 上下文发送吗？ | **不是**。前端重建 chat_history（`overrides.chat_history.prompts`），场景请求只覆盖 chat_history；每日安排/日报几乎清空全部上下文 |
| 有隐藏上下文吗？ | **有，4 个注入点**：injects / 动态临时世界书 / 预设注入 / zeroLock 视觉零层 |
| 卡内有隐藏正则吗？ | **没有**。角色卡 JSON 里无任何正则脚本；唯一 `"use_regex":true` 是世界书 keys 匹配标志 |

## 26. 场景请求：chat_history 覆盖 + 场景隔离

### 26.1. 构建（makeSceneChatHistoryPrompts @decoded 4295-4313）

```js
getChatMessages('1-${lastMessageId}', {include_swipes:true})
  → 过滤 role ∈ {system, user, assistant}
  → 映射 {messageId, role, content: getSceneMessageText(message),
          hidden: message.is_hidden,
          sceneId: extra?.sceneId, legacySceneKey: extra?.sceneKey}
  → buildTangquanSceneHistoryPrompts()   // minified: Du @17773
```

### 26.2. 过滤规则（minified Du @17773）

```
filter(Number.isInteger(messageId))
filter(messageId > identity.startedAfterMessageId && messageId < beforeMessageId)
filter(!hidden && (消息.sceneId ? sceneId===identity.sceneId
                               : legacySceneKey===identity.legacySceneKey))
filter(role ∈ system/user/assistant) → trim → 去空 → 按 messageId 升序
```

**含义**：
- 保留「当前场景 `sceneId`（或旧版 `sceneKey` 完全一致）内、开始于 `startedAfterMessageId` 之后、非 `is_hidden`」的楼层；
- 过滤掉：其它场景楼层、隐藏楼层、`<三明月>` 占位（0 号，`is_hidden:true`）、`1-` 起始范围外的楼层；
- **消息内容只 `trim`，不加前缀、不精简、不改写**，原样以 `{role, content}` 进 prompts；
- `beforeMessageId` 仅在重掷用户楼层时传入（截断该楼之后的历史）。

### 26.3. generate() 调用（@decoded 5349-5363）

```js
overrides: { chat_history: { with_depth_entries: true, prompts: chatHistoryPrompts } }
```

**只覆盖 chat_history**——世界书、角色卡描述、persona、jailbreak、系统提示词全部保留。

### 26.4. 如何分辨楼层属于哪个角色（场景即角色）

**核心答案：按 `sceneId`（场景）分辨，不按角色字段。** 每个"对话场景"天然绑定一个说话人/一组参与者，楼层写 extra 时带上场景的 `sceneId`，过滤时只比对 `sceneId`。

**① 楼层 extra 里有哪些标识**（`makeSceneGenerationExtra` / `bs` @1034809，写入每条现场/联系人楼层）：

```js
{ tangquanSceneGeneration: {
    version: 2, traceId, mode, kind, outputMode,
    sceneKey,          // = [mode, kind, title, speaker, ...participants].join('|')  ← 含说话人
    speaker,           // 说话人名
    participants,      // 参与者名列表
    sceneId,           // 场景唯一 ID（角色分辨的关键）
    startedAfterMessageId,
    speakerId,         // character:{id} / role:boss / role:coworker / actor:{名}
    participantIds,
    characterId,       // findTangquanCharacter(speaker)?.id
    locationId, serviceId, projectId, assignmentId, role
}}
```

**② 两种场景的 sceneId 生成规则**（`prepareAirpSceneIdentity` @218433）：

| 场景类型 | sceneId | 特点 |
|---|---|---|
| 现场（老板/游客/服务员） | `scene.sceneId || makeTangquanRuntimeSceneId(随机)` | 进入现场时生成并**持久化在 airpState**，该场景所有楼层共用；换角色=新场景=新 sceneId |
| 联系人（线上消息） | `makeTangquanContactSceneId(speakerId)` | **由说话人 ID 确定性派生**——同员工永远同 sceneId，跨轮次稳定 |

**③ 过滤时只比对 sceneId**（`Du` = `buildTangquanSceneHistoryPrompts` @1000874）：

```js
.filter(e => e.sceneId
    ? e.sceneId === identity.sceneId                    // 新式：精确匹配场景 ID
    : Boolean(e.legacySceneKey && e.legacySceneKey === identity.legacySceneKey))  // 旧式：sceneKey 含说话人
```

**为什么"场景即角色"成立**：
- 现场对话每个场景**只有当前一个说话人**（如服务员在 3 号桌接待客人 → scene.speaker=客人名），参与者列表固定；
- 联系人每个员工一条独立"会话"（`customerState.联系人[员工.姓名]`），sceneId 由员工派生；
- 所以**不需要按角色字段过滤**——同 sceneId 的楼层天然就是"当前角色对话的一部分"；不同角色（另一个员工/另一个场景）的楼层 sceneId 不同，直接被滤掉。

**④ 例外：联系人历史不走楼层**（`makeCustomerContactHistoryPrompts` @364000）：

```js
const conversation = customerState.value.联系人[employee.姓名];   // 前端内存里的会话记录
const messages = (conversation?.消息 ?? []).map(...);            // 不是 getChatMessages！
return buildTangquanSceneHistoryPrompts({ identity, messages });
```

→ 联系人的"历史"来自**前端状态里的联系人会话数组**（每个员工一条），楼层写入只是给酒馆存档，上下文重建用内存副本——这保证了**只看当前员工的对话**，天然按角色隔离。

## 27. 每日安排 / 经营日报：上下文几乎全清空

`makeDailyGenerationOverrides`（@decoded 5406-5420，minified `wi` @17816）：

```js
{
  world_info_before: '',   persona_description: '',
  char_description: '',    char_personality: '',
  scenario: '',            world_info_after: '',
  dialogue_examples: '',
  chat_history: { with_depth_entries: false, prompts: [] }
}
```

配 `user_input: ''` + `max_chat_history: 0`。

> ⚠️ **唯一保留的是 jailbreak（预设系统提示词）**。模型只看到注入的 `<daily_input>`（员工/指名/项目 XML）或 `<boss_daily_report>`（项目/员工/区域 XML）+ 输出格式要求。

## 28. 角色卡内正则：不存在

对 `V1.0.6.chara.json` 检索 `regex_scripts / find_regex / substitute_regex / trimStrings / markdownOnly / promptOnly / runOnEdit / scriptName / findRegex / substituteRegex` 以及 `"regex" / "placement" / "interrupt" / "chat_input" / "on_edit"`——**全部 0 匹配**。

- ❌ 卡内没有酒馆正则脚本（无"替换成空"、无"隐藏 UpdateVariable"、无作者信息清除等隐藏正则）；
- ✅ 唯一的 `"use_regex":true` 是**世界书条目的 keys 匹配标志**（每条都有，keys 均为空数组），与正则脚本无关；
- 卡内唯一脚本：`extensions.tavern_helper.scripts[0]`，内容仅一行 `import '.../dist/汤泉/脚本/零层美化/index.js'`。

**隐藏逻辑全部由 index.js 脚本实现，不走正则。**

## 29. 隐藏上下文：4 个注入点（模型可见、玩家不可见）

| # | 注入点 | 机制 | 玩家可见性 |
|---|---|---|---|
| 1 | `generate({injects})` | 现场/每日/日报/人才市场各注入 `{position:'in_chat', depth:1/0, role:'system', content:'[输出格式要求]...'}` + `<daily_input>` / `<projects>/<employees>/<areas>` XML | 聊天界面完全看不到，模型必见 |
| 2 | 动态临时世界书（`replaceTemporaryEntries` → `worldbookRuntime.enableEntries/disableEntries`） | 按模式/场景启用条目，**用脚本生成的内容重写条目 content**（`entryContentMap`）：`common.*`（always）、`boss.rules.* / customer.rules.* / waiter.rules.*`（mode）、`area.current / project.current / character.current-employee / current-guest / current-candidate`（manual 动态）、`character.profile.*`（角色档案）、`facility.*`；关闭时 content 被清空 | 玩家只能在世界书编辑器里看到改写后的内容 |
| 3 | 预设注入（`presetOutputFormat`） | 在酒馆当前预设里启停 🎯 输出格式 / 💭 思维链 prompt 段（`updatePresetWith('in_use')`），随每次请求发模型 | 聊天界面不可见 |
| 4 | zeroLock 视觉零层 | `<三明月>` 占位楼层（`is_hidden:true` + `extra.tangquanZeroPlaceholder:true`）挂 `data-tq-visual-zero`，`hideNonZero` 时 CSS `#chat.tangquan-zero-lock[data-tq-hide="true"] > .mes:not([data-tq-visual-zero="true"]){display:none}` 隐藏全部真实楼层 | **玩家看不到真实楼层，但同场景非隐藏楼层仍会进 chat_history 上下文**——"玩家看不到但模型看得到"的最大一块 |

## 30. 历史消息的 extra/sceneId 标记

键名常量：`sC='tangquanSceneGeneration'`、`iC='tangquanCustomerGeneration'`、`lC='tangquanWaiterGeneration'`。

### 30.1. makeSceneGenerationExtra（@decoded 4216-4242）

每条 AI 现场楼层写入：

```js
{tangquanSceneGeneration: {
  version: 2, traceId, mode, kind, outputMode,
  sceneKey: mode|kind|title|speaker|participants 拼接,   // makeAirpSceneKey @4107
  sceneId, startedAfterMessageId,
  speakerId, participantIds, locationId, serviceId,
  projectId, assignmentId, role
}}
```

### 30.2. 其它生成类型

- 联系人消息：`{tangquanCustomerGeneration: {version:1, traceId, kind, speaker, contactName, role}}`（@4529-4546）
- 服务员接待：`{tangquanWaiterGeneration: {version:1, traceId, assignmentId, role}}`（minified `Js`）

### 30.3. 读取与用途

`getSceneGenerationExtra`（@4244-4267）从四处取：`message.extra` / 嵌套 `extra.extra` / `swipes_info[swipe_id].extra`（swipe 兼容）。

用途：
1. **sceneId 过滤**（第 2 节：历史只留同场景）；
2. **`findLatestSceneGenerationPair`**（@4315-4350）：按 `mode+sceneId(或sceneKey)+traceId` 聚合 user/assistant 对，用于页面重挂/重掷时定位"最后一对生成楼层"（`startedAfterMessageId` 即最新场景开始楼层）。

## 31. 场景切换记忆机制（A → B → 回 A 会发生什么）

### 31.1. 核心事实：每次"进入场景"都是全新的一次

`openAirpScene` 调用 `prepareAirpSceneIdentity(scene, true)`（freshScene=true），关键两个字段每次都重新生成：

```js
// sceneId：每次随机生成（@1057344，minified）
u = e.sceneId?.trim() || function(e='scene') {
  const t = Math.random().toString(36).slice(2,10);       // 随机 8 位
  return `${Eu(e)}-${Date.now().toString(36)}-${t}`;       // + 时间戳
}(`${e.mode}-scene`)

// startedAfterMessageId：新场景从"当前最后一条消息"开始记
startedAfterMessageId = freshScene
  ? Math.max(0, getLastMessageId())                                  // 新场景
  : inferLegacySceneStartedAfterMessageId(scene);                    // 恢复场景：往前找旧场景起点
```

### 31.2. 逐步推演

```
时间线（message_id 递增）：
  ─── 场景A（第一次）─── 楼层1~10，sceneId=A1（随机），startedAfter=0
  ─── 切换去 B ──── openAirpScene(B)：sceneId=B（新随机），startedAfter=当前最后(10)
  ─── 场景B ────── 楼层11~20
  ─── 切回 A ──── openAirpScene(A)：sceneId=A2（【新的随机ID】），startedAfter=当前最后(20)
  ─── 场景A（第二次）─ 楼层21~...
```

### 31.3. 回到 A 后，AI 请求的历史里有什么

用过滤规则 `Du`（`messageId > startedAfterMessageId && sceneId === identity.sceneId`）套：

| 楼层 | messageId | sceneId | 进历史？ | 原因 |
|---|---|---|---|---|
| 1~10（第一次 A） | 1-10 | A1 | ❌ | `messageId(1-10) > 20` 不成立（在 startedAfter 之前） |
| 11~20（B） | 11-20 | B | ❌ | sceneId ≠ A2 |
| 21~...（第二次 A） | 21+ | A2 | ✅ | 同场景且 > startedAfter |

**结论：回到 A 后，AI 只记得第二次 A 里新聊的内容——第一次 A 和 B 的对话全部不在上下文里。**

### 31.4. 为什么（设计意图）

1. **每次进入场景 = 一次"重开"**：sceneId 全新、`startedAfterMessageId` 从当前末尾开始——**故意失忆**，让 AI 专注眼前这场戏；
2. 切换场景时旧对话**不是被"精简"，是被"清零"**（对 AI 而言）；
3. **但存档里没有丢**：`extractSavedCustomerUiState` / `extractSavedBossUiState` 等把「游客界面状态 / 老板界面状态」连同 scene 存进前端数据（`tangquan-save-v1`），下次读档能**恢复**那个场景（`prepareAirpSceneIdentity(scene, false)` 复用旧 sceneId、`inferLegacySceneStartedAfterMessageId` 往前找旧起点）。

### 31.5. 微妙点：UI 恢复 ≠ 模型记忆恢复

- **UI 层面**：切回 A 时若走"存档恢复"（页面重挂 / 读档），前端会把旧场景恢复出来（旧 sceneId 保留）；
- **模型上下文**：无论 UI 是否恢复旧场景，只要**新开了一次对话**（freshScene=true），历史就从新起点算，旧的同场景楼层（messageId 在 startedAfter 之前）也不进上下文；
- 只有**走恢复路径（非 freshScene）**时，identity 才用旧 A1 sceneId + `inferLegacySceneStartedAfterMessageId`（往前找 A 起点），此时第一次 A 的楼层**能**回到上下文——但正常游玩中"切回 A"都是新开，第一次 A 的记忆对 AI 是消失的。

## 32. 接收到的上下文如何落地与保留（回复不丢失）

> 回答三个问题：AI 回复存到哪？是否全量保留？聊天文件里是否有？

### 32.1. 回复落地：createChatMessages 双楼层写入

每次现场/联系人回复，前端把 **user + assistant 两个楼层一次写入**（`createChatMessages` @289963，现场；@383058 联系人）：

```js
await createChatMessages(
  [
    { role: 'user',
      message: userText,                      // 玩家输入（原样）
      data: oldMvuData,                        // 发送前变量快照
      extra: { ...makeSceneGenerationExtra(scene, traceId, 'user'), ... } },
    { role: 'assistant',
      message: parsedMessage.displayText,      // 剥标签后的正文
      data: newMvuData,                        // 变量更新后的新快照
      extra: { ...makeSceneGenerationExtra(scene, traceId, 'assistant'), ... } },
  ],
  { insert_before: 'end', refresh: 'none' },   // 追加到聊天末尾
);
// 随后 setChatMessages 把 newMvuData 同步到楼层的 variables[0]（@291221 等）
```

- **写入目标 = 酒馆内存 `chat` 数组**（`createChatMessages` 内部 `chat.splice()`，见 ST 源码 `JS-Slash-Runner/chat_message.ts:314`）；
- 楼层附带 `extra.tangquanSceneGeneration`（§30 的 sceneId/traceId 等）+ `data`（Mvu 变量快照，存进楼层 `variables[0]`）。

### 32.2. 持久化：酒馆自动存聊天文件

```
createChatMessages → chat.splice() + addOneMessage()
  → 触发 ST 保存（saveChatConditional @script.js:9352 → saveChat → POST /api/chats/save）
  → 写入 data/default-user/chats/{角色}/{聊天名}.jsonl
```

- 回复**正常保存在酒馆聊天文件**（jsonl，每行一条楼层，含 mes/data/variables/extra/swipes_info）；
- 聊天文件 = **唯一的持久化副本**，刷新页面后从它恢复。

### 32.3. 第二份副本：存档内嵌 chatSnapshot（关键设计）

**存档（`tangquan-save-v1`）里内嵌一份完整聊天快照** `data.chatSnapshot`，保存时抓取、载入时校验恢复：

**保存时**（@827410，`captureChatSnapshot`）：

```js
getChatMessages(`0-${lastMessageId}`, { role:'all', hide_state:'all', include_swipes:true })
  .map(fr)   // 楼层 → 快照条目
→ { version:1, capturedAt, chatId, messageCount, lastMessageId, checksum, messages }
→ 存进槽位存档 data.chatSnapshot（@827934）
```

- **`0-` 起始 + `role:'all'` + `hide_state:'all'` + `include_swipes:true` = 全量快照**（含隐藏楼层 `<三明月>`、含 swipe 备选）；
- `checksum`（`Cr`）做完整性校验。

**载入时**（@823685 `Br`，恢复聊天快照）：

```js
// ① 校验：Cr(e.messages) === e.checksum，不一致则中止恢复
// ② 清空当前聊天：deleteChatMessages(0..lastMessageId)（分批 @824100）
// ③ 重建楼层：createChatMessages(snapshot.messages.map(hr))（分批，@824400）
// ④ 恢复楼层附加数据（swipes 等）→ loadCurrentChat() 刷新显示（@825292）
```

> **读档完整链路见 [04-存档与世界书.md §9.4.1](04-存档与世界书.md)**：`loadSlot` → `readSlotData`（分块读取+checksum 校验+zod 解析）→ 取 `chatSnapshot` → `Br` 清空当前聊天并分批重建 → 恢复用户信息 → 更新运行时变量。快照条目 `hr` 原样保留 `role/name/is_hidden/message/data/extra`——上下文在存档里不丢，读档时完整搬回。

### 32.4. 结论：三层保留

| 层 | 位置 | 内容 | 何时 |
|---|---|---|---|
| ① 实时内存 | 酒馆 `chat` 数组 | 全部楼层 | 每次写入后 |
| ② 聊天文件 | `data/default-user/chats/{角色}/{聊天}.jsonl` | 全部楼层（含 extra/data/swipes） | ST 自动保存 |
| ③ 存档快照 | `tangquan-save-v1` 槽位 `data.chatSnapshot` | **全量楼层快照 + checksum** | 手动/自动存档时 |

> **存档的物理位置**：存档（含 `chatSnapshot`）**不是**独立文件，而是写在**当前聊天绑定的世界书文件**里（`data/default-user/worlds/{世界书名}.json` 的 `meta`/`chunk` 条目，`extra.source:'tangquan-save-v1'` 打标）——详见 [04-存档与世界书.md §9.1.2](04-存档与世界书.md)。所以：
> - 楼层本体 → 聊天文件 `chats/{角色}/{聊天}.jsonl`（每行一条）；
> - 游戏状态 + 存档（含楼层快照副本）→ 世界书文件 `worlds/{世界书}.json`。

**回答用户问题**：
- **收到的上下文全量保留**（正文、变量快照、extra 都在）；
- **保留在聊天文件**（正常 jsonl）+ **存档快照**（第二副本，读档时校验恢复）；
- 前端**没有**把回复正文存进 localStorage/sessionStorage/IndexedDB（0 命中，见 09 文档 §34.9）；
- 所以"切场景 AI 失忆"（§31）**不影响数据完整性**——楼层还在聊天文件里，只是 `startedAfterMessageId`/`sceneId` 过滤让它们不进上下文；存档快照则保证读档能完整还原聊天。
