# 完整循环轮：从输入到回复落地的全链路

> 本文档回答：进入 Galgame 界面 → 输入文字 → 点击发送 → 回复落地 的完整循环。
> 覆盖：请求组装（发送了什么、注入了什么、预设在哪）、回调监控（怎么知道回复完成）、回复解析（正文/立绘/变量）、结束对话、剧情缓存。
> 证据均带 `index.js` 字节偏移。本文档基于 4 个子代理深挖 + 手工复核。

## 36.1. 进入 Gal 界面

- 入口：标题画面 → 选择游玩身份（老板/游客/服务员）→ 存档 → 进入主界面；
- 主界面是 iframe（`srcdoc` @1224265），前端是 Vue3 + pinia（`createApp(...).use(pinia).mount(iframe.body)` @6 文档）；
- 进入场景（`openAirpScene` @215187）：选地点/员工/项目 → 生成场景对象（含 `speaker`、`participants`、`characterId`、`sceneId`）→ 显示 Gal 界面（输入框 + 台词气泡 + 立绘 + 背景）；
- 输入框 `v-model="airpInput"`，按钮 `@click="submitAirpInput"`，快捷键 **Ctrl+Enter / Cmd+Enter**（@121588-121880）。

## 36.2. 点击发送：submitAirpInput（@286853）

```js
async function submitAirpInput() {
  const scene = airpState.value;
  const userText = airpInput.value.trim();      // ① 只 trim，不改写、不加前后缀
  // ② 校验：无场景→"还没有进入现场"；空输入→"先输入要做的事"；提交中→return
  airpSubmitting.value = true;                   // ③ 上锁（防重复提交）
  writeUiMemorySnapshot('现场互动发送前');        // ④ UI 状态快照（刷新可恢复）
  await runAction('现场互动', async () => {
    const oldMvuData = ...;                      // ⑤ 读当前 MVU 变量
    const result = await requestSceneGeneration(scene, userText, oldMvuData,
        '现场互动', { inputBoxValue, inputSource: 'scene-input' });  // ⑥ 核心
    // ⑦ 把 MVU 结果写回页面状态
    // ⑧ createChatMessages([user, assistant]) + setChatMessages ——写楼层
    airpInput.value = '';                        // ⑨ 清空输入框
    showToast('已生成');
  });
}
```

> 输入文本**从头到尾只做 trim**，不包裹任何 XML/前缀。所谓"玩家输入变成 {cot}{格式}{输入}"——cot 和格式要求是**独立参数**（预设 + injects），不是拼在玩家输入前后。见 [36.4](#364-实际发送顺序generate-参数)。

## 36.3. 请求组装：requestSceneGeneration（@271990）

玩家点发送后，真正组装请求的函数按**严格顺序**执行 4 步：

| 步骤 | 函数 | 偏移 | 干什么 |
|---|---|---|---|
| ① | `enqueueAiGeneration(reason, ...)` | @272029 | 进 **AI 生成串行队列**（见 09 文档 34.1） |
| ② | `syncPresetOutputFormat(scene, ...)` | @272242 | **切换预设**：story→`🎯 未开之花·AIRP正文输出`，否则→`🎯 未开之花·Galgame输出`；启用对应输出条目 + 启用 `💭 思维链`（CoT），禁用其它输出条目 |
| ③ | `replaceTemporaryEntries(scene.entryIds, ...)` | @272304 | **写临时世界书**：把 `area.current`、`project.current`、`character.current-employee`、`character.current-guest` 等条目 `enabled:true` 并把动态内容写进条目 content（`worldbookRuntime.enableEntries` @1236336）——不是 overrides.world_info，是**直接改世界书文件** |
| ④ | `makeSceneChatHistoryPrompts`（Du @1000598） | @272515 | **历史过滤**：`getChatMessages('1-${last}', {include_swipes:true})` → 只留 `messageId > startedAfterMessageId && messageId < beforeMessageId && !hidden && 同sceneId/legacySceneKey` 的楼层 → 输出 `[{role, content}]` |
| ⑤ | `makeCustomer/ WaiterGenerationInjects`（lc @951545） | @272640 | **格式要求 injects**：`{position:'in_chat', depth:1, role:'system', content:'[输出格式要求]...', should_scan:false}`，按 outputMode 三选一（Galgame/AIRP/联系人），见 03 文档 7.2.1 |

> **临时世界书的完整机制见 [11-临时世界书.md](11-临时世界书.md)**（专篇：世界书文件解析、5 个动态条目、启停/覆写实现、4 类生命周期调用点全清单、用户问答）。这里只留定位：
>
> - **本质**：改的是当前聊天绑定的那份世界书文件（`getChatWorldbookName('current')`），不是新建独立世界书；唯一新建场景是聊天从未绑定世界书时 `createWorldbook` 建空文件再绑定；
> - **动态条目**：5 个 `current` 条目（区域/项目/员工/客人/候选人）只放"当前"即时状态快照，长篇静态设定在常驻条目（`common.*`、`character.profile.*`）；
> - **核心心智**：不是"创建/删除"条目，而是"**启停 + 覆写**"预置条目（空占位 → enabled:true + 覆写 content → 离开时恢复空占位）；
> - **4 类调用点**：① 进入场景激活 → ② 每次发送前幂等确认（diff 无变化不写）→ ③ 场景内状态变更先清后重建 → ④ 离开现场/返回标题清场恢复占位；
> - **为什么聪明**：不增删条目（无垃圾）、幂等写入（不频繁落盘）、打标可追踪（`extra.tangquanEntryId`，绝不误改常驻条目）、**内容即状态**——把"运行态状态"伪装成"世界书知识"喂给模型，是这张卡最核心的注入技巧之一。

## 36.4. 实际发送顺序（generate 参数）

```js
// @274654 现场互动
await generate({
  user_input: userText,                 // 玩家输入（仅 trim 原样）
  should_stream: true,
  overrides: {
    chat_history: {                     // 唯一 override：聊天历史
      with_depth_entries: true,
      prompts: chatHistoryPrompts,      // [{role, content}] 场景过滤后的楼层
    },
  },
  ...(customerInjects?.length ? { injects: customerInjects }
      : waiterInjects?.length ? { injects: waiterInjects } : {}),
  // 老板模式：无 injects 字段
});
```

**SillyTavern 最终组装顺序**（按 ST 全局状态 + 参数推导）：

```
{预设} → {世界书 before/内嵌} → {chat_history(上下文)} → {CoT思维链} → {玩家输入=user_input} → {worldInfoAfter}
```

| 段 | 来自哪 | 说明 |
|---|---|---|
| **预设** | 当前 ST 预设（被 `syncPresetOutputFormat` 改过 in_use） | 含角色卡 prompt + 🎯 输出格式 + 💭 思维链，见 03/02 文档 |
| **世界书** | 当前角色世界书（临时条目已被 enableEntries 写回） | ST 自动按 activation 注入 |
| **上下文** | `overrides.chat_history.prompts` | 场景过滤后的历史楼层 |
| **CoT 思维链** | 预设中 `💭 思维链` 条目（现场互动时启用） | 让模型先想后答 |
| **玩家输入** | `user_input` | 追加为最后一条 user 消息（depth 0） |
| **worldInfoAfter** | 世界书（无 override） | 现场互动不覆盖它 |

> **重要**：`overrides` **只有 `chat_history` 一个键**——没有 world_info/persona/char/scenario 覆盖。只有每日安排/经营日报/AI 人才市场才用 `makeDailyGenerationOverrides()`（@276873）清空全部上下文（world_info/persona/char/scenario/dialogue_examples/chat_history 全空，仅留 jailbreak），见 02 文档 6.3。

### 36.4.1. 请求格式逐参数详解（+ 历史"砍掉重写"）

前端只用了 4 个参数（`signal`/`swipes`/`streaming` 回调/`abort` 全部 0 命中——刻意保持最小请求）：

| 参数 | 值 | 语义 |
|---|---|---|
| `user_input` | 玩家输入（仅 trim） | ST 追加为**最后一条 user 消息**（depth 0）；`currentInputAppendCount: 1` 诊断确认不重复 |
| `should_stream` | `true` | ST 开流式：每 token 触发 `STREAM_TOKEN_RECEIVED`（零层实时预览）；**结束才 resolve**，返回完整文本 |
| `overrides.chat_history` | `{with_depth_entries:true, prompts:[...]}` | **砍掉 ST 默认历史组装，用前端自己的 prompts 当 chat 段** |
| `injects` | `[{position:'in_chat',depth:1,role:'system',content:'[输出格式要求]…'}]` | 格式要求，贴历史末尾；**老板模式没有**（靠预设 🎯 段） |

**`getGenerationText` @222283 的隐藏约束**：

```js
function getGenerationText(result) {
  if (typeof result === 'string') return result;   // 纯文本
  throw new Error('本次生成返回了工具调用结果，暂时不能写入楼层');  // 工具调用直接抛错
}
```

> 这张卡**要求模型纯文本回复，不支持工具调用**——一切"工具"都是 `<content>`/`<UpdateVariable>` 文本协议。

#### 历史"砍掉重写"：为什么是信息控制力最强的单点

`overrides.chat_history` 的语义：**ST 不再扫描当前聊天记录构建 chat 段，而是直接用前端给的 `prompts` 数组**。前端"自己创作"这段上下文的管道（`Du` @1000598，minified 名）——**内容不改写，但集合完全由前端决定**：

```js
function Du({identity, messages, beforeMessageId = Infinity}) {
  return messages
    .filter(m => Number.isInteger(m.messageId))                        // ① 有 id
    .filter(m => m.messageId > identity.startedAfterMessageId          // ② 时间窗：场景开始之后
              && m.messageId < beforeMessageId)                        //    重Roll时截断到上一轮 user
    .filter(m => !m.hidden &&                                          // ③ 非隐藏
      (m.sceneId ? m.sceneId === identity.sceneId                      //    场景隔离：sceneId 归属
                  : (m.legacySceneKey && identity.legacySceneKey       //    或旧版 sceneKey
                     && m.legacySceneKey === identity.legacySceneKey)))
    .filter(m => ['system','user','assistant'].includes(m.role))       // ④ 只留三类角色
    .map(m => ({ ...m, content: m.content.trim() }))
    .filter(m => m.content.length > 0)                                 // ⑤ 去空
    .sort((a,b) => a.messageId - b.messageId)                          // ⑥ 按时间正序
    .map(m => ({ role: m.role, content: m.content }));                 // ⑦ 只输出 role+content
}
```

**这个设计为什么有重大意义**（做卡人必读）：

1. **历史与聊天记录解耦**——前端完全掌控模型能看到哪些楼层：跨场景隔离（B 场景的历史不会漏进 A）、隐藏楼层剔除、时间窗截断（重 Roll 从上一轮 user 重放）、角色白名单。ST 原生历史机制做不到这种粒度；
2. **场景切换 = 上下文切换**——换场景时 `startedAfterMessageId` 变化，旧场景楼层自动消失，模型上下文"归零重开"，但聊天记录本身保留（可回溯）；
3. **不改写内容、只改集合**——楼层的 `content` 原样透传，不压缩不加工（08 文档结论），保证模型看到的和玩家看到的一致；
4. **`with_depth_entries: true`**——prompts 元素已带 messageId/顺序语义，ST 不再自行推算 depth，避免注入位置错乱；
5. **双保险的位置控制**——历史末尾紧跟 injects 格式要求（`in_chat depth:1`），玩家输入最后（depth 0），模型"先读规则→再读输入→再作答"的顺序被前端锁死。

## 36.5. 发送后：如何监控回调（监听层）

**核心结论：前端判断"回复完成"的唯一权威信号是 `await generate()` 的 Promise resolve**（@273579 / 新版 @1076050）。酒馆事件只是视觉层的旁路。

```
generate() 发出
  ├─ 酒馆触发 MESSAGE_SENT ──► beautifier(@726773) 美化用户层 / zeroLock(@733514) isGenerating=true + 预览用户输入
  ├─ 流式 token ──► STREAM_TOKEN_RECEIVED ──► zeroLock(@734628) 克隆楼层实时预览（streamPreview）
  ├─ 生成完成 ──► 酒馆写楼层 + 触发 MESSAGE_RECEIVED ──► beautifier(@726720) / zeroLock(@734192) isGenerating=false + 450ms 延迟镜像
  └─ generate() Promise resolve（完整文本）◄──【前端真正等的是这个】
```

**完整事件监听清单**（`eventOn`/`eventMakeLast` 包装，回调均 `errorCatched` 包裹）：

| 事件 | 用途 |
|---|---|
| `MESSAGE_SENT` | 用户发出：isGenerating=true、预览用户输入 |
| `MESSAGE_RECEIVED` | AI 落地：isGenerating=false、触发美化/镜像 |
| `GENERATION_STARTED/STOPPED/ENDED` | 生成状态同步 |
| `STREAM_TOKEN_RECEIVED` | 流式 token 实时预览（零层克隆层） |
| `MESSAGE_SWIPED/EDITED/UPDATED/DELETED` | 楼层变更：重镜像 / MVU 重对齐 |
| `USER/CHARACTER_MESSAGE_RENDERED` | 楼层渲染后刷新零层锁 |
| `CHAT_CHANGED` | 切换聊天：重置镜像状态 |

**MutationObserver 兜底**（@727222、@735300）：观察 `#chat` 楼层 DOM，80ms~2800ms 后重刷美化/零层/MVU 对齐——不是完成信号，是容错。

## 36.6. 回复解析：正文/变量/立绘

`generate()` resolve 后（时序见 07 文档 §19 用户发送后回调完整流程）：

```js
// ① 取文本（@275086）
const rawMessage = getGenerationText(result);      // 字符串直接返回，工具调用抛错
const message = rawMessage.trim() || '<content>对方暂时没有继续回应。</content>';

// ② 解析正文（Ko @870310，见 03 文档 7.5）
const parsed = parseTangquanAiMessage(message);
// → { rawText, displayText, contentText, timeText, dialoguePages, ... }

// ③ MVU 变量更新（@276210）
const newMvuData = (await Mvu.parseMessage(message, _.cloneDeep(oldMvuData))) ?? oldMvuData;
// 提取 <UpdateVariable><Analysis>..</Analysis><JSONPatch>[..]</JSONPatch></UpdateVariable>
// 执行 JSON Patch（replace/delta/insert/remove/move），改 stat_data

// ④ 写楼层（@289963）
createChatMessages([user楼层, assistant楼层], {insert_before:'end', refresh:'none'});
//   assistant.message = parsed.displayText        ← 正文（已剥标签）
//   assistant.data    = newMvuData                 ← 变量写进楼层 data
//   assistant.extra   = { tangquanSceneGeneration: 场景标记, traceId, ... }
setChatMessages([{message_id: lastId, data: newMvuData}], {refresh:'none'});   // 变量写回楼层
setChatMessages([{message_id: lastId-1}, {message_id: lastId}], {refresh:'affected'}); // 触发重渲染

// ⑤ 前端状态刷新
chatHistoryVersion.value += 1;                     // 版本号驱动 Vue 重算
applyBoss/Customer/WaiterStatDataToState(...);     // reactive 状态直接赋值
applyScenePresentation(scene, parsed, '现场互动完成');  // dialoguePages→台词气泡、timeText→游戏时间

// ⑥ 视觉零层同步
await zeroLock.mirrorNow('现场互动完成');          // @294551 克隆楼层镜像
beautifier.applyNow('现场互动完成');               // @294607 美化最新楼层
```

## 36.7. 立绘控制（LLM 完全不能控制）

**结论：AI 回复中不输出任何控制立绘的内容。立绘 = 前端 100% 状态机控制。**

- 全文件搜不到 `<sprite>`/`<立绘>`/`<emotion>`/`<pose>`/`<表情>` 等标签（0 命中）；
- 立绘 URL 由 `Ws`（@899715）拼 zeabur CDN，查 `Gs`(portraits)/`Us`(avatars) 哈希表合并成目录 `Js`（@918229）；
- 三个视角：
  - **老板**：`bossSceneSpriteUrl` = 场景 `characterId || findTangquanCharacter(speaker)?.id` → 查表，找不到返回 `''`（不显示）；`suppressCharacterStanding`（AI 人才市场虚拟 NPC）时强制隐藏；
  - **游客**：`customerSceneSpriteUrl` = 当前服务/指名员工，宽松回退 `'114'` 默认立绘；支持多人并排（has-2/3/4）；
  - **服务员**：恒定 `ri('114')`，与对话无关；
- **看板娘**：只是老板选的员工身份（`bossState.看板娘`），她上班/被指名时该员工立绘出现；
- **无表情/服装/姿态维度**：URL 只有 `名字.哈希.png`，前端只取数组索引 0，无切换代码。

> 唯一间接关联：AI 人才市场 NPC 由 LLM 生成 JSON（`ai-market-xxx` id），前端用该 id 正则触发 `suppressCharacterStanding`——LLM 影响"有没有这个人"，不影响"立绘怎么显示"。

## 36.8. 点击结束对话后

**没有名为"结束对话"的按钮**，实际有三类"结束/返回"：

### ① 现场右上角"离开"（closeAirpScene @220738）——最接近"结束对话"

```js
async function closeAirpScene() {
  await runAction('离开现场', async () => {
    deactivateBoss/Customer/WaiterMvuBlocks('离开现场');  // 卸下活动变量块
    mvuRuntime.clearInteractionScene(mode);               // stat_data.互动现场 = {}
    replaceTemporaryEntries([], '离开现场');              // 关闭所有临时世界书条目
    syncPresetOutputFormat(null, '离开现场');             // 切回 none 格式
    airpState.value = null; airpInput.value = '';         // 清现场状态
    resetScenePresentation(null);                          // 恢复主界面
    showToast('已离开现场');
  });
  if (sceneHasUnsavedAiInteraction) await requestAutoSave('有效AI互动后离开现场');  // 有未保存互动才存
}
```

- **聊天历史永不删除**——消息留在聊天里，靠 `extra.tangquanSceneGeneration` 的 sceneId 归属；
- 离开后场景对象还在 stat_data（`互动现场`），下次进入是**新场景**（新 sceneId），旧消息不再匹配。

### ② 主界面"返回标题"（returnToTitle @404417）

```
saveActiveWaiterMvuBlocks（服务员）→ forceAutoSaveBeforeTransition（强制保存，失败则取消返回）
→ clearUiMemorySnapshot → deactivateXxxMvuBlocks → replaceTemporaryEntries([])
→ disableModeWorldbookEntries → airpState=null → activePage='home' 切回标题
```

### ③ 游客"结束服务"/服务员"下班"

- 游客 `finishSelectedCustomerService` @365930：结算服务结果（好感/满意度/行程）→ 卸块 → 清场景 → 切回关系页；
- 服务员下班 @397000 区间：先 `saveActiveWaiterMvuBlocks` 保存接待结果再卸块。

## 36.9. 剧情简介/摘要缓存：**没有**

**结论：LLM 不返回剧情简介，前端也不缓存剧情摘要。** 关键词全量搜索（index.js + magvarupdate.js + chara.json 三处）：

- `<summary>`/`<摘要>`/`<recap>`/`<brief>`/`摘要`/`剧情简介`/`剧情摘要`/`recap`/`brief`/`memory`/`story_summary` 全部 **0 命中**（`summary` 25 处全是 CSS 类名和经营日报字段名 `guest_summary` 等）；
- `<UpdateVariable>` 的 JSONPatch path 全是具体业务字段（`/用户/资金`、`/今日结算/...`），**没有** `/记忆`、`/剧情`、`/summary`、`/recap` 类路径；
- 唯一由 LLM 生成的"纪要"：老板经营日报 `<boss_daily_report>`（`guest_summary/revenue_summary/rating_summary`），只存前端 `bossState.结算.经营纪要` 随存档保存，**不写世界书、不进 stat_data 供后续对话调用**（且 `boss.settlement` 块从未被激活）；
- 跨会话连续性完全依赖三样：**存档**（世界书条目 `tangquan-save-v1`）+ **聊天历史**（sceneId 过滤）+ **stat_data**（SillyTavern 消息变量，MVU 载体）。

> 也就是说：这张卡**不靠剧情摘要**维持长期记忆，而是靠"完整聊天历史按场景过滤 + 存档恢复"。模型每次看到的是当前场景的完整历史楼层（受 `startedAfterMessageId` 截断），不是压缩摘要。

## 36.10. 一句话总结

玩家点发送 → `submitAirpInput` 只 trim 输入 → `requestSceneGeneration` 依次做 **切预设（🎯+💭）→ 写临时世界书 → 过滤场景历史 → 组格式要求 injects** → 发出 `generate({user_input, should_stream:true, overrides:{chat_history}, injects?})` → 酒馆按 **{预设}{世界书}{上下文}{CoT}{玩家输入}** 组装 → `await generate()` resolve 拿到完整文本 → `parseTangquanAiMessage` 剥标签取正文 → `Mvu.parseMessage` 执行变量更新 → `createChatMessages` 写楼层（正文+变量+场景标记）→ Vue 状态刷新（立绘/台词/时间）→ 零层镜像；回复中**没有**任何立绘控制标签，立绘 100% 前端状态机决定；"离开"只卸块清场景不删历史；**没有剧情摘要缓存**，记忆靠存档+场景过滤历史+stat_data。
