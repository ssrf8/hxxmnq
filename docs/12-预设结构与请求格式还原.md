# 预设 JSON 结构与 ST 请求格式还原（强证据版）

> 本文档以 **TGbreak-V3 预设 JSON（134 条 prompts）+ 本地 SillyTavern 源码**为证据，还原"一次 AI 请求最终长什么样"。
> 源码位置：`D:\json脚本地下城\主体\SillyTavern\`
> 核心文件：`public/scripts/openai.js`、`public/scripts/PromptManager.js`
> 预设 JSON：用户提供的 TGbreak-V3（134 prompts + 125 项 prompt_order）

## 43. 结论先行：预设是"占位符 + 顺序表"，不是"包裹层"

**用户直觉**："整个预设包裹了所有内容，然后根据请求内容（世界书、玩家信息、上下文）填入预设内发送。"

**修正后的事实**：
1. 预设 JSON 里的 `prompts` 分两类：**用户自定义条目**（写作要求、文风、COT 等，内容真实存在）+ **系统 marker 条目**（`worldInfoBefore`/`charDescription`/`chatHistory` 等 9 个，内容是**空的占位符**，运行时由 ST 填充）；
2. `prompt_order`（125 项）定义**所有条目（含 marker）的相对顺序 + 开关**；
3. ST 发送前把真实内容（世界书、角色卡、persona、聊天历史）**替换进 marker 位置**，整个集合按 prompt_order 顺序拼成 messages 数组；
4. **内容块嵌在 prompt 流中间，不是包在最外面**：TGbreak-V3 里世界书/角色卡/persona 位于「故事设定」与「886###」之间，前后都是预设作者写的 prompt。

### 44.2. prompts：134 条，全部 `injection_position=0`（RELATIVE）

| 类别 | 示例 | injection_position | injection_depth/order | 说明 |
|---|---|---|---|---|
| 用户 system 条目（123） | `⚠️使用必看`、`法则`、`写作要求开始`、`COT-头`、`故事设定` | 0 (RELATIVE) | depth=4 order=100 | **depth/order 不生效**（仅 ABSOLUTE 模式用），顺序全靠 prompt_order |
| 用户 assistant 条目（5） | `**&&**`、`❄️ds专用--底部`、`❄️大总结之术`、`❄️拷打ai` | 0 (RELATIVE) | 同上 | 以 assistant 角色注入 system 区，引导模型输出形态 |
| 系统 marker（9） | `main`、`dialogueExamples`、`worldInfoBefore/After`、`personaDescription`、`charDescription`、`charPersonality`、`scenario`、`chatHistory` | 0 (RELATIVE) / marker=true | — | **内容为空占位**，运行时被真实数据替换 |
| 特殊标识符条目 | `jailbreak`、`nsfw`、`enhanceDefinitions` | 0 | — | ST 保留标识符，有特殊逻辑（如 jailbreak 可被角色卡 override） |

> **为什么全部 depth=4 order=100？** 这是预设导出的**默认遗留值**。ST 的 `INJECTION_POSITION = { RELATIVE: 0, ABSOLUTE: 1 }`，只有 `ABSOLUTE`（in_chat 注入）才读 depth/order。这份预设没有任何 ABSOLUTE 条目，所以 **COT 等条目全部排在 system 区（聊天历史之前）**，而不是插在对话中间。

## 45. ST 源码组装算法（证据链）

### 45.1. 阶段一：getPromptCollection（顺序 + 开关过滤）
`PromptManager.js:1516`

```js
getPromptCollection(generationType) {
    const promptOrder = this.getPromptOrderForCharacter(this.activeCharacter);
    promptOrder.forEach(entry => {
        const prompt = this.getPromptById(entry.identifier);
        const allowedTrigger = entry.enabled && this.shouldTrigger(prompt, generationType);
        if (allowedTrigger) promptCollection.add(this.preparePrompt(prompt));
        else if (entry.identifier === 'main') { /* main 必须有，空内容也占位 */ }
    });
}
```

→ 产出：**按 prompt_order 顺序**、只含 enabled 条目的 PromptCollection。

async function populationInjectionPrompts(prompts, messages) {
    // 只处理 injection_position === INJECTION_POSITION.ABSOLUTE 的条目
    for (let i = 0; i <= maxDepth; i++) {           // depth 0..max
        const depthPrompts = prompts.filter(p => p.injection_depth === i && p.content);
        // 按 injection_order 分组 → 再按 role(system/user/assistant) 排序
        // messages.splice(injectIdx, 0, ...roleMessages)  ← 插进对话中间
    }
    messages = messages.reverse();
}

## 46. 还原：一次请求的最终 messages 结构（TGbreak-V3）

```
messages = [
  // —— system 区（聊天历史之前，按 prompt_order 顺序）——
  { role:'system',    content:'⚠️⚠️使用必看⚠️⚠️ ...' },          // 使用必看
  { role:'system',    content:'😾😾别关 ...' },                   // 别关
  { role:'system',    content:'^ - ^ ...' },                    // main 系统提示符
  { role:'system',    content:'法则 ...' },
  { role:'assistant', content:'**&&** ...' },                   // 示例形态引导
  { role:'system',    content:'<角色卡 mes_example>' },         // dialogueExamples(marker→真实)
  { role:'system',    content:'写作要求开始 ...' },
  ... 文风指导（各 enabled 文风）...
  { role:'system',    content:'COT-头 ...' },
  { role:'system',    content:'cot-✔️原思维 ...' },
  { role:'system',    content:'cot-end ...' },
  { role:'system',    content:'故事设定 ...' },
  { role:'system',    content:'<世界书条目 before>' },          // worldInfoBefore(marker→真实)
  { role:'system',    content:'<persona 描述>' },              // personaDescription(marker→真实)
  { role:'system',    content:'<角色卡 description>' },        // charDescription(marker→真实)
  { role:'system',    content:'<角色卡 personality>' },        // charPersonality(marker→真实)
  { role:'system',    content:'<角色卡 scenario>' },           // scenario(marker→真实)
  { role:'system',    content:'<世界书条目 after>' },           // worldInfoAfter(marker→真实)
  { role:'system',    content:'故事设定结束 ...' },
  { role:'system',    content:'886### ...' },
  // —— 聊天历史区（token 预算从新到旧裁剪）——
  { role:'user',      content:'<真实聊天...>' },                // chatHistory(marker→真实, 可含 ABSOLUTE in_chat 注入)
  { role:'assistant', content:'<真实聊天...>' },
  ...
  // —— 最新 ——
  { role:'user',      content:'<当前玩家输入>' },
]
```

**要点**：
- 世界书/角色卡/persona 是**嵌在预设 prompt 流中间**（故事设定之后、886 之前），不是包裹在最外层；
- 聊天历史是最后一个大块，按 token 预算从最新往旧塞（`populateChatHistory`），**太老的历史被预算裁剪**；
- 玩家输入就是 messages 最后一条 user 消息；
- 若开了 `squash_system_messages`，多个 system 段会被合并成一条。

## 47. 与汤泉卡的关系（两条注入路径要分清）

| 路径 | 机制 | 载体 | 位置 | 例子 |
|---|---|---|---|---|
| **预设 prompt**（本文） | prompt_order + marker 替换 | 预设 JSON | system 区固定位置 | TGbreak-V3 的 COT/文风 |
| **in-chat 注入** | `generate({injects})` → ST `getInjects` → extension prompt `IN_CHAT` | 前端代码动态生成 | 聊天消息中间（depth 定位） | 汤泉卡 `lc/ic` 生成的「AIRP 正文输出」等 |

- 汤泉卡前端**不动预设 JSON**，它通过 `generate()` 的 `injects` 参数走**第二条路**（in_chat extension prompt），因此可以动态开关、按消息插入；
- 预设的「🎯/💭 段」由 `presetOutputFormat` 服务用 `updatePresetWith('in_use')` 启停（见 02 文档），那是**预设内的条目**，与前端 injects 无关；
- 汤泉卡历史上下文是**前端自建**的 `overrides.chat_history`（砍掉酒馆真实历史，见 08 文档），替换进 `chatHistory` marker 位置。

## 49. 汤泉卡自建 chat_history 注入链路（实战证据）

### 49.2. ST 端如何消费（JS-Slash-Runner `dataProcessor.ts:114`）

```ts

    oaiMessages = [...config.overrides.chat_history].reverse();   // ← 直接用自建 prompts（reverse 成旧→新）

```

→ 一旦给了 `overrides.chat_history`，**酒馆真实楼层完全被跳过**。

### 49.3. 填入 marker 位置（`openai.js:877 populateChatHistory`）

```js
if (!prompts.has('chatHistory')) return;
chatCompletion.add(new MessageCollection('chatHistory'), prompts.index('chatHistory'));
// 逐条把 oaiMessages（旧→新）插入 chatHistory marker 位置，按 token 预算裁剪
```

→ 正是 TGbreak-V3 预设 `prompt_order` 中 `chatHistory enabled: true` 的那个位置（12 文档 §46 的 `[user/assistant]<聊天历史...>`）。

### 49.4. with_depth_entries 语义（`dataProcessor.ts:320-342` + `utils.ts:131-132`）

- `with_depth_entries: true`（默认）→ 世界书按深度插入的条目（`processWorldInfoDepth`）**保留**，插入聊天历史中间；
- `with_depth_entries: false` → `worldInfoDepth = null`，深度条目被抑制（每日安排/日报模式用）；
- 判定：`isPromptFiltered('with_depth_entries')` 返回 `config.overrides.with_depth_entries === false`。

### 49.5. 完整链路（一次 Galgame 发送）

```
index.js submitAirpInput @274693
  → 前端构造 chatHistoryPrompts（08 文档 Du 历史过滤后的自建数组）
  → generate({ user_input, overrides: { chat_history: { with_depth_entries: true, prompts: chatHistoryPrompts } }, injects })
    → JS-Slash-Runner dataProcessor.ts:114  用 prompts 覆盖真实楼层（reverse 旧→新）
    → populateChatCompletion / populateChatHistory  填入 TGbreak-V3 的 chatHistory marker 位置
    → 最终 messages：
       [system] 使用必看 → main → 法则 → … → 故事设定 → 世界书/角色卡/persona
       → [user/assistant] ← 自建 chatHistoryPrompts（这里！）
       → [user] ← 当前玩家输入 userText
```

### 49.6. 双层裁剪（易误解点）

1. 汤泉卡前端**先自己过滤/精简**历史（08 文档 `Du` 过滤：sceneId/时间/隐藏）；
2. ST `populateChatHistory` **再按 token 预算从新到旧裁一次**（`openai_max_context - openai_max_tokens`）。

→ 自建数组里太旧的内容仍可能被 ST 预算砍掉（通常不会，前端已精简过）。
