# 确定性开场事务契约

开场界面先维护当前聊天的本地草稿：姓名、称谓/代词、外貌简述、庭园名称。预览和修改草稿不得写入 MVU，也不得把庭园标记为已经继承。

新聊天开始时：

1. 校验并冻结草稿与聊天 ID；
2. 确认当前聊天尚无 user 楼层，并把首个 assistant 楼层作为唯一写入目标；
3. 从 `initial-state.json` 补齐共享默认状态，只覆盖玩家姓名、称谓、外貌、庭园名、庭守钥状态及 `meta.initialized`、`meta.opening_committed`；
4. 使用 `Mvu.replaceMvuData` 写入该 assistant 楼层并立即复读；
5. 只有复读字段完全一致后才开放庭园，并允许数据库做可选归档；
6. 整条路径不得创建 user 或 assistant 消息，不得触发 `/trigger`，不得调用 LLM。

继承确认必须幂等。相同资料重复提交直接视为成功；若当前聊天已用另一组资料完成开场，则拒绝静默覆盖。写入失败时保留草稿和开场页，不推进时间、资源、关系或事件，并提供原地重试。

继承完成后的第一次真实行动从玩家刚穿过结界、抵达荒废庭园的当下承接。变量模型不得再次初始化玩家资料或重复发放庭守钥。

旧聊天若已经存在带 `gensokyo_opening` 标记的 user 消息，桥接层可继续解析其资料以兼容历史存档；默认开场界面不得再暴露生成式序章或修复入口。

快速开始优先读取 Persona。缺失字段使用“中性称谓”和“无名庭园”，外貌可为空。叙事人称由玩家预设和实际输入决定。

验收必须覆盖：草稿无副作用、确认时消息数不变且无 LLM 请求、首个 assistant 楼层复读持久化、刷新恢复、重复点击、聊天切换、写入失败保留草稿、旧聊天兼容解析，以及继承后的第一次真实行动才首次调用 LLM。
