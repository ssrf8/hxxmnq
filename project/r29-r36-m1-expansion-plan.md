# 0.2.0-r29 ～ r36：M1 剧情收束、金币循环、温室三路线与最终验收计划

## 1. 状态与目标

- 计划状态：已确认，等待从 `0.2.0-r28` 已验收基线开始实施。
- 已验收基线：`0.2.0-r28`（在场快照同步）。
- 下一检查点：`0.2.0-r29-narrative-economy`。
- 交付节奏：每一轮都生成独立检查点，完成自动门禁、打包、导入和真实 Luker 验收后，才进入下一轮；旧检查点不覆盖。
- 当前阶段目标：完成 M1，而不是提前铺开四设施、八角色的 M2 全量内容。
- 本计划新增的主循环：

```text
完成温室妖花核心教学战
→ 解锁可重复符卡副本
→ 胜负结算金币并推进一个时段
→ 在灵梦小店购买材料或特殊道具
→ 分别完成魔理沙、爱丽丝、荷取的温室方案剧情
→ 三套方案全部解锁后正式选型并消耗资源改造
→ 后续可再次付费换型
```

## 2. 已确认决策

### 2.1 剧情责任分类

剧情是否限制 LLM 回合，不按“发生在哪个设施”判断，而按它是否承担下游状态责任判断。

| 类型 | 适用范围 | LLM 调用 | 正式状态写入 | 收尾方式 |
|---|---|---|---|---|
| `progression_fixed` | 解锁设施、解锁方案、正式选型、改变主线门槛、触发后续连锁 | 1 次为主，必要时最多 2 次；输入次数预先登记 | 本地白名单结算器 | 固定结局后关闭输入并回到庭园 |
| `progression_session` | 确需玩家补充一次的阶段推进剧情 | 固定 2 个有效 assistant 回合 | 本地按真实楼层计数并结算 | 最后一回合自动收束 |
| `free_side_story` | 可有场景、角色、天气、道具或既有状态等出现条件，但自身结果不作为任何后续事件前置、不推进主线、不触发连锁的独立支线 | 不限制回合数 | 只允许会话摘要与普通关系事实 | 玩家主动离开或自然结束 |
| `ambient_interaction` | 普通对话、查看、照料与不改变长期状态的日常内容 | 不限制回合数 | 常规 MVU 更新规则 | 自由结束 |
| `static_script` | 商店特殊商品提示、重复使用提示、确定性短演出 | 0 次 | 本地动作按登记表写入 | 播放预写文本后返回原界面 |
| `deterministic_action` | 购买普通商品、副本奖励、库存增减、冷却判断 | 0 次 | 本地原子事务 | 即时结果与复读验证 |

`free_side_story` 可以由主屋已修复、设施已开放、角色在场、特定天气或玩家持有某件道具等条件触发；这里的“自由”不是没有出现条件，而是该支线的结果不承担任何后续前置。它不得在结束后偷偷解锁另一条事件。若后来需要承担下游结果，必须升级为 `progression_fixed` 或 `progression_session`，并新增正式事件配置。

### 2.2 受控推进剧情

所有推进事件必须从登记配置取得：

- `config_id`、标题、事件类型与优先级；
- 当前 MVU 前置、阻断条件和参与角色；
- 本轮模型可见的最小状态投影；
- 预登记剧情大纲、必须出现的关键节点和禁止偏离项；
- 允许结果与每个结果的固定结尾；
- 最大有效 LLM 回合数；
- 本地结算效果、成本、时间推进与幂等 ID；
- 失败恢复方式和回归用例。

模型只负责在人物性格和当前状态内演绎过程，不得自由决定设施是否解锁、方案是否获得、资源是否扣除、时间是否推进或下一事件是否开启。正式写入必须发生在完整 assistant 楼层结束后，并由本地从请求前状态计算、复读验证和原子提交。

### 2.3 温室三路线

保留三条正式路线：

1. 魔理沙：自由生长型；
2. 爱丽丝：人偶维护型；
3. 荷取：河童自动化型。

规则：

- 第一次正式选型前必须看完三套方案；
- 三个方案解锁结果永久保留；
- 同一时间只允许一种 `current_form` 生效；
- 第一次改造统一消耗 4 点物资并推进一个时段，不消耗灵感；
- 后续换型消耗 3 点物资并推进一个时段；
- 换型不抹除角色剧情、方案解锁与关系事实；
- 三条路线只改变设施表现、事件路由、角色参与和异常类型，不增加生产率、等级或经营数值加成。

### 2.4 副本与金币

- 完成 `greenhouse_flower_core` 后解锁可重复符卡副本。
- 副本使用本地白名单 JSON 配置；进入、游玩、结算和发奖均不调用 LLM。
- 初版提供 3 个固定配置，允许无限重复挑战，不设体力或每日次数限制。
- 漂亮取胜奖励 12 金币；勉强取胜奖励 8 金币；落败奖励 3 金币；主动取消奖励 0。
- 漂亮取胜、勉强取胜和落败都推进一个时段；主动取消不推进时间。
- 每个 `settlement_id` 只能发奖和推进时间一次。
- 副本模式不提供剧情替代结算，避免零游玩刷取奖励。

### 2.5 灵梦小店与特殊商品

- 普通购买为纯本地事务，不调用 LLM。
- 商品目录由本地静态配置维护，MVU 只保存余额、库存、唯一物品状态与幂等记录，不复制整张商品表。
- 普通材料首发价格：1 点物资 6 金币；4 点物资组合包 22 金币。
- `异变触发卡` 为可重复购买的消耗品；使用后只从本地已登记且当前满足条件的异变配置中选择，不生成未知事件。
- `十六夜咲夜的怀表` 为唯一关键物品；购买和使用提示采用预写对话，不调用 LLM。
- 后续新增商品必须通过 `item_id + item_type + price + local_effect/use_behavior + dialogue_id` 登记，不允许模型临时创造可购买按钮、价格或物品效果。

### 2.6 咲夜怀表

- 能力：暂停五分钟。
- 永久关键物品，每个游戏日最多使用一次。
- 启动本身不推进时段，不允许回滚 MVU、撤销战斗、退还购物或改写已完成事件。
- 每次使用记录地点、日期、时段和累计次数，并产生 `temporal_trace`。
- 当天重复使用只播放预写失败提示，不调用 LLM。
- 灵梦、咲夜、八云紫、蓬莱山辉夜等具备相关能力或实力的角色只在满足地点、在场、接触或事件条件时察觉，不得全员隔空同步得知。
- 第一次察觉若会开启后续链，采用受控推进剧情；没有下游解锁的单独后续反应可以是 `free_side_story`。
- 紫、辉夜等不自动加入第一版固定八人，也不因一次察觉建立长期动态档案。

## 3. 计划中的 MVU 状态链

下面是目标字段，不在 R29 开始前一次性全部写入。每轮只添加当轮拥有完整消费者和测试的字段。

### 3.1 金币

| 链路 | 计划 |
|---|---|
| 路径 | `resources.coins` |
| 类型/默认 | integer，`0`，范围 `0..99999` |
| 写入者 | 本地副本奖励结算、本地商店购买事务 |
| 读取者 | 顶栏资源显示、商店价格判断、模型条件投影（仅剧情确有需要时） |
| 清理/迁移 | R28 旧存档缺失时补 `0`；不得从正文猜测余额 |
| 测试 | 胜负奖励、失败奖励、取消零奖励、重复 ID、余额不足、购买后复读 |

### 3.2 可重复副本

计划扩展 `battle`：

- `dungeon_unlocked: boolean`；
- `run_count: integer`；
- `last_run: null | { config_id, outcome, reward_coins, started_day, started_time_period, settled_day, settled_time_period }`；
- `rewarded_ids: string[]`，最多 256 个，FIFO 清理；旧 ID 不能从聊天文本、模型输出或外部参数重新提交；
- `current` 继续承担待结算可信结果，并增加 `mode: mainline | dungeon` 来源标记，区分主线战斗与副本战斗。

结算顺序固定为：校验配置与结果 → 检查结算 ID → 计算金币 → 推进时段 → 追加幂等记录 → 更新最近结果 → 清空待结算字段 → 复读。任何一步失败不得部分发奖或部分推进时间。

### 3.3 商店与库存

计划新增：

```text
shop
├─ unlocked
├─ purchase_settled_ids[]（最多 256 个，FIFO）
└─ static_dialogue_seen_ids[]（最多 128 个，FIFO）

inventory
└─ consumables.{item_id}: quantity（每项 0..99）
```

现有 `key_items` 继续保存唯一关键物品。普通材料购买直接增加 `resources.materials`，不在库存中再保存第二份数量。

商店固定在 `greenhouse_flower_core` 完成时与符卡副本一起解锁。入口位于庭园常驻壳，不要求灵梦当前在场；商店内容仍以灵梦经营与预写文本表现。购买后若物资会超过 schema 上限 20，则整笔交易拒绝，不做部分成交、不扣金币。

### 3.4 温室路线

优先复用现有字段，避免第二事实源：

- `facilities.magic_greenhouse.unlocked_forms`：已解锁的基础形态和三套改造方案；
- `facilities.magic_greenhouse.current_form`：当前实际生效形态；
- `facilities.magic_greenhouse.active_effects`：当前形态的叙事/事件效果；
- `events.completed_key_events`：三套方案事件与首次选型/换型结果；
- `characters.{id}.current_relationship_facts`：合作中形成的具体事实。

计划使用的稳定形态名：

- `基础魔法温室`；
- `自由生长型温室`；
- `人偶维护型温室`；
- `河童自动化型温室`。

不新增“当前路线”字段；`current_form` 是唯一事实源。是否已具备选型资格由三项方案事件完成标记与 `unlocked_forms` 共同校验。

### 3.5 怀表与时间痕迹

`key_items.sakuya_watch` 计划保存：

- `obtained`；
- `state: ready | daily_cooldown`；
- `last_used_day`；
- `total_uses`；
- `last_used_area_id`；
- `last_used_time_period`；
- `temporal_trace_active`；
- `noticed_by_character_ids`。

新一天开始时本地规则把 `daily_cooldown` 恢复为 `ready`，但不会自动清除尚未被剧情消费的时间痕迹。痕迹只能由登记事件确认、转化或清除。

### 3.6 事件配置唯一维护源

R29 起，事件配置采用“统一契约、分文件目录、运行时合并”的结构：

```text
src/lorebook/events/
├─ event-contract.md                 # 字段、类型、投影与结算契约
├─ greenhouse-vertical-slice.json    # 现有主屋/温室主线，继续作为当前事件内容事实源
├─ greenhouse-upgrade-routes.json    # R31～R34 三方案与改造事件
├─ free-side-stories.json            # 不承担下游前置的自由支线
└─ special-item-events.json          # R35 异变卡、怀表与察觉事件
```

不得再创建第二份包含相同 `config_id` 的全局 JSON。构建时由一个本地事件注册器读取上述文件并拒绝重复 ID、未知类型、缺失结尾或非法下游引用。

运行时所有者固定为 `src/ui/event-registry.ts`；它只负责合并、索引和校验配置，不写 MVU。R29 同时新增 `src/ui/state-migrations.ts`，集中处理 R28 及后续旧存档的幂等默认值迁移；不得把迁移补丁散落在各个视图。时间推进统一收口到 `src/ui/time-rules.ts`，副本、建设、换型和怀表冷却都调用同一实现。

每个事件使用以下稳定字段：

```text
config_id
title
event_type
trigger_action_ids[]
prerequisites[]
blocks[]
participants[]
facility_id
priority
one_time
max_effective_rounds
projection_keys[]
narrative_outline[]
required_beats[]
forbidden_deviations[]
allowed_results[{ result_id, fixed_ending }]
local_settlement
downstream_unlocks[]
failure_recovery
```

模型只接收当前事件的参与者、最小 MVU 投影、`narrative_outline`、`required_beats`、`forbidden_deviations` 与所选行动对应的固定结尾。`local_settlement`、幂等规则、内部文件路径和开发注释绝不投影给模型。

受控事件的 `action_id -> result_id` 映射由本地注册表决定，不解析模型正文来选择结果。模型可以自由组织措辞和过程，但不能通过输出另一个结果改变结算。

## 4. R29：剧情责任收束与金币副本闭环

检查点：`0.2.0-r29-narrative-economy`

### 4.1 目标

- 将现有事件明确标记为受控推进、自由支线、静态演出或确定性动作；
- 把当前温室链的模型可见文字从“自由推进”收束为 MVU 状态 + 剧情大纲 + 固定结尾；
- 在妖花核心完成后解锁可重复符卡副本；
- 建立金币奖励与胜负均推进时段的本地事务。

### 4.2 维护源范围

- `src/schema/initial-state.json`；
- `src/schema/02-mvu-schema.js`；
- `src/schema/field-ledger.md`；
- `src/lorebook/variable-update-rules.md`；
- `src/lorebook/model-projection.md`；

- `tests/ui-contract.test.mjs`；

### 4.3 事件整理

现有主线事件全部显式归入 `progression_fixed` 或 `progression_session`：

- 灵梦结界检查；
- 主屋维修；
- 魔理沙材料线索；
- 第二点灵感；
- 清理旧地基；
- 建造基础温室；
- 第一次使用；
- 两回合温室研究；
- 妖花核心激活与战后结算。

每项配置补齐剧情骨架、固定结局、最大回合、允许结果和本地效果。开发事故说明不得进入模型可见文本。

### 4.4 副本内容

- 新增独立副本菜单，不复用主线事件入口；
- 庭园常驻壳新增最小“符卡副本”入口，放在庭园主操作区；R36 再统一优化布局；
- 新建 `src/battle/dungeon-registry.json` 作为副本配置白名单，实际配置存放在 `src/battle/configs/dungeons/`；
- 初版固定登记三个纯本地配置：`fairy_pattern_practice_v1`（单阶段练习）、`forest_magic_residue_v1`（双阶段标准）、`boundary_echo_trial_v1`（双阶段高压）；
- 三个配置首版共用 `coins_standard_v1` 奖励表，即 clean/narrow/loss 为 12/8/3；难度差异只提供玩法选择，不形成收益上的唯一最优副本；
- 所有配置通过现有速度、数量、间隔、持续时间和伤害上限校验；
- 配置差异以弹幕组合和阶段结构为主，不引入技能树、装备或永久战斗成长；
- 结算页使用预写结果文本，不触发战后 LLM；
- 战斗失败仍给 3 金币并推进一个时段，不造成死局或永久伤残。

### 4.5 验收

- R28 全部回归；
- R28 旧存档补出 `coins=0` 且可继续；
- 教学战未完成时副本入口不可用并显示本地原因；
- 完成后可无限重复进入；
- clean/narrow/loss 分别只发 12/8/3 金币并推进一个时段；
- 取消不发奖、不推进时间；
- 刷新或重复提交同一结果不重复发奖；
- 副本全过程没有新 user/assistant 楼层。
- `last_run` 同时保存开战时与结算后的日期/时段，跨越夜晚时可以证明日期推进正确。

## 5. R30：灵梦小店与数据驱动商品目录

检查点：`0.2.0-r30-reimu-shop`（已完成并由所有者验收）

### 5.1 目标

- 建立可扩展的本地商品目录；
- 打通金币购买物资的零 LLM 闭环；
- 为后续普通道具、玩家可使用道具和角色契机道具保留稳定类型边界。

### 5.2 商品类型

| 类型 | 行为 |
|---|---|
| `resource` | 购买后直接原子修改登记资源 |
| `consumable` | 增加 `inventory.consumables` 数量 |
| `key_item` | 唯一获得，写入 `key_items` |
| `trigger_item` | 使用时选择登记事件，不允许任意事件 ID |
| `player_usable` | 执行本地登记能力；不得执行模型代码 |

首发普通商品：

- `basic_material_single`：6 金币，物资 +1；
- `basic_material_crate`：22 金币，物资 +4。

商品维护源固定为：

- `src/shop/catalog.json`：ID、类型、价格、数量、唯一性、启用检查点和本地行为 ID；
- `src/shop/dialogues.json`：预写购买、使用、冷却和错误提示；
- `src/ui/shop-rules.ts`：白名单校验、购买预览、原子结算与复读；
- `src/ui/shop-view.ts`：商店的单一 UI 所有者，只渲染目录，不计算价格或效果。

`shop.unlocked` 在妖花核心结算时由本地与 `battle.dungeon_unlocked` 同时写入。R28 旧存档若已经完成妖花核心但缺少这两个字段，迁移器幂等补为 `true`。

特殊商品可先出现在目录中，但必须在相应使用能力完成后才允许购买；禁止出现“买到了却永远不能用”的半成品状态。

### 5.3 购买事务

点击商品 → 本地检查商店解锁、价格、库存/唯一性 → 显示确认 → 生成唯一购买 ID → 原子扣金币并应用效果 → 写入幂等记录 → 复读 → 播放本地结果。

余额不足、重复购买唯一物品、未知商品、越界数量或复读失败都不得部分扣款。

### 5.4 验收

- 购买普通材料不创建聊天楼层；
- 单份和组合包价格、数量正确；
- 余额不足不扣金币；
- 快速重复点击只成交一次；
- 刷新后金币和物资一致；

## 12. 每轮统一实施与交付门

每个检查点依次执行：

1. 从上一已验收检查点建立变更清单和回归锚点；
2. 先更新事件/字段契约和测试夹具，再改维护源；
3. 任何新字段完成 schema → initial state → field ledger → update rules → model projection → runtime reader → renderer → writer → migration → tests 全链；
4. 执行 `npm run check:ui`；
5. 执行 `npm test`；
6. 执行 `npm run build:ui`；
7. 更新 package/manifest 到新的、未占用的检查点；
8. 执行 `npm run package:checkpoint:dry` 并检查写入清单；
9. 在所有者明确授权的该轮交付范围内执行正式打包；
10. 记录文件大小、SHA-256、脚本 ID、世界书条目和源/包一致性；
11. 导入真实 Luker，新建测试聊天并完成该轮验收；
12. 所有者确认后更新交接，再进入下一轮。

任何失败先修维护源并创建新的检查点，不覆盖已经交付的目录或角色卡。
