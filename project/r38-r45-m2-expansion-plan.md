# 0.2.0-r38 ～ r45：M2 四设施、八角色与组合事件扩展计划

## 1. 状态与进入条件

- 计划状态：方向已由所有者确认，可作为 R37 之后的正式路线；尚未授权提前实施、打包或覆盖任何检查点。
- 当前维护源位于 R34 后、R35 前；必须完成 R35～R37，并补齐 R33/R34 尚未闭环的独立真实验收。只有 R37 真实验收通过后，才能把 manifest 的 `next_checkpoint` 切换到 R38。
- M2 目标是完成第一版总计四个主要设施与八名固定角色的真实可玩内容，不是额外增加四座新设施。
- M2 保持独立检查点策略：每轮修改维护源、执行自动门禁、打包到未占用目录、导入真实 Luker 并由所有者验收；旧检查点永不覆盖。

## 2. M2 完成目标

第一版四个主要设施：

1. 魔法温室：M1 已形成建设、异常、战斗和三路线改造闭环；
2. 妖精花园：R39 建立完整垂直切片；
3. 月见温泉：R40 建立设施主导的夜间观测与小型异常闭环；
4. 宴会广场：R41 建立夜间饮食、聚会与符卡活动闭环。

第一版固定八名角色：灵梦、魔理沙、琪露诺、爱丽丝、米斯蒂娅、萃香、荷取、咲夜。M1 负责灵梦、魔理沙、爱丽丝、荷取的主要可玩内容并建立咲夜契机；M2 重点补齐琪露诺、米斯蒂娅、萃香、咲夜，同时让既有角色能参与跨设施组合事件。

M2 还必须完成：

- 登记式组合事件和小型异变；
- 更多本地白名单战斗配置，但不引入等级、装备或技能树；
- 长期存档迁移、数据库恢复和无数据库降级；
- 移动端、无障碍、长聊天、Swipe/重试等高级运行验收。

## 3. 沿用的稳定架构

M2 不重写 M1 架构，继续使用四层协议：

```text
剧情模型：庭园正文 + GensokyoScene + 可选 GensokyoPresence
额外变量模型：唯一 UpdateVariable/JSONPatch，只写开放语义字段
bridge：UID、会话生命周期、关键事件、设施、资源、奖励和幂等结算
MVU stat_data：所有正式剧情进度与持久状态的唯一事实源
```

事件推进固定为：

```text
本地登记表定义前置、参与者、投影、剧情骨架、允许结果和结算效果
UI 读取“登记表 + 当前 MVU”派生可用入口
剧情模型演绎过程
额外变量模型更新关系事实、摘要、焦点和长期记忆
bridge 验证并提交关键状态迁移
```

禁止恢复以下旧方向：

- 剧情模型顺手输出或决定全部变量；
- 额外变量模型直接完成设施、路线、奖励或下游事件；
- UI、数据库或聊天正文成为第二事实源；
- 新增与 `completed_key_events`、设施状态或 `current_form` 重复的万能章节/路线字段；
- 从模型文本生成可执行按钮、事件 ID、商品、战斗配置、HTML、URL 或脚本。
- 在结算器维护第二份事件级允许结果，或通过通用关键词世界书向模型投影整份事件目录；
- 接受倒退日期/时段或未登记区域进入正式状态。

M2 每个新事件必须登记并通过统一 loader，运行时只投影当前事件及其白名单状态路径。新设施或角色需要新投影路径时，应显式扩展 allowlist 与正反测试，不得以全量状态或全量事件配置作为兼容兜底。

## 4. M2 状态与内容边界

### 4.1 设施状态

四个固定设施继续使用显式稳定字段，不把固定设施伪装成无约束动态字典。每座新设施在对应轮才加入：

```text
areas.{area_id}
facilities.{facility_id}
events.completed_key_events.{event_id}
```

每个新增字段必须完成 schema → initial state → field ledger → update rules → model projection → runtime reader → renderer → writer → migration → tests 全链。设施完整配置、剧情脚本、建设成本和事件目录留在本地维护源，MVU 只保存当前状态、已解锁形态、活动效果和完成结果。

### 4.2 角色与在场状态

- `presence_snapshot` 继续是地图与现场叙事的唯一在场事实；
- 角色抵达、退场或换区只通过受控 `GensokyoPresence` 回执或登记事件的本地结算改变；
- `characters.{id}.current_relationship_facts` 保存具体关系事实，不使用好感度数值；
- 额外变量模型可写关系事实、互动摘要与长期记忆，不得把角色自动加入现场、创建 UID 或完成关键事件；
- 新内容不能让不在场角色隔空共享秘密，也不能因为某角色与设施有关就把其设为永久管理员。

### 4.3 组合事件

组合事件使用登记配置引用设施、角色、时段、天气、物品和已完成事件，不为每个角色对或设施对新增专用布尔字段。只有承担下游前置的结果才写 `completed_key_events`；独立插曲只写开放语义记忆，或在结束后不留下正式进度。

### 4.4 数值与资源

具体建设成本、商店价格、异常权重、奖励和冷却在对应检查点实施前作为本地目录数据确认。未经单轮计划确认，不把讨论数值写进 Schema 或稳定契约。任何资源结算继续由 bridge 本地原子提交，不由额外模型决定。

## 5. R38：M2 基础设施与 M1 冻结

检查点：`0.2.0-r38-m2-foundation`

目标：

- 以 R37 已验收状态冻结 M1 字段和迁移基线；
- 完成普通会话 UID/创建/关闭/幂等结算的 bridge 单一所有权，不把 M1 遗留双写问题带入 M2；
- 定义四设施登记、来访条件、组合事件和事件队列的项目契约；
- 建立新设施/新角色的模板化字段台账与测试夹具，但不预建无消费者字段；
- 统一事件冲突、优先级、最大活动事件数、等待队列容量和失败恢复；
- 验证 R29～R37 既有流程不受基础设施调整影响。
- 冻结并回归 R35～R37 已采用的事件精确投影、时间单调、区域白名单和 R37 世界书激活审计证据；缺失证据时不得进入 R39。

R38 不新增大型可玩设施，不改变资源价格、温室路线或怀表能力。只有基础契约和回归门通过后才进入 R39。

## 6. R39：妖精花园与琪露诺

检查点：`0.2.0-r39-fairy-garden-cirno`

内容范围：

- 建立妖精花园的发现、建设、首次使用和异常观察闭环；
- 琪露诺作为主要角色参与冻结、局部季节异常和妖精式误解，但不能被写成稳定可靠的设施管理员；
- 至少一条受控推进剧情负责正式解锁/建设，至少一条不限回合的自由支线负责角色互动；
- 局部冻结或季节变化作为登记事件/效果，不修改全局天气事实来伪造影响范围；
- 琪露诺抵达、移动与离场必须遵守 `presence_snapshot`；
- 不加入大妖精作为固定第九角色，不建立等级、采集产量或经营数值链。

验收重点：从旧存档迁移到花园未解锁状态；完整完成建设；刷新和 Swipe 不重复扣资源；琪露诺退场后地图和下一轮提示同步更新。

## 7. R40：月见温泉与夜间观测

检查点：`0.2.0-r40-moon-view-hot-spring`

月见温泉采用设施主导路线，不指定永久管理员角色：

- 核心是夜间观测、天气变化、访客交流和小型异常，不建立体力、生命值或数值恢复系统；
- 设施建设/启用由本地受控事件结算，实际参与角色由当前在场、事件配置和信息边界共同决定；
- 同一设施可由不同角色在不同事件中参与，但任何角色都不会因参与一次就永久绑定温泉；
- 月相、夜色或天气若只承担当前表现，保持派生/事件上下文；只有确需跨轮持续时才设计正式字段；
- 至少包含一条设施推进剧情、一条夜间自由交流和一条无下游解锁的小型异常。

验收重点：白昼/夜晚入口正确；不在场角色不能参与；异常结束后临时效果正确清理；不会引入第二套时间或天气状态。

## 8. R41：宴会广场、米斯蒂娅与萃香

检查点：`0.2.0-r41-banquet-square`

内容范围：

- 建立宴会广场的建设、首次小宴会和后续可重复聚会入口；
- 米斯蒂娅负责夜间饮食、歌声和林地来访内容，商品或食物效果必须来自本地登记表；
- 萃香负责宴会组织、地点重叠与符卡活动，不把酒量、醉意或好感做成数值养成；
- 宴会允许临时突破普通在场人数，但仍必须输出完整 `GensokyoPresence` 并在结束后恢复合理快照；
- 可重复聚会不得重复发放一次性解锁、资源或关系事实；
- 宴会中的战斗/符卡只引用白名单配置，不接受模型生成参数。

验收重点：多人正文与 GAL 顺序稳定；参与者和退场快照正确；重复宴会幂等；米斯蒂娅与萃香各自至少拥有一条可自由持续的互动内容。

## 9. R42：咲夜正式路线与时间异常

检查点：`0.2.0-r42-sakuya-time-anomaly`

内容范围：

- 承接 R36 怀表的 `temporal_trace` 与咲夜察觉事件，形成正式接触和后续可重复互动；
- 咲夜可参与宴会维护、精确管理和时间异常调查，但不会自动成为庭园管家或永久常驻；
- 时间能力继续遵守“怀表每天一次、暂停五分钟、不回滚消息、不撤销结算、不倒退时段”；
- 正式登场、察觉确认和下游解锁由 bridge 结算；对玩家行为的判断、互动摘要和具体关系事实由额外变量模型写入；
- 八云紫与蓬莱山辉夜仍只保留未来白名单/信息边界，不加入第一版固定角色或现场快照。

验收重点：旧 R36 怀表记录可迁移；同一痕迹不重复触发首次接触；不在场时不能隔空发言；时间异常失败不会破坏已完成状态。

## 10. R43：跨设施组合事件

检查点：`0.2.0-r43-combination-events`

目标是证明四设施和八角色可以组合，而不是堆叠大量孤立按钮：

- 从本地登记表选择少量可完整验收的组合事件；
- 组合条件可引用两个设施状态、在场角色、时段、天气、物品和既有事件，但不得创建无限组合矩阵；
- 示例方向包括温室植物影响妖精花园、宴会改变访客快照、温泉夜间观测发现时间余波；
- 会开启后续链的组合事件使用 `progression_fixed/session` 和本地白名单结算；纯插曲使用 `free_side_story`，不能偷偷写关键完成态；
- 同一组合事件必须有稳定 `config_id`、冷却/一次性规则、冲突条件和失败恢复。

验收重点：事件优先级可预测；两个候选冲突时不并发写入；刷新不重抽待处理事件；模型不能创造未登记组合。

## 11. R44：小型异变、战斗扩展与长期恢复

检查点：`0.2.0-r44-anomalies-battles-recovery`

内容范围：

- 增加少量与四设施相关的登记异变和白名单战斗配置；
- 异变卡继续只从当前满足前置的登记事件中确定性抽取；
- 战斗结果继续由本地 BattleEngine 与 settlement ID 结算，不从正文、玩家 JSON 或模型输出读取；
- 完成长聊天、旧存档迁移、数据库归档恢复、数据库不可用和中断事务恢复；
- 明确等待事件、近期结果、幂等 ID 和关系事实的容量与清理策略；
- 不加入装备、等级、技能树、体力、税收或生产链。

## 12. R45：M2 完整第一版候选

检查点：`0.2.0-r45-m2-release-candidate`

完成门：

- 四设施都可从受支持的旧存档或新聊天进入并完成核心闭环；
- 八名固定角色都拥有真实可玩内容、正确在场边界与至少一条可持续互动；
- 组合事件、小型异变和扩展战斗遵守登记、白名单、幂等和失败恢复；
- 额外变量模型只写开放语义字段，关键进度全部由 bridge 本地结算；
- 桌面、约 320px 宽容器、短视口、200% 缩放、键盘、触控与 reduced motion 通过；
- Swipe、停止/继续、空回复、网络失败、变量模型失败、刷新、切聊天和切角色卡通过；
- 长期迁移、数据库恢复与无数据库降级通过；
- 自动门禁、JSON/PNG 包复读（若当轮明确授权打包）和真实 Luker 验收全部通过。
- 真实运行抽查新增事件只激活自身投影，缺席角色不因姓名或递归扫描误入上下文，时间与在场迁移继续遵守 M1 护栏。

R45 通过后 M2 才可标记为 `complete`，随后再决定是否进入 M3 的正式发布、PNG 兼容和更广设备验收；不得把 M2 离线候选直接称为发布版。

## 13. 每轮统一门禁

每轮必须：

1. 从上一已验收检查点建立回归锚点；
2. 先更新事件/字段契约和正反测试夹具，再改维护源；
3. 为每个新增字段完成完整字段链和幂等迁移；
4. 为每个事件分别列出剧情正文、GAL 表现、可选在场回执、额外变量开放字段和 bridge 本地结算字段；
5. 验证模型不能写本地独占字段，bridge 不能覆盖额外模型的合法语义更新；
6. 执行 TypeScript 检查、自动测试和生产 UI 构建；
7. 只有所有者明确要求该轮打包时，才更新到未占用检查点并执行 dry-run、正式打包和产物复读；
8. 真实 Luker 验收必须使用新聊天和该轮精确产物，离线预览不能替代；
9. 失败时修维护源并创建新的未占用检查点，不覆盖已交付目录。

## 14. 仍需逐轮确认的数据

下列内容已允许设计，但具体值必须在对应检查点实施前确认并写入本地登记表：

- 妖精花园、月见温泉、宴会广场的建设成本与前置；
- 小型异常权重、冷却和持续时间；
- 新战斗配置数量、名称、阶段参数与奖励；
- 可重复宴会、温泉观测和组合事件的冷却；
- 临时效果和近期结果的容量、FIFO 或归档规则；
- 各设施的美术表现与素材范围。

这些数据调优不得改变事件所有权、模型/bridge 边界、固定角色名单、信息边界或禁止系统。若需要改变架构，必须先更新本计划并由所有者再次确认。
