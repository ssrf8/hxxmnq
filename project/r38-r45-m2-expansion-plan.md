## 2. 产品阶段划分

### 2.1 新手教程：到首次温室选型为止

教程继续覆盖：

1. 确定性开场与庭园地图；
2. 灵梦结界检查、主屋修复和资源消耗；
3. 温室建设、首次使用和多轮交流；
4. 妖花核心与符卡战；
5. 副本、金币、商店和物资循环；
6. 魔理沙、爱丽丝、荷取三套温室方案；
7. 首次温室选型。

教程毕业状态不新增 `current_chapter`、`current_route` 或重复的 `tutorial_complete` 字段。运行时使用以下既有事实派生：

```text
events.completed_key_events.select_greenhouse_form 已存在
```

首次选型结算成功后，UI 显示一次明确的毕业说明：移动庭园已经开放，此后没有必须完成的主线，可以自由建设、邀请访客、处理异变、使用道具或进行日常交流。

### 2.2 开放庭园：能力网络而非主线链

教程结束后的内容分为四个并行循环：

| 循环 | 内容 | 允许的门槛 | 禁止的门槛 |
|---|---|---|---|
| 庭园建设 | 妖精花园、月见温泉、宴会广场、温室换型 | 资源、设施自身状态 | 完成另一个无关设施剧情 |
| 角色生活 | 邀请、随机来访、停留、离场、自由聊天、个人事件 | 已认识、时段、设施、天气、具体关系事实 | 全局章节、数值好感或无关角色路线 |
| 七日异变 | 玩家创建世界规则，连续七天影响所有相关剧情 | 持有异变卡、当前无活动异变 | 预登记随机异变池 |
| 经营与道具 | 副本、金币、商店、背包、聊天用物 | 本地目录、数量、冷却、使用条件 | 模型临时创造价格、物品或本地效果 |

开发检查点可以顺序交付，游戏内不得把 R39、R40 等版本顺序解释成玩家必须按顺序完成的剧情。

## 3. 沿用的稳定架构

```text
剧情模型：基于当前场景事实自由生成庭园正文 + GensokyoScene + 可选 GensokyoPresence
额外变量模型：唯一 UpdateVariable/JSONPatch，写开放语义字段并提出聊天后的时间更新
bridge：UID、时间、资源、背包事务、七日异变生命周期和关键结算
MVU stat_data：全部正式状态的唯一事实源
UI：只读取“本地登记表 + 当前 MVU”派生入口和表现
```

继续禁止：

- 模型决定资源、设施、物品数量、异变生命周期或关键事件结果；世界时间只能通过受校验的 MVU 时间字段前进，异变到期由运行时从已接受时间派生；
- UI、数据库、聊天正文成为第二事实源；
- 从模型文本创建可执行按钮、物品、事件 ID、战斗参数、HTML、URL 或脚本；
- 把完整事件目录、完整背包目录或其他异变历史无条件投影给模型；
- 新增与既有完成态重复的万能章节字段；
- 接受倒退日期/时段、未知区域或未知角色进入正式状态；
- 用全量父对象替换绕过 bridge 独占路径。

## 4. 七日自定义异变系统

### 4.1 异变卡的新含义

`incident_trigger_card` 从“随机抽取登记事件的消耗品”改为“创建一次自定义七日异变的授权消耗品”。

使用流程：

```text
背包选择异变卡
→ 打开结构化异变表单
→ 本地校验字段和当前生命周期
→ 玩家确认
→ 预留 1 张卡并创建 pending_activation
→ 首次 LLM 调用生成启用剧情和隐藏源头草案
→ bridge 校验源头结构并锁定
→ 原子消费预留卡并创建活动异变
→ 28 个标准时段内所有 LLM 剧情携带当前异变投影
→ 到期后强制进入灵梦收束
→ 收束成功后归档
```

玩家取消表单、字段校验失败、当前已有活动异变、源头生成失败、事务失败或复读失败时不得消费卡片。重试复用同一个 `pending_activation` 和生成事务，成功结果只能提交一次。

### 4.2 创建表单

表单至少包含：

- `title`：异变名称；
- `rule_text`：异变核心规则；
- `scope_mode`：全员、玩家与当前在场角色、指定角色；
- `character_ids`：指定角色时使用，只接受固定角色白名单；
- `presentation_tone`：玩家希望的表现倾向，自由文本；
- `excluded_content`：玩家不希望出现的内容，可留空。

项目不增加向布尔值、分级标签或独立开关，也不根据题材过滤玩家填写的异变规则。技术校验只限制长度、结构、白名单 ID 和不可执行内容；所有字段按纯文本转义和投影。

建议初始上限：标题 40 字、规则 600 字、倾向 160 字、排除内容 240 字。具体数值在 R39 实施前用提示预算测试确认，不进入 Schema 常量。

### 4.3 候选状态契约

正式字段以实施时的 schema 命名为准，计划契约如下：

```text
anomaly_cycle
├─ pending_activation: null | {
│    transaction_id,
│    reserved_item_id,
│    authoring_fields,
│    activation_message_id
│  }
├─ active: null | {
│    uid,
│    title,
│    rule_text,
│    scope_mode,
│    character_ids,
│    presentation_tone,
│    excluded_content,
│    hidden_origin: {
│      name,
│      type,
│      summary,
│      location,
│      cause,
│      resolution_method
│    },
│    revealed_clues: [{ day, summary }],
│    status: active | resolving,
│    started_day,
│    started_time_period,
│    started_period_serial,
│    expires_period_serial,
│    last_guidance_day,
│    activation_message_id,
│    resolution_message_id
│  }
└─ history: 最近完成异变的最小摘要，固定容量
```

字段责任：

| 路径 | 写入者 | 读取者 | 清理与迁移 |
|---|---|---|---|
| `anomaly_cycle.pending_activation` | bridge 异变预留事务 | 启用调用、背包事务恢复 | 成功提交或玩家取消后置空；旧存档默认 `null` |
| `anomaly_cycle.active` | bridge 异变事务 | UI、当前剧情投影、时间规则 | 收束后置空；旧存档默认 `null` |
| 活动异变文本字段 | 创建时由 bridge 固化 | 当前剧情模型 | 活动期间不可由模型改写 |
| `hidden_origin` | 启用回合由 LLM 生成草案，bridge 校验并一次性固化 | 每日灵梦调查、最终收束 | 普通剧情和普通 UI 不可见；活动期间不可改写 |
| `revealed_clues` | 每日调查回合由 LLM 生成摘要，bridge 每日最多追加一次 | 后续调查、最终收束、玩家可见调查摘要 | 随活动归档为最小摘要，不保存完整调查正文 |
| 起止时间与状态 | bridge | UI、时间推进、事件冲突器 | 只按标准时段单调推进 |
| `last_guidance_day` | bridge | 每日引导调度器 | 每日最多登记一次 |
| `anomaly_cycle.history` | bridge | 历史摘要 UI，可选模型回忆 | 固定容量，FIFO；不保存完整七日正文 |

额外变量模型不得任意写 `anomaly_cycle`。启用回合的隐藏源头草案和每日调查的线索摘要必须通过各自一次性、窄结构的 bridge 入口校验后提交；其余字段仍为 bridge 独占。额外变量模型仍可根据真实剧情更新关系事实、互动摘要和长期记忆，但不得延长、缩短、改名、改规则、替换源头或提前结束异变。

### 4.4 七日计时

- 标准时段继续是 `清晨 → 白昼 → 黄昏 → 夜晚`；
- 启用时记录绝对标准时段序号；
- `expires_period_serial = started_period_serial + 28`；
- 异变从确认启用起生效，直到经过完整 28 次标准时段边界；
- 怀表的五分钟暂停不推进标准时段，因此不减少异变剩余时间；
- Swipe、刷新、重试、空回复和失败事务不得重复计时；
- 玩家不能主动解除、提前找到源头或使用另一张卡覆盖活动异变。

当到达结束边界时，bridge 把状态从 `active` 改为 `resolving`，并创建唯一收束事务。收束完成前仍投影异变规则，但暂停其他会推进时间的操作；收束成功后才归档并置空 `active`。

### 4.5 灵梦引导与自由剧情

异变阶段只有三类固定骨架：

1. **启用回合**：异变开始影响现场，灵梦确认发生异变并开始寻找源头；同一次调用生成隐藏源头草案，校验成功后才正式启用与消费卡片；
2. **每日首次 LLM 剧情**：用一两句提及灵梦仍在调查或获得小进展，不要求她每次都在当前场景出现；
3. **最终收束回合**：第七日结束后，灵梦公开已锁定的源头并按登记解除方式完成收束，异变解除并归档。

除此之外没有固定剧情。角色互动、设施事件、自由聊天和组合事件按自身内容进行，但所有正文、GAL 表现和关系分析都必须遵守当前异变规则。

如果灵梦不在当前区域，每日提示只能通过合理的消息、传闻、远处动静或之后见面得知，不得违反 `presence_snapshot` 让她隔空参与现场对话。

隐藏源头不是正式角色、正式物品或可执行事件。LLM 可以把它写成角色、物品、地点或自然现象，但相关自由文本只服务本次异变叙事；除非另有本地登记流程，不得借此解锁角色、创建背包物品或写入新的永久世界状态。

### 4.6 模型投影

活动异变只向会产生剧情的请求投影最小信息：

```text
异变名称
核心规则
影响范围及命中的当前参与者
表现倾向
排除内容
当前是第几日／剩余标准时段
本轮是否需要灵梦的每日简短引导
是否处于最终收束回合
```

普通剧情不投影 `hidden_origin`。每日灵梦调查额外投影锁定源头和既有公开线索，但要求本日最多新增一条简短进展，不能完整揭露；最终收束才投影完整源头并允许公开。启用回合只投影玩家填写的异变字段和源头输出结构，不提供预写答案。

不向模型投影卡片预留 ID、消费 ID、结算 ID、完整历史、内部绝对序号或 bridge 清理规则。纯本地商店购买、背包整理和无剧情副本结算不调用 LLM，也不需要投影异变。

## 5. 独立背包与聊天使用物品

### 5.1 物品来源与类型

玩家不能创建物品。所有物品必须来自本地目录，并声明：

```text
item_id
title
item_type: consumable | key_item
stack_limit
use_mode: local | scene_chat | anomaly_authoring
scope_tags: registered_scope_id[]
unlock_conditions: registered_local_condition[]
consume_policy: on_commit | never
local_effect_id（可选且必须白名单）
prompt_description（聊天使用时的最小叙事说明）
cooldown_policy（可选）
```

- 可消耗品保存在 `inventory.consumables`，数量由本地事务维护；
- 永久物品保存在 `key_items`，获得后不因聊天使用删除；
- 咲夜怀表继续是永久关键物品，使用后进入每日冷却，不转成普通堆叠物；
- 普通材料继续使用 `resources.materials`，不在背包重复保存第二份数量。

现有字段结构可以继续承担正式数量，R38 先新增统一背包展示层，不为了界面美观迁移出第二套物品事实源。

首批设施与聊天物品目录：

| `item_id` | 名称 | 价格 | 商店开放条件 | 可用范围 | 正式效果 |
|---|---|---:|---|---|---|
| `fairy_candy_pack` | 妖精糖果包 | 6 | 妖精花园建成 | 妖精花园、普通角色聊天 | 只建立本场景的分享、游戏或吸引妖精叙事上下文 |
| `moon_viewing_tea` | 月见茶 | 8 | 月见温泉建成 | 月见温泉、普通角色聊天 | 只建立本场景的饮茶与夜谈上下文 |
| `hot_spring_sachet` | 温泉香包 | 8 | 月见温泉建成 | 月见温泉 | 只改变本场景的气味、氛围与相关描写 |
| `banquet_bento` | 宴会食盒 | 10 | 宴会广场建成 | 宴会、普通角色聊天 | 只建立本场景的分享食物上下文 |
| `oni_sake_flask` | 小瓶鬼酒 | 12 | 宴会广场建成 | 宴会、普通角色聊天 | 只改变本场景表现，不新增醉酒数值或长期状态 |
| `emergency_repair_kit` | 应急修缮包 | 12 | 任一后续设施建成 | `damaged` 设施修复 | 可替代修复所需 2 物资，仍需完成修复剧情并推进一个时段 |

六件消耗品的 `stack_limit=99`，不设置每日库存、轮换或刷新。商店只从当前设施正式状态派生开放商品，购买、扣金币、增库存和开放通知全部使用本地事务，不创建聊天楼层，也不调用 LLM。

第一版不新增第二件永久收藏品；咲夜怀表继续是唯一登记永久使用物。异变卡保持 `anomaly_authoring` 授权物，不进入普通场景道具上下文。

普通 `scene_chat` 道具只允许用于自由聊天、设施自由行动、月见温泉会话和宴会活动。以下上下文统一禁用：建设、装修、战斗、异变启用、每日灵梦调查、最终收束、其他固定结算，以及任意正在等待原子提交的事务。`emergency_repair_kit` 只通过专用修复入口使用，不受普通场景道具入口控制。

### 5.2 背包界面

背包作为庭园常驻入口，也可以在自由聊天输入区打开。至少提供：

- 全部、消耗品、永久物品分类；
- 名称、说明、数量、冷却和是否可在当前情境使用；
- 禁用原因直接可见，不只依赖鼠标悬浮；
- 异变活动期间，异变卡显示“已有异变，剩余 X 时段”，不可启用；
- 聊天内选择物品后显示待使用条目，可取消或更换，不立即扣除。

### 5.3 聊天使用事务

聊天中使用登记物品时：

```text
玩家选择物品和可选使用对象
→ UI 在下一条真实 user 消息中加入受控 GensokyoItemUse 标记
→ 剧情模型只看到登记物品说明、数量状态和玩家自然语言意图
→ assistant 完整回复
→ 额外变量阶段结束
→ bridge 校验 use_id、物品、数量、上下文和消费策略
→ 本地提交消费/冷却，并建立或合并 scene_item_context
→ 后续每轮继续投影最多 3 种道具及其当前叙事状态
→ 玩家点击“结束剧情”
→ 最后一次 LLM 调用携带道具上下文并完成收尾
→ 收尾成功后清除 scene_item_context
```

空回复、停止生成、消息发送失败、变量阶段失败或复读失败时不得消耗。刷新、Swipe 和重放使用稳定 `use_id` 幂等；模型正文不能声称消耗另一个物品，也不能通过描写创建目录外物品。

### 5.3 道具授权回执与自然语言边界

道具名出现在玩家自由输入中不是交易，也不是剧情事实。每次庭园请求必须在玩家文本之后附加一份由本地状态派生的 `【本轮道具授权】` 回执：

- `scene_item_context` 为空时输出“无”。模型只能把“我使用／激活／掏出某道具”及相近的声称、威胁、假设、玩笑或角色扮演，理解为台词或未完成的行动尝试；不得据此认定物品已在场、已发动、已消耗或已产生效果。
- `scene_item_context` 非空时输出“已登记”及其中的 `item_id`。只有这些本地 bridge 已登记的条目以及 `【当前场景道具】` 中的叙事状态，才是模型可以演绎的道具事实。
- 玩家文本不能创建、替换、激活或消费目录道具，模型和额外变量阶段也不能补写库存变化、强制状态或其他既成结果。

离线回归至少覆盖两种请求：未选择 UI 道具但玩家明确声称已使用某物时，提示必须给出“本轮道具授权：无”；选择 UI 道具并生成预留上下文时，提示必须只承认该登记 `item_id`。

永久物品的 `consume_policy=never`，但仍可写入登记冷却、使用次数或痕迹。可消耗物默认在完整回复和本地结算成功后扣除一次。

普通道具消费成功后，其叙事影响属于整个当前剧情，而不是单条 assistant 回复。同一调用最多提交一件新道具；同一场景最多存在 3 种不同 `item_id`，达到上限后必须结束场景才能加入第四种。同类道具后续再次使用时照常再消费一个，但只增加同一条目的 `quantity_used` 与 `use_ids`，不复制场景条目。

候选状态：

```text
scene_item_context: null | {
  uid,
  scene_uid,
  items: [{
    item_id,
    quantity_used,
    use_ids,
    initial_target_character_id: null | registered_character_id,
    started_message_id,
    narrative_state_summary
  }],
  status: active | ending
}
```

`item_id`、`scene_uid`、使用数量、消费 ID 和生命周期由 bridge 拥有；额外变量模型只允许更新每项简短的 `narrative_state_summary`，例如尚未打开、已经分享、已经用尽但仍是本场景既有事实。即使物品在正文中已经吃完或用完，后续调用仍投影它对当前场景造成的事实影响，直到场景正式结束。

角色在道具使用后进入当前场景时，模型可以看到道具的当前可观察状态，但必须结合 `presence_snapshot` 和摘要判断她能合理知道什么；不得把使用前因、缺席对话或他人私下反应自动写成后来者记忆。

活动异变与 `scene_item_context` 可以同时投影：异变规则继续约束所有适用描写，道具作为本场景事实参与演绎。两者都使用自己的最小投影，普通道具不能延长、缩短、覆盖异变，也不能改变作用范围或隐藏源头。

糖果、茶、食盒和鬼酒允许把当前在场角色作为初始使用对象，表现为分享或赠与。该选择只影响 `initial_target_character_id` 和场景叙事；成功后物品照常从玩家库存消费，不向角色创建永久库存，不强制写入关系事实、好感数值或承诺结果。额外变量模型只能根据真实互动决定是否产生普通关系事实。

玩家点击“结束剧情”时先把状态改为 `ending`，最后一次 LLM 调用仍携带道具和当前摘要；完整收尾与 MVU 更新成功后才清除上下文。收尾失败、停止生成或未采用 Swipe 时保持 `ending` 并允许幂等重试，不能提前遗忘物品或再次消费。

玩家尝试离开区域或开始另一段受控剧情时，UI 必须先阻止切换并引导执行同一结束事务。温泉或宴会因为本轮接受的 MVU 时间更新自动结束时，本轮完整回复直接兼任最终回复，安全结算时同时关闭活动与清除 `scene_item_context`，不额外发起一次模型调用。

`emergency_repair_kit` 不写入 `scene_item_context`。它只在 `pending_recovery` 中作为 2 物资的替代成本预留，修复剧情和结构回执成功后消费一次；失败、取消、重试或未采用 Swipe 时释放预留并保留物品。

## 6. 角色自主来访、邀请与离场系统

### 6.1 设计目标

角色不是常驻任务按钮，也不共享同一张随机出勤表。每个人的来访倾向由现有人设推导，时间只负责第一次筛选，设施、天气、活动事件、认识事实、当前人数和角色自己的目的共同决定权重。

```text
正式行动成功并推进标准时段
→ 固定事件参与者优先结算
→ 处理应当离场的普通访客
→ 检查普通/宴会人数上限
→ 从已认识且满足条件的角色中计算来访权重
→ 用聊天身份 + 日期 + 时段 + 调度版本确定性抽取
→ 写入待到访计划
→ 返回庭园安全状态时更新 presence_snapshot
→ 显示本地到访/离场通知
```

调度只在正式游戏时间推进后运行，不按现实分钟计时。刷新、Swipe、停止/继续、空回复和失败事务不重新抽取。

### 6.2 软认识门槛

角色档案存在不等于已进入随机来访池。资格从既有相遇事实派生，不新增全局章节或数值好感：

| 角色 | 进入随机来访池的软门槛 |
|---|---|
| 灵梦 | 教程开场已正式见面 |
| 魔理沙 | 教程温室线正式见面 |
| 爱丽丝 | 完偶维护方案会面；教程毕业时正常已经满足 |
| 荷取 | 完成工程测量方案会面；教程毕业时正常已经满足 |
| 琪露诺 | 妖精花园相关初遇、局部冻结事件或登记邀请完成 |
| 米斯蒂娅 | 夜间来访初遇、宴会筹备或登记邀请完成 |
| 萃香 | 宴会/聚集事件、空间聚散异常或登记邀请完成 |
| 咲夜 | 怀表时间痕迹调查或其他登记的正式接触完成 |

这些门槛只回答“她是否知道这个庭园并有理由再来”，不能作为其他设施或角色路线的前置。若后续新增等价初遇事件，只扩展本地资格条件，不建立第二套 `unlocked_characters` 事实源。

### 6.3 本地来访档案

每名角色在本地登记表拥有一个不可由模型修改的 `visit_profile`：

```text
character_id
eligibility_conditions
time_weights
interest_conditions
arrival_area_preferences
crowd_preference
stay_period_range
cooldown_period_range
invitation_policy
arrival_reason_ids
arrival_notice_ids
departure_notice_ids
```

登记表存放概率和行为边界，MVU 不保存整份人设或概率表。模型只在玩家真正开始交流时接收当前角色人设、现场快照、到访理由和必要状态。

### 6.4 八名角色来访倾向

以下是本卡人设的调度派生，不是新的原作事实：

| 角色 | 偏好时段 | 主要吸引条件 | 停留与人群倾向 |
|---|---|---|---|
| 灵梦 | 清晨、白昼、黄昏 | 结界不稳、活动异变、危险设施、正式验收 | 有事才来，通常较短；不把日常巡查写成常驻管理 |
| 魔理沙 | 白昼、黄昏，偶尔夜晚 | 温室、魔法实验、新道具、可观察异常 | 自发性较高，可不请自来；实验有进展时可能多留一段 |
| 琪露诺 | 白昼、黄昏 | 妖精花园、冻结现象、挑战和明显热闹 | 来得突然、停留偏短；被认真交付小职责时可延长 |
| 爱丽丝 | 白昼、黄昏 | 维护、人偶工程、结构故障、明确邀请 | 偏计划来访；无意义拥挤会降低权重，工作未收尾时不会突然走 |
| 米斯蒂娅 | 黄昏、夜晚 | 宴会、夜间客流、表演、摆摊机会 | 夜间权重高；有客流时愿意停留，清晨前通常离开 |
| 萃香 | 黄昏、夜晚 | 人群、宴会、空间聚散异常、明显热闹 | 最可能循动静出现；热闹持续时停留较长，冷清时可能很快换地方 |
| 荷取 | 清晨、白昼、黄昏 | 工程、水路、仪表、故障、正式委托 | 到访理由具体；完成测量或修复后倾向离开，夜间权重低 |
| 咲夜 | 白昼、黄昏；时间事件可突破 | 怀表痕迹、时间异常、宴会安排、明确邀请 | 基础权重低、目的明确、停留精准；不会无理由长期滞留 |

活动七日异变的自由文本只影响到场后的叙事，不被解析为可执行来访概率。任何活动异变都可以统一提高灵梦的调查候选权重，但不能从“大家都想来”等文本自动突破认识门槛或人数上限。

### 6.5 确定性随机与人数上限

- 同一聊天、同一日期、同一时段和同一调度版本的抽取结果固定；
- 每个标准时段最多产生 1 名普通随机新访客，避免一次推进突然刷满地图；
- 普通庭园最多同时有 3 名访客，不计算玩家；
- 宴会状态最多同时有 6 名访客；
- 固定事件需要的登记参与者可以临时突破普通上限，但事件结束后必须恢复合理人数；
- 已在场、冷却中、未认识、正在其他固定事件中或不满足信息边界的角色不进入候选；
- 没有候选时允许本时段无人到访，不能为了热闹强行选择零权重角色。

具体基础概率和权重数值在对应角色内容实施前调优，不进入稳定 Schema。

### 6.6 候选状态契约

`presence_snapshot` 继续是“现在谁在这里”的唯一事实源。调度状态只保存计划、冷却和当前来访的生命周期元数据：

```text
visit_scheduler
├─ version
├─ last_evaluated_period_serial
├─ pending_arrivals: [{
│    uid,
│    character_id,
│    reason_id,
│    target_area_id,
│    scheduled_period_serial,
│    source: random | invitation | event
│  }]
├─ cooldown_until_serial: { character_id: period_serial }
└─ invitation_cooldowns: { character_id: period_serial }

presence_snapshot
└─ visitor_meta: {
     character_id: {
       arrival_uid,
       reason_id,
       source,
       arrived_period_serial,
       earliest_departure_serial,
       planned_departure_serial
     }
   }
```

| 路径 | 写入者 | 读取者 | 清理规则 |
|---|---|---|---|
| `visit_scheduler` | bridge 来访调度器 | UI、时间规则、邀请事务 | 旧计划到达或失效后移除；旧存档幂等补默认值 |
| `presence_snapshot.present_character_ids` | bridge、本地登记事件、合法在场回执 | 地图、剧情模型、操作派生 | 到访/离场原子更新；仍是唯一在场事实 |
| `presence_snapshot.visitor_meta` | bridge | 离场调度器、到访说明 UI | 与当前在场白名单同步；角色离场时删除 |

额外变量模型不得修改 `visit_scheduler`、`visitor_meta` 或通过父对象替换改变在场角色。自由剧情中的主动换区/离场仍可使用经过白名单验证的 `GensokyoPresence`，bridge 合并时必须清理对应来访元数据。

### 6.7 安全时点与到访表现

- 战斗、固定剧情、受控会话、异变最终收束或背包事务进行中，不把待到访角色直接加入现场；
- 待到访计划在返回庭园地图且事务空闲时提交；
- 到访只显示本地通知和地图角色，例如“魔理沙骑着扫帚落在温室旁”；
- 到访通知使用登记模板和 `reason_id`，不调用 LLM，也不提前制造关系事实；
- 玩家点击角色后才创建真实聊天楼层，模型从到访理由和当前人设自然开始互动；
- 离场同样使用简短本地通知，不为每次离场调用 LLM。

### 6.8 停留与自动离场

- 普通访客初始停留范围为 1～3 个标准时段，具体范围由角色档案决定；
- 每次正式时间推进后检查离场，不在同一时段反复计算；
- 角色正在与玩家交流、参与固定事件或承担当前异变收束时不得自动离场；
- 到达计划离场时间但仍被事务占用时，标记为下一安全时点离场，不删除正在使用的参与者；
- 离场后写入角色自己的冷却，不能下一时段立即随机折返；
- 米斯蒂娅等夜间访客、萃香等宴会访客和咲夜等短时目的访客使用不同停留范围，不能共用统一模板。

### 6.9 玩家邀请

背包或庭园“访客”入口可以邀请已认识角色。邀请由本地规则决定三种结果：

1. `accept_now`：当前时段、人数、角色档案和事务允许，创建最近安全时点的待到访计划；
2. `reschedule`：当前不合适但后续存在合理时段，登记一个明确时段的待到访计划；
3. `decline`：角色当前没有合理来访条件，只显示预写的简短拒绝说明并进入邀请冷却。

邀请结果按请求 ID 幂等，刷新不能从拒绝重抽成答应。邀请不调用 LLM、不把角色瞬移进进行中的场景，也不因为关系友好就取消角色自己的职责、时段偏好和人数上限。

## 7. 旧异变卡与存档迁移

R36 的以下行为在 R39 被明确替换：

- 删除 `INCIDENT_IDS` 随机候选池和 `use_id` 哈希抽取；
- `fairy_seed_shower`、`wandering_magic_mist` 不再是异变卡固定候选；它们可以保留为普通登记插曲，但不承担七日异变卡语义；
- `clockwork_temporal_ripple` 回归怀表/时间痕迹自己的登记事件，不通过自定义异变卡抽取；
- 旧存档中已经存在的 `events.waiting_events` 必须继续可完成，不在迁移时静默删除；
- 旧存档中的异变卡数量原样保留；升级后下一次使用进入自定义表单；
- 新增 `anomaly_cycle` 时幂等补默认值，不根据旧等待事件伪造活动七日异变。

## 8. M2 内容边界

### 8.1 四设施

第一版仍包含：魔法温室、妖精花园、月见温泉、宴会广场。教程结束后，三个未建设设施的探索/规划入口同时可见；资源不足可以阻止施工，但一个设施的剧情不能作为另一个设施的全局前置。

三个后续设施采用统一但不互相复制的设施契约：

- 每座设施只有一个建设实体和一个正式状态；基础设施只是共同建筑壳，施工时从三种登记形态中选择一个作为初始形态，另外两种以后逐步取得；
- 同时允许查看、勘察和规划全部项目，但 `active_construction` 同时最多指向一个大型施工；
- 建设完成不会按时段自动生成金币、材料、灵感或其他资源；
- 当前形态只改变可选行动、访客权重、聊天场景事实和物品使用条件，不绑定预写剧情；
- 设施与当前七日异变正交：异变改变所有适用剧情的表现，不能跳过建设、解锁形态、修改成本或伪造设施损坏；
- 形态、活动和参与模式必须是本地登记 ID；模型可以描写结果，但不能创建新的正式形态或参与规则。

#### 8.1.1 共通建设与换型流程

建设前半段是确定性的本地选择器，不消耗模型调用：

```text
查看三个方案及明确差异
→ 检查当前是否已有大型施工
→ 检查资源与设施自身条件
→ 玩家确认方案
→ 本地事务扣除登记成本并推进一个时段
→ 将所选方案写为初始 current_form 和首个 unlocked_form
→ 本地直接完成施工结算
→ 开放该设施的首次使用入口
```

方案卡至少展示：内容倾向、容易出现的角色、主要互动、适合时段、对来访权重和道具场景的影响、建设成本。不能只使用“偏社交”“偏探索”之类没有可验证含义的标签，也不能让 LLM 临时生成方案差异、成本或解锁条件。

每种方案统一提供：一个自由输入框和三个登记快捷行动。自由输入只携带玩家文本与当前场景事实，默认没有正式风险；快捷行动只携带 `action_id`、显示名、场景意图和可选 `risk_tag`，不携带预写剧情、固定台词、奖励或结局。所有实际正文仍由 LLM 根据当前角色、设施、时间天气和活动异变生成。

三座设施的首版固定成本：

| 设施 | 首次建设 | 任意已取得形态换型 |
|---|---:|---:|
| 妖精花园 | 4 物资 | 2 物资 |
| 月见温泉 | 6 物资 | 2 物资 |
| 宴会广场 | 5 物资 | 2 物资 |

三种初始方案在同一设施内使用相同建设成本，避免便宜方案成为隐性最优解。后续设施建设和换型都不消耗灵感。

另外两个方案使用“活跃熟悉度 + 日历兜底”双轨解锁，满足任一路径即提交，且同一方案只能解锁一次：

- 在该设施完成跨 2 个不同标准时段的有效聊天后，开放第二方案选择；
- 完成跨 4 个不同标准时段的有效聊天后，解锁最后一个方案；
- 同一标准时段的多轮聊天只计一次，刷新、重试、Swipe 和失败回复不计；
- 从首个方案施工结算、设施正式投入使用的绝对时段开始计时；不等待首次聊天或首次换型；
- 经过 12 个标准时段仍未取得第二方案时，开放一次本地第二方案选择；玩家可以暂不选择，不阻断设施日常；
- 经过 24 个标准时段仍未全部取得时，自动把两个剩余方案全部加入 `unlocked_forms`，并清除未处理的第二方案选择；
- 三座设施分别计时，某座设施的聊天和日历不能替另一座设施解锁方案；
- 设施 `damaged` / `abnormal` 不暂停熟悉度或兜底计时，但修复前不能把已取得方案装修为 `current_form`；
- 睡觉、长途行动等一次跨越多个时段时，运行时逐一执行中间边界的解锁结算，并在行动结束后的安全时点合并显示通知；
- 解锁由本地时间与设施状态结算，不调用 LLM，也不要求固定剧情。

换型属于轻量装修而不是再次建设：

```text
选择已取得形态
→ 检查没有进行中的活动
→ 如有访客，玩家确认后结束本次停留并清理在场状态
→ 本地预留少量材料和一个时段
→ 代码从合法候选组中做确定性 roll，并固定 selected_character_id 或无人
→ 调用 LLM，投影目标形态、代码选定角色、当前场景事实与当前异变
→ 剧情成功结算后切换 current_form、扣除预留并推进时间
→ 失败或取消时回滚预留，不改变 current_form
```

装修剧情可以引出目标形态对应的角色，但候选资格、时段、当前事务、确定性随机和最终角色 ID 全部由代码决定。第一次启用方案时，代码选中的陌生角色可以在剧情成功后形成正式初遇；如果已认识，则作为装修拜访。重复换回同一形态只使用简短装修过渡，不重复首次初遇，也不得因为 LLM 自由发挥把未抽中的角色加入认识或来访状态。

设施不维护固定日常剧情、固定装修台词或固定相遇故事。每次真实剧情调用只提供本轮所需的最小事实：当前设施与形态、玩家选择的行动、代码选定角色、实际在场角色、当前时间天气，以及活动中的完整异变背景。LLM 在这些事实内自由生成正文；没有活动异变时不投影空白异变模板。

聊天后的时间由额外变量模型通过现有 MVU 时间字段提出更新。普通聊天只允许保持当前时间或前进一个标准时段；只有睡觉、长途行动等由玩家明确发起的登记长行动可以跨越多个时段。MVU 没有返回时间更新时保持当前时间。运行时只接受登记日期/时段语义和合法的向前变化，再以接受后的时间驱动来访、离场、邀请、异变剩余时长和其他调度；空回复、失败生成、Swipe 未确认版本或非法时间值不得推进正式时间。

代码在装修事务开始时使用聊天、设施、目标形态和事务 ID 形成稳定种子，从合法角色候选组中 roll 一次，并把结果固化到事务。刷新、生成重试和 Swipe 复用同一结果；玩家取消整次装修后 `pending_refit` 清理，下一次新建事务才允许重新抽取。

设施受损或异常继续使用登记的结构状况 ID，由代码决定是否触发、正式状态和允许结算；LLM 只依据该状况自由生成原因、过程和现场表现。结构状况不是预写剧情，不能被模型改成另一个状态、奖励或修复成本。

只有登记为 `experiment` 或 `challenge` 的快捷行动进行结构风险 roll。roll 在剧情事务开始时由稳定种子决定，基础触发率为 10%；每个形态的第一次行动分别受保护，触发后写入该设施 28 标准时段的风险冷却。自由输入、普通闲聊、未登记风险的快捷行动、刷新、重试和 Swipe 均不能额外触发风险或重抽结果。

首版风险标签固定为：

| 形态 | `experiment` | `challenge` |
|---|---|---|
| 四季花境 | 无 | 无 |
| 妖精游乐庭 | 无 | 发起妖精竞赛 |
| 冰露迷宫 | 进行冰冻实验 | 发起符卡挑战 |
| 露天月见汤 | 无 | 无 |
| 静水观测池 | 观察魔力、调查时间痕迹、映照当前异变 | 无 |
| 雾隐汤屋 | 无 | 无 |
| 灯火夜市 | 无 | 无 |
| 鬼之大宴台 | 无 | 无 |
| 符卡演武场 | 无 | 安排切磋、举办符卡展示 |

风险命中后，代码使用第二个稳定结果按 70% `abnormal`、30% `damaged` 选择严重度，再从当前行动允许的结构状况 ID 中选择具体状况。所有结果随行动事务锁定，LLM 不能改变严重度或重新抽取。

风险触发时，代码从当前行动允许的结构状况中确定 `abnormal` 或 `damaged` 及对应状况 ID，再让 LLM 生成正文。`abnormal` 的解决入口不消耗物资，预留一个时段并调用一次调查剧情；`damaged` 的解决入口预留 2 物资和一个时段并调用一次修复剧情。只有完整剧情与结构回执成功后才清除状态并提交时间/成本；失败、取消或重试不会扣费或推进。

设施始终可以进入；时段只控制登记互动，例如月见、夜市或夜间观测。没有登记事件时不产生随机损坏、耐久衰减或维护任务。登记事件造成的 `damaged` / `abnormal` 状态必须同时定义修复入口、成本、写入者和失败恢复；自定义异变文本永远不能直接生成这些状态。

候选状态只描述正式状态，不记录装修 prose：

```text
facility
├─ status: locked | planned | under_construction | operational | damaged | abnormal
├─ current_form: null | registered_form_id
├─ unlocked_forms: registered_form_id[]
├─ familiarity_count: 0..4
├─ last_counted_period_serial: null | integer
├─ first_form_operational_at: null | period_serial
├─ second_form_due_at: null | period_serial
├─ all_forms_due_at: null | period_serial
├─ pending_form_choice: false | true
├─ first_use_completed_forms: registered_form_id[]
├─ risk_cooldown_until: null | period_serial
├─ pending_refit: null | { transaction_id, target_form, reserved_cost, started_at }
└─ pending_recovery: null | { transaction_id, condition_id, reserved_cost, started_at }

garden_projects.active_construction: null | registered_facility_id
```

具体字段命名在对应检查点按现有 Schema 定型，但必须满足：唯一大型施工、登记 ID、换型原子结算、失败可恢复、旧存档幂等补默认值，以及模型不能写资源、正式形态和设施状态。

#### 8.1.2 会话与活动生命周期

月见温泉每次进入时创建本次会话上下文并使用玩家确认的参与模式：

- `public` 立即开始，允许既有来访调度在普通 3 人上限内安排已认识角色；
- `invite_only` 只把本次已经接受邀请的角色加入会话，改约和拒绝者不占位；
- `alone` 强制阻止新访客，开始前若现场有人必须先确认并在安全时点结束其停留；
- 玩家离开温泉、点击结束或正式时间进入下一标准时段时，会话关闭并清理临时参与约束。

宴会创建器使用本地登记活动类型、参与模式、邀请名单和开始时间。开始时间只能是当前时段或未来 4 个标准时段之一：

```text
玩家创建宴会计划
→ 本地校验形态、模式、人数和开始时间
→ 对邀请名单执行确定性接受 / 改约 / 拒绝
→ 到达开始时点
→ 邀请制只提交已接受者；公开活动再按来访调度补充合法角色
→ 活动开始，最多 6 名访客
→ 同一时段允许多轮自由聊天
→ 玩家主动结束，或接受的 MVU 时间首次进入下一时段
→ 活动在安全时点关闭并处理离场
```

宴会的最大时长是一个标准时段，不按聊天轮数强制结束；只要正式时间保持不变，可以继续交流。活动结束后必须恢复普通 3 人上限，超出者按已锁定的离场顺序在安全时点离开，不能留下幽灵在场记录。

候选活动状态：

```text
garden_activities
├─ scheduled_banquet: null | {
│    uid, facility_id, form_id, activity_id, participation_mode,
│    invited_character_ids, accepted_character_ids,
│    start_period_serial, status: scheduled | active | closing
│  }
└─ moon_spring_session: null | {
     uid, form_id, participation_mode, accepted_character_ids,
     started_period_serial
   }
```

`garden_activities` 是温泉会话与宴会活动的唯一事实源；设施对象不再重复保存 `active_activity`。活动 UID、开始时点、参与模式、邀请结果和生命周期由本地事务拥有；模型只读取活动事实并生成正文，不能延长活动、改变模式或增加角色。

#### 8.1.3 妖精花园

定位是不可完全控制的自然游乐场，强调妖精生态、季节变化、挑战、恶作剧与琪露诺相关互动。建成后所选初始形态默认开放，已认识角色可按调度规则随机来访；普通同时访客上限仍为 3。

三种登记形态：

| 形态 | 三个快捷行动意图 | 装修角色候选组 | 参与模式 |
|---|---|---|---|
| 四季花境 | 观察季节变化、整理花境、研究天气痕迹 | 琪露诺、爱丽丝、灵梦 | 固定公开 |
| 妖精游乐庭 | 举办小游戏、加入恶作剧、发起妖精竞赛 | 琪露诺、魔理沙、灵梦 | 固定公开 |
| 冰露迷宫 | 探索迷宫、进行冰冻实验、发起符卡挑战 | 琪露诺、魔理沙、灵梦 | 固定公开 |

未认识的琪露诺是妖精花园设施代表，进入合法候选时使用双倍权重。

局部冻结只能影响设施或登记事件范围，不能把全局天气改写成降雪；七日异变活动时，上述全部剧情仍携带异变投影。

#### 8.1.4 月见温泉

定位是低人数、夜间倾向、可控制私密度的休息与观测空间。设施始终可以进入，但具体互动可按时段开放；玩家每次进入前选择 `public`、`invite_only` 或 `alone`，该选择只约束本次停留和来访调度，不成为永久设置。

三种登记形态：

| 形态 | 三个快捷行动意图 | 装修角色候选组 | 默认参与模式 |
|---|---|---|---|
| 露天月见汤 | 泡汤闲谈、赏月、观察夜间天气 | 灵梦、魔理沙、爱丽丝、荷取 | 公开 |
| 静水观测池 | 观察魔力、调查时间痕迹、映照当前异变 | 咲夜、灵梦、魔理沙、荷取 | 仅邀请 |
| 雾隐汤屋 | 独处放松、邀请私下交谈、使用随身道具 | 不随机抽取；只使用玩家邀请且已接受的角色 | 独处 |

未认识的咲夜只在静水观测池满足正式接触条件时作为设施代表使用双倍权重；选择 `alone` 时所有形态强制不抽角色。

月见温泉不提供体力、好感或数值恢复，也不因建成自动解锁陌生角色；只有代码合法抽中的首次相遇可以建立认识事实。除此之外，它只能提高已经认识角色在符合人设与时段时的到访候选权重。

#### 8.1.5 宴会广场

定位是由玩家主动组织的多人活动场地。日常进入不自动生成宴会；玩家创建活动时选择登记活动类型、公开或邀请制、邀请名单与开始时段。宴会活动最多容纳 6 名访客，接受邀请与随机公开来访仍须遵守各自人设调度。

三种登记形态：

| 形态 | 三个快捷行动意图 | 装修角色候选组 | 默认活动模式 |
|---|---|---|---|
| 灯火夜市 | 筹办摊位、观看表演、逛夜市 | 米斯蒂娅、魔理沙、荷取 | 公开 |
| 鬼之大宴台 | 举办宴席、进行宴会游戏、多人自由交流 | 萃香、米斯蒂娅、灵梦 | 公开 |
| 符卡演武场 | 安排切磋、观看比赛、举办符卡展示 | 灵梦、魔理沙、琪露诺、萃香 | 仅邀请 |

未认识的米斯蒂娅和萃香在各自相关形态满足正式接触条件时作为设施代表使用双倍权重。

活动结束时由本地流程结算在场状态和离场候选；不得让模型自行留下超额角色、生成未登记商品，或引入饥饿、醉酒、烹饪等级等新的长期数值系统。

### 8.2 八名固定角色

固定角色仍是灵梦、魔理沙、琪露诺、爱丽丝、米斯蒂娅、萃香、荷取、咲夜。角色个人内容可以有自己的前后关系，但不得形成全局主线，也不得使用数值好感、等级或无关设施作为门票。

### 8.3 组合事件

组合事件可引用设施、在场角色、时段、天气、背包物品和当前异变，但只作为机会内容：

- 独立插曲不写 `completed_key_events`；
- 真正拥有下游结果的事件才使用受控完成态；
- 当前异变可以改变组合事件的表现，但不能让模型修改组合事件成本和本地结果；
- 没有满足组合条件时，玩家仍能进行设施日常和角色自由聊天。

## 10. 每轮统一字段链与门禁

每个新增字段必须完成：

```text
schema → initial state → field ledger → update rules → model projection
→ runtime reader → renderer → bridge writer → cleanup/migration → tests
```

每轮必须：

1. 从上一已验收检查点建立回归锚点；
2. 先更新契约、事件登记和正反测试，再改运行维护源；
3. 区分剧情正文、GAL、在场回执、额外变量开放字段和 bridge 独占字段；
4. 验证当前异变只影响叙事和登记允许的表现，不接管资源或关键结算；
5. 验证背包目录、物品数量、冷却和消费 ID 均由本地事务拥有；
6. 执行 TypeScript 检查、自动测试和生产 UI 构建；
7. 只有所有者明确要求时才更新未占用版本并打包；
8. 真实 Luker 使用精确新候选和新聊天验收，离线预览不能替代；
9. 失败时修维护源并创建新的未占用检查点，不覆盖历史产物。

## 11. 真实运行验收矩阵

### 教程毕业

- 新聊天走到首次选型后显示毕业说明；
- 不出现强制下一主线；
- 三个设施项目同时可见；
- 资源不足显示直接原因和获得方式。

### 七日异变

- 分别从清晨、白昼、黄昏和夜晚启用，均准确维持 28 个标准时段；
- 验收“全员互换身体”等全员规则在自由聊天、设施剧情和多人宴会中持续成立；
- 验收指定角色规则不扩散给其他角色；
- 每个新游戏日第一次剧情仅有简短灵梦调查提示；
- 中途购买或使用另一张卡被拒绝且不消费；
- 怀表、刷新、Swipe、空回复、停止生成和变量阶段失败不改变剩余时长；
- 最终收束失败可重试，成功后只归档一次。

### 背包与聊天用物

- 商店获得的消耗品与永久物品正确分类显示；
- 六件首批新增物品按 6 / 8 / 8 / 10 / 12 / 12 金币购买，使用范围与目录一致；第一版没有新增怀表之外的永久物品；
- 妖精、温泉、宴会道具分别随对应设施建成开放，应急修缮包随任一后续设施建成开放；未建成时不可伪造购买；
- 六件消耗品无每日库存，单项可堆叠到 99；购买和商品开放通知不创建聊天楼层或调用 LLM；
- 玩家不能输入目录外 item ID 创建物品；
- 聊天选择物品后可以取消，不提前消费；
- 完整回复和 MVU 结算后消耗一次；
- 消费成功后建立当前场景唯一的道具上下文容器，最多保存 3 种道具；后续多轮回复持续看到各自叙事状态，不重复扣除；
- 同一轮不能加入两件道具；同类道具再次使用会再扣一个并合并数量，不创建第四条或重复条目；
- LLM 可以把道具写成已打开、已分享或已用尽，但只能更新叙事摘要，不能恢复库存、创建数值效果或改变正式资源；
- 后来进入的角色只感知可观察的当前状态，不能自动得知缺席期间的使用过程与对话；
- 点击结束剧情后的最后一次 LLM 收尾仍携带道具；成功后才清除，失败或未采用 Swipe 保留上下文并可重试；
- 离开区域或开始另一段受控剧情前必须先完成收尾；温泉/宴会因时间推进自动结束时使用当前完整回复收尾，不额外调用 LLM；
- 普通场景道具在建设、装修、战斗、异变启用/调查/收束和其他固定结算中保持禁用；修缮包只能从损坏修复入口使用；
- 活动异变与最多三种场景道具可以同时正确投影，道具不能修改异变字段、期限或隐藏源头；
- 把道具送给当前角色会消费玩家库存并维持本场景事实，但不会创建角色永久库存、好感数值或强制关系结果；
- 应急修缮包可以替代 2 物资完成 `damaged` 修复，但不能跳过修复剧情、时间推进和成功回执；
- 永久怀表不删除，只更新冷却、次数和痕迹；
- 异变卡表单取消、校验失败、已有活动异变、源头生成失败或启用事务失败时不消费。

### 角色来访、邀请与离场

- 教程毕业后灵梦、魔理沙、爱丽丝和荷取具备合理来访资格，未认识角色不会随机出现；
- 同一聊天、同一日期和时段反复刷新，来访结果保持一致；
- 推进时段最多新增一名普通随机访客，无候选时允许无人到访；
- 战斗、固定剧情和自由聊天过程中不突然插入待到访角色；返回庭园后才显示本地通知和地图角色；
- 随机到访本身不创建 user/assistant 楼层，点击角色后才开始真实交流；
- 普通状态第 4 名访客被阻止，宴会状态第 4～6 名可以进入，第 7 名被阻止；
- 固定事件临时超限后，事件结束可以在安全时点恢复到普通上限；
- 角色在聊天、固定事件或异变收束中不会自动离场；事务结束后按原计划离开；
- 离场角色进入冷却，不能下一时段立刻随机折返；
- 邀请分别覆盖立即接受、改约和拒绝，刷新不改变结果，拒绝不产生幽灵在场记录；
- 活动异变不会从自由文本执行“提高某角色概率”或突破认识/人数边界；到场后的剧情仍必须遵守异变规则。

### 设施建设、换型与活动

- 三个设施的勘察入口同时可见，任一时刻只能存在一个大型施工；
- 每座设施的三个方案都在本地界面完整显示差异、成本、内容倾向、角色倾向和时段倾向，打开与确认过程不调用 LLM；
- 妖精花园、月见温泉和宴会广场分别只扣除 4、6、5 物资并推进一个时段；三者换型只扣 2 物资，不扣灵感；
- 首次施工选择的方案立即成为 `current_form` 和首个已取得形态；基础建筑壳不能作为第四个可切换形态出现；
- 施工确认只扣费一次、推进一个时段并直接建成，不生成施工正文、不残留多日等待任务；
- 资源不足、已有大型施工或设施条件不满足时拒绝开始，且不部分扣费；
- 已取得形态可以用少量材料和一个时段换型，不重新进入大型施工；
- 同一设施在第 2 个不同有效聊天时段开放第二方案选择，第 4 个时段补齐最后方案；同一时段复读与失败生成不能刷熟悉度；
- 即使完全不聊天，从首个方案施工完成起经过 12 时段也会开放第二方案选择，经过 24 时段保证三个方案齐备；三座设施的兜底计时互不串联；
- 第二方案待选择时不阻断日常；24 时段期限到达后自动补齐剩余方案并清理待选择状态；
- 受损或异常期间照常解锁，但拒绝换型；长行动跨越 12 / 24 时段期限时不打断正文，只在安全时点显示合并通知；
- 有活动时拒绝换型；有访客时必须二次确认并在安全时点完成离场，不能遗留幽灵在场记录；
- 装修调用只投影目标形态、代码已经 roll 的角色、当前场景事实和当前异变；LLM 不能改选角色，未抽中的陌生角色不能进入认识或来访状态；
- 装修角色严格来自当前形态的确认候选组；未认识的设施代表使用双倍权重，没有合法候选时允许无人出现；
- 月见温泉选择独处时 `selected_character_id` 必须为空；雾隐汤屋只有已经接受邀请的角色可以参与；
- 第一次启用方案可在成功剧情后提交正式初遇；重复换回只生成简短装修过渡，不重复初遇；
- 设施不依赖预写日常、装修或相遇剧情库；相同状态允许 LLM 生成不同正文，但正式角色、形态、资源和时间结果仍须满足结构约束；
- 装修成功只提交一次形态、材料和时间；取消、空回复、停止生成、刷新、Swipe 或变量阶段失败均可重试且不重复扣费；
- 白昼可以进入月见温泉，但夜间专属互动保持不可用并显示原因；宴会广场闲置时不会自动创建宴会；
- 长期推进不会随机产生耐久损耗；只有登记事件可以写入受损或异常，并存在对应修复入口；
- 七日异变会改变建设后、装修和设施互动的剧情表现，但不能改变方案成本、强制换型或创建正式损坏状态。
- 每种方案显示一个自由输入和三个确认的快捷行动；快捷行动只规定意图，重复选择可以生成不同正文，不能附带模型自创奖励；
- 妖精花园固定公开；温泉和宴会各形态正确带出默认参与模式，玩家修改只影响本次会话或活动；
- 只有确认表中的 `experiment` / `challenge` 快捷行动按稳定种子进行一次 10% 风险 roll；每个形态首次行动、自由输入、普通闲聊、冷却 28 时段内、刷新和 Swipe 均不重抽；
- 风险命中后的严重度固定由代码按 70% `abnormal` / 30% `damaged` 决定，LLM 不能把异常升级成损坏或反向降级；
- `abnormal` 调查成功只推进一个时段且不扣物资；`damaged` 修复成功只扣 2 物资并推进一个时段；失败或复读不重复扣费；
- 角色 roll 只在首次启用或换型事务存在；普通设施行动不能绕过来访调度凭空增加角色。
- 温泉公开、仅邀请、独处三种模式分别满足普通来访、已接受邀请白名单和零访客约束；离开或时间跨时段后会话状态清理；
- 宴会只能安排在当前或未来 4 时段，邀请结果在开始前固定；公开活动可补合法访客，邀请制不能混入随机角色；
- 宴会同一时段允许多轮聊天，时间一旦推进即在安全时点结束，6 人上限恢复为 3 且无幽灵在场记录；

### 聊天时间更新

- 普通聊天、设施聊天、角色相遇、装修和宴会完成后，由额外变量模型在 MVU 时间字段中表达实际经过的时间；
- 普通聊天每次最多前进一个标准时段，也允许保持当前时段；未返回时间字段视为不推进；
- 睡觉、长途行动等明确登记的长行动可以跨越多个时段，运行时按目标时间逐一处理跨越边界，而不是跳过中间的异变和调度检查；
- 合法更新提交后，来访、离场、邀请计划、每日异变提示和 28 时段异变到期统一使用新时间，不维护第二套聊天计时器；
- 非法日期/时段、倒退时间、生成失败、空回复和未采用的 Swipe 不改变正式时间；
- 活动异变期间每一次 LLM 剧情调用都能看到同一活动异变的完整当前背景，直到接受后的世界时间到达收束点；
- LLM 不得直接设置异变剩余时长、到期状态或归档结果，这些值只能由运行时根据已接受的世界时间派生。

## 12. 明确排除

- 不建立新的全局主线、章节等级或通关顺序；
- 不允许同时存在多个活动异变；
- 不允许主动结束或覆盖七日异变；
- 不允许玩家创建背包物品；
- 不允许模型或玩家文本直接创建来访计划、修改概率、突破人数上限或召唤未认识角色；
- 不让所有角色共享相同时间表、停留时长、拒绝话术或来访理由；
- 不让随机到访自动触发 LLM 过场或打断当前事务；
- 不执行玩家或模型文本中的 HTML、URL、脚本和未登记本地效果；
- 不加入数值好感、等级、装备、技能树、体力、税收或自动生产链；
- 不把灵梦写成每个异变场景都必须在场的旁白机器；
- 不因项目没有向开关，就新增题材分类或改变角色与在场信息边界。

## 13. 实施时仍需确认的数据

以下只属于单轮数据调优，不再改变本计划架构：

- 异变表单各文本字段的最终长度上限；
- 异变历史保留数量及摘要格式；
- 每日灵梦提示的目标字数；
- 八名角色的基础来访权重、停留范围、冷却范围和邀请改约窗口；
- 各时段“无人到访”的基础概率及宴会结束后的离场节奏；
- 首批本地到访/离场通知模板和角色地图素材覆盖范围；
- 首批消耗品的简短说明与本地购买反馈文案；
- 组合事件冷却与新战斗奖励；
- 各风险行动允许的结构状况 ID 与本地通知文案；
- 背包图标和设施美术素材范围。

这些数值在对应检查点实施前确认；不得借数据调优恢复随机异变池、叠加异变、玩家自建物品或全局主线门槛。
