## 1. 所有者方向确认（2026-07-27）

- 现有八人（灵梦、魔理沙、琪露诺、爱丽丝、米斯蒂娅、萃香、荷取、咲夜）都已有对应设施；本计划新增设施服务于**后续加入的新角色**，同时人设相符的老角色也要被同一设施吸引。
- 新设施与月见温泉同类：**没有后置主线、不做任何全局前置、完全沙盒自由**。
- 首批规划 **3 座**新设施。
- 新角色具体名单、素材制作与契约红线修订仍需所有者逐项确认（见 §9 开放问题）；本计划给出推荐配对与备选表。

## 2. 设计原则

1. **完全复用 M2 设施契约**（`r38-r45-m2-expansion-plan.md` §8.1）：一个建筑壳 + 三种可切换形态；建设/换型纯本地事务；无被动产出；形态只改变可用行动、来访权重、场景事实与道具使用条件；`experiment`/`challenge` 快捷行动 10% 结构风险 roll、70/30 严重度；熟悉度 2/4 时段 + 12/24 时段日历兜底解锁方案。不新造第二套设施协议。
2. **设施先行、角色后到（两期解耦）**：设施建成当天就对老角色完全可玩；新角色沿用「静水观测池引出咲夜」模式——作为设施代表进入装修 roll 候选组并享受双倍权重，初遇成功才建立认识事实、进入来访池。新角色素材未就位时，候选组只含老角色，设施不空转。
3. **吸引力走既有来访调度**：老角色被新设施吸引 = 更新 `visit-profiles.json` 的 `interest_tags` / `arrival_area_preferences`，不新增第二套权重系统；上限仍是普通 3 人、每时段最多 1 次随机到访。
4. **状态所有权不变**：`facility_runtime`、`garden_activities`、来访调度、初遇事实全部 bridge 独占；模型只叙事。新角色的在场回执、GAL 立绘、reaction 仍走白名单。
5. **一切新增 ID 均为本地登记 ID**；模型不能创造形态、参与模式、角色或道具。

## 3. 首批三座设施设计

主题选型逻辑：补上现有四设施未覆盖的玩法位——温室=经营主线、妖精花园=户外玩闹、月见温泉=私密休憩、宴会广场=多人活动；缺口是**安静室内（读书/研究）**、**季节性户外观赏（赏花）**、**信仰/祭典**。三座各锚定一名推荐新角色，且均有多名老角色人设相符。

成本沿用 M2 区间（4–6 物资建设 / 2 物资换型），三形态同价。

### 4.2 每名新角色的完整接入清单

以下每项都是硬性交付，缺一不可视为「角色已加入」：

1. **契约修订**（见 §7，需所有者逐条授权）；
2. **像素素材（占位先行，2026-07-27 所有者裁定）**：首批接入使用程序生成的占位图集（§4.4），**不等待真素材，也不再以灵梦 V2 试点为前置**。真素材后补时按 `project/pixel-character-animation-v2-plan.md` 的 32 帧合同制作（V2 单图集约 1.4MB，不再生产 V1 双图），走 `asset-manifest.json` 统一评审制，默认闭嘴/中性/轻微微笑；
3. **世界书条目**：`src/lorebook/characters/<id>.xml`（对齐现有八人 1.6–1.8KB 规格），并核对打包器世界书条目数与路由（`[mvu_plot]` 阶段）；
4. **来访档案**：`visit-profiles.json` 新 profile（eligibility 指向初遇完成事实、时段权重、兴趣标签、到访区、人数偏好、停留/冷却、邀请三权重、base_weight）；
5. **初遇事件登记**：沿用装修 roll 双倍权重 → 初遇成功写认识事实的既有链路（参照 `visitor-rules.ts` 中 cirno/sakuya 的 eligibility 模式），不新造事件类型；

7. **测试**：来访 eligibility、初遇幂等、装修 roll 稳定种子、presence 白名单各加断言；
8. **字段台账**：`field-ledger.md` 补认识事实字段行。

### 4.3 体积预算

- 当前 r54 检查点 36.2MB。占位图集每角色 ≤30KB，接入期体积可忽略。
- 真素材后补时：每名新角色 V2 图集约 1.2–1.5MB + 世界书 ~2KB；三人合计约 **+4–4.5MB**，计入替换轮而非接入轮。
- 若叠加美化 F1 细腻立绘线，新角色立绘同样计入该线 ≤6MB 预算内单列核算。
- 红线：任何一轮打包前 dry-run 体积超过 45MB 时暂停，先做素材压缩复核再继续。

### 4.4 占位素材规格（2026-07-27 所有者裁定：占位先行、素材后补）

沿用 `project/r49-placeholder-asset-spec.md` 的占位纪律——占位现在长什么样、真素材要满足什么、拿到后改哪里，逐项登记逐项勾销：

- **地图小人占位**：每名新角色生成一张最小占位图集——角色主题色像素剪影小人（暂定：妖梦=银绿、帕秋莉=紫、早苗=青绿），与现有角色相同画布尺寸、脚底基线与像素密度；idle 单帧，四方向复用同帧。占位图集直接按 V2 版式（9×4 网格）排布并复制到对应格位，真素材到位后**原位替换、clip 描述表零改动**。
- **GAL 立绘占位**：复用占位剪影进像素取景框（美化方案 §2.6 过渡态本身即回退方案）；reaction 白名单照常注册，全部标签指向同一占位帧。
- **登记方式**：`asset-manifest.json` 以 `status: placeholder` 登记；`character-sprite-registry.ts` 正常注册。走真实素材管线而非代码特判，保证换真素材时零链路改动、并顺带验证 V2 图集加载链。

## 5. 工程改造：设施底座泛化（新内容的前置）

现状审计发现三设施在代码里约 7 处硬编码，且温泉会话是专字段。新增第 4+ 座设施前先做一次数据驱动泛化，否则每座新设施都要横切改动全部硬编码点：

| 硬编码点 | 现状 | 泛化目标 |
|---|---|---|
| `state-migrations.ts:118` | `['fairy_garden','moon_spring','banquet_plaza']` 写死 | 从 `facilities/catalog.json` 派生迁移清单 |
| `app.ts:773` 及温泉/宴会入口 | 三设施 ID 数组 + 每设施专用入口分支 | 目标菜单按 catalog 生成；会话/活动入口按设施能力标志（`session_capable` / `event_capable`）派生 |
| `garden-spatial.ts` `REFITTABLE_FACILITY_AREAS` | 三元组写死 | 由 catalog 的 `facility_id → area_id` 派生 |
| `inventory-rules.ts` 解锁条件 | `facility_<id>_built` 逐个 case | 通用 `facility_*_built` 模式匹配 + `any_followup_facility_built` 保持 |
| `test-tools.ts` 形态表/快进按钮 | 三设施形态写死 | 从 catalog 派生；新设施自动获得验收快进 |
| `garden_activities.moon_spring_session` | 温泉专字段 | 泛化为按 `facility_id` 索引的 `facility_session`（书斋「仅邀请/独处」与枯山水复用同一生命周期：进入选模式→立即开始→离开/结束/跨时段关闭）。旧字段迁移映射，旧存档幂等，`types.ts`/schema/字段台账同步 |
| `visitor-rules.ts` eligibility | 逐角色 switch | 保持显式（认识事实字段名不规则，强行泛化损失校验），仅追加新角色分支 |

泛化必须零行为变化：泛化轮的门禁标准是全部既有测试不改断言直接通过 + 三设施回归用例（建设/换型/会话/宴会/风险/道具解锁）逐项复验。
