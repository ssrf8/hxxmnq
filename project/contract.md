# 稳定契约

## R28：在场角色快照同步

- `presence_snapshot` 是地图小人、模型现场叙事与后续互动的唯一事实来源。
- 每一次由庭院 UI 发起的 LLM 请求都必须注入在场角色 ID、姓名、区域、动作、朝向及完整不在场名单。
- 正文只允许把快照中的在场角色写成现场人物；不在场角色可以被提及，但不得在当前场景发言、行动或被地图渲染。
- 角色抵达、离场或换区时，assistant 必须在正文之后输出一次 `GensokyoPresence` 回执；回执不是正文、不是 `UpdateVariable`，也不显示在 GAL 正文中。
- 本地只接受已登记角色、`front/back/left/right` 朝向和受控字段；有效回执原子更新 `presence_snapshot` 并清除离场视图。
- 没有现场变化时不得输出回执；叙事变化而没有回执时不做自然语言猜测，记录为模型协议违例。

## R29：金币副本与事件责任

- 温室主线事件必须登记事件类型、触发行动、最大有效回合、最小投影、剧情骨架、禁止偏离、固定结尾与失败恢复；正式状态仍只由本地结算器写入。
- `resources.coins` 的唯一写入者是本地副本奖励事务和后续本地商店事务；旧存档缺失时幂等迁移补为 `0`。
- 可重复副本仅接受三个登记 `config_id` 与本地 BattleEngine 结果；全过程不得创建 user/assistant 楼层，也不允许叙事替代结算。
- clean/narrow/loss 分别只奖励 12/8/3 金币并推进一个时段；取消不写状态。每个副本 `settlement_id` 最多奖励和推进一次，`last_run` 同时保留开战与结算日期/时段。
- 妖花核心完成后才可解锁副本；副本不提供技能树、装备、体力或永久战斗成长。

## R30：灵梦小店

- 小店只读取本地 `src/shop/catalog.json` 与预写 `dialogues.json`；不得执行其中之外的商品、价格、HTML、URL、脚本或模型临时效果。
- 普通物资购买为零 LLM 本地原子事务：校验解锁、价格、余额、物资上限与购买 ID，再扣金币、加物资、复读并记录幂等 ID。
- 小店解锁与副本解锁同由妖花核心本地结算拥有；旧存档迁移必须幂等补齐。

## 必须成立

- `stat_data` 是唯一正式游戏状态源。
- 数据库只做可选长期归档与检索。
- 玩家只在符卡战中显示，不出现在庭园地图。
- 第一版固定角色为灵梦、魔理沙、琪露诺、爱丽丝、米斯蒂娅、萃香、荷取、咲夜。
- 角色交互允许跨越多轮消息，并以显式结束完成结算。
- 玩家正常游玩时只看见一个常驻游戏壳；该壳不绑定真实消息 0 楼，后台真实消息只做视觉隐藏。
- GAL 剧情必须镜像真实 SillyTavern user/assistant 楼层；自定义输入、建议回应和结束聊天均走正常消息事务。
- 角色和设施的入口操作由本地受控配置与当前 MVU 状态计算，LLM 不得临时创造可执行按钮或绕过前置条件。
- 一次 assistant 回复最多渲染 24 个庭园正文协议演出片段；旧版 `scene.v1` 兼容投影最多 6 段。片段全部播放后才允许玩家提交下一次回应。
- 结束聊天必须先完成一次真实收尾生成和幂等 MVU 结算；完成一次交互回合不等于必然推进时段。
- 角色立绘由本地素材注册表解析；LLM 只可选择白名单角色、反应和姿态标签。
- 变量更新只使用目标 MVU 支持的 JSONPatch `add`、`replace`、`remove`。
- 灵梦结界检查、主屋维修和 r19/r20 温室关键链由本地事件结算器拥有正式状态写权限；LLM 负责叙事，本地只接受经登记的结算结果。
- 自由文本和没有匹配 `event_id` 的回复不得推进本地托管事件；回复完成后必须恢复模型误写的托管字段。
- 本地托管结算必须写入精确 assistant 楼层并复读验证；失败进入可重试事务，不得预扣或部分推进。
- 已登记的庭园主线事件只执行一次真实剧情请求；本地结算器根据登记的 `action_id + event_id`、持续交流的真实楼层轮数或已验证的 `battle.current` 在完整 assistant 楼层后直接写入白名单结果，不发起第二次模型解析。任一前置或复读失败都不得落盘部分结算；固定推进剧情不开放续聊输入。
- `greenhouse_multiturn_conversation` 是固定两轮的例外：初始回复为第 1 轮，玩家至多补充一次；第 2 个真实 assistant 楼层落盘后本地自动结算、隐藏输入并返回庭园。研究正文每轮目标不超过约 300 汉字，玩家补充限制为 120 字；它不能提前激活妖花核心。
- 庭园主动行动正文必须放在最后一个 `【庭园正文开始】` 与其后的第一个 `【庭园正文结束】` 之间；协议内部仅允许 `narration` 与带登记角色 ID 的 `dialogue`，协议外文本绝不进入 GAL。
- 推进关键状态的固定剧情必须有预登记剧情骨架和固定结尾，尽量在一次、最多两次 LLM 生成内完成；结尾后不显示选项或输入框，并返回庭院。只有自由交流会话可接受后续玩家输入。
- 妖花战结果只允许本地 bridge 在白名单、范围和事件前置校验后写入 `battle.current`；模型只能消费该字段，正文中的第二份结果无效。
- 战斗结算以 `settlement_id` 幂等；四种允许结果都只留下移动锚点线索，r20 不创建正式稳定锚点。
- 新开场只允许 bridge 在首个 assistant 楼层执行一次确定性 MVU 写入；必须复读成功后进入庭院，不得调用 LLM 初始化资料。
- UI 故障时必须恢复原生聊天。
- 游戏壳心跳丢失、脚本卸载、切换角色卡或进入维护模式时，必须恢复被视觉隐藏的原生楼层和输入区。
- 角色像素素材默认闭嘴、中性或轻微微笑。

## 禁止成立

- 大妖精不得作为第一版固定角色。
- 不得把玩家作为庭园地图行走角色。
- 不得使用 `is_hidden` 改变真实消息上下文。
- 不得把 GAL 片段、当前立绘、点击进度或输入草稿写成第二份正式剧情状态。
- 不得将模型输出作为 HTML 插入页面，不得执行模型给出的图片路径、URL、脚本或未登记操作。
- UI 和数据库不得绕过 MVU 成为第二事实源。
- 不得让新开场依赖 LLM 输出玩家资料、庭园名或初始化变量块。
- 不得从聊天正文、玩家 JSON 或模型输出伪造副本结果、金币余额或奖励 ID。
- 不得执行 LLM 生成的代码、URL、HTML 或未校验战斗配置。
- 不得从模型正文、玩家声称的 JSON 或任意 HTML 覆盖 `battle.current`，不得重复消费已在 `battle.settled_ids` 中的结果。
- 不得在未授权时打包、发布或覆盖角色卡成品。
