## 3. 根因拆分

### P0-A：本地事务结算依赖易丢失的内存上下文

`src/ui/bridge.ts` 的消息发送流程把操作前状态保存在 `pendingOwnershipBefore` 中，等待助手回复和变量阶段结束后，再由 `preserveLocalOwnership()` 恢复代码所有权字段，并显式调用 `markSettlementSucceeded()`。

问题是：

- 该上下文只存在于当前 iframe 内存中；iframe 重载、切楼、运行时异常都可能令其丢失。
- `sendUserMessage()` 的异常分支只记录错误并重新抛出，没有保证调用 `markSettlementFailed()`，事务可能永久停在 `settling`。
- 异变激活/最终结算请求没有持久化的操作类型、操作 ID 和必要参数，重放器无法从聊天楼层重建本地动作。
- `message-transaction.ts` 在找到助手楼层后会继续保持 `settling`，必须等待显式成功标记；因此“原生楼层已经回复”本身不会解锁。

### P0-B：异变状态仍被 LLM 往返包裹

异变卡激活属于确定性的游戏状态操作，本应由代码立即校验、消耗卡片并写入 active 异变；LLM 只负责随后生成剧情文本。当前流程先进入 LLM 消息事务，使核心状态提交受到模型回复、MVU 空补丁、iframe 生命周期影响。

这与既定设计不符，需在后续修复中一并调整，不能只给遮罩加超时。

### P1-A：遮罩与 GAL 文字框层级冲突

`src/ui/styles.css` 中生成遮罩的层级为 `z-index: 3`，GAL 文字框为 `z-index: 4`。同时文字框规则显式设置 `display: grid`，覆盖了 HTML `hidden` 属性的默认隐藏行为，所以遮罩显示时文字框仍在其上方并可点击。

### P1-B：“本次对话记录”只认识角色交互场景

`src/ui/app.ts` 的会话记录依赖 `activeTarget`，并通过前置用户楼层里的 `GensokyoAction` 查找会话起点。异变激活和异变结算没有角色目标，也没有该标记，因此当前实现必然返回空记录。

### P1-C：重新生成绕过事务协调器

同步遮罩期间，“重新生成”和右滑仍可操作。重新生成直接调用宿主重生成接口，没有替换或完成旧事务；新助手楼层虽然生成成功，旧事务仍是 `settling`，所以遮罩不会消失。

### 派生现象：结束聊天不可点击

这不是独立根因。事务长时间停在 `settling` 后，界面持续处于 generating 状态，`setGenerating(true)` 会禁用结束聊天按钮。

## 4. 修复任务

### P0-1：把异变卡激活改为代码原子提交

1. 点击使用后，由代码完成卡片存在性、数量和当前异变状态校验。
2. 在一次本地事务中完成：扣除卡片、创建异变实例、写入隐藏源头/种子、设置七日周期、清空 pending、写入 active。
3. 为操作生成唯一 `operationId`，重复执行相同 ID 必须幂等。
4. 状态提交成功后再请求 LLM 生成开场剧情；LLM 失败不得回滚已激活异变。
5. LLM 不得决定是否激活、扣卡数量、持续天数或核心状态转移。

### P0-2：建立可持久恢复的消息事务

1. 为所有系统场景写入统一的持久操作标记，至少包括：
   - `operationId`
   - `sceneId`
   - `operationType`（如 `anomaly_activation`、`anomaly_resolution`）
   - `phase`
   - 本地结算所需的最小参数
2. 标记必须落在聊天楼层可读的 `extra` 或等价持久字段中，不能只放 iframe 内存。
3. 初始化、切楼和 MESSAGE_RECEIVED 时均可根据标记恢复未完成事务。
4. 本地结算函数必须幂等；同一 `operationId` 重放多次，只能产生一次状态变化。
5. 所有异常出口都必须进入明确的 `failed/retryable` 状态，禁止遗留无期限 `settling`。
6. 区分“等待助手”“等待 MVU”“执行本地结算”三种状态，并为界面提供准确原因。

### P0-3：重做最终异变结算的所有权边界

1. 点击“结束剧情”时，由代码锁定本次结算意图并持久化操作标记。
2. 当前轮异变影响继续生效，直到这次结束剧情回复完成，符合既定玩法。
3. 助手回复完成后，由代码执行最终状态转移：结束 active、写入归档/冷却、清理结算标记。
4. 即使 MVU 返回空补丁，也必须完成代码结算。
5. 若回复完成后本地结算失败，显示“重试本地结算”，不得重新请求 LLM。
6. 页面重载后应依据持久操作标记继续完成结算，不再依赖旧 iframe 的 `pendingOwnershipBefore`。

### P1-1：修复遮罩和输入锁

1. 增加明确的 `[hidden] { display: none !important; }` 规则，或移除会覆盖 hidden 的显示声明。
2. 生成/结算遮罩层级必须高于全部可交互 GAL 控件，并拦截其下方 pointer events。
3. `settling` 期间禁用重新生成、左右滑、发送、道具、建议回复和结束聊天。
4. “本次对话记录”可保持只读开放，但不得触发会改变事务的动作。
5. 失败状态只开放安全操作：重试本地结算、查看记录、返回；是否允许重新请求模型由明确状态决定。

### P1-2：统一系统场景的会话归档

1. 用 `sceneId/sessionId` 作为会话边界，不再只依赖 `activeTarget + GensokyoAction`。
2. 角色聊天、设施事件、异变激活、异变结算都写入相同结构的场景标记。
3. “本次对话记录”按 sceneId 聚合用户和助手楼层。
4. 即使没有角色目标，异变剧情仍应正常显示标题、阶段和完整消息。

### P1-3：防止楼层状态回退

1. 明确宿主楼层变量、运行时变量、代码所有权字段的合并顺序。
2. 写入新助手楼层前，不得把旧 pending 快照覆盖到已进入 resolving 的状态。
3. 最新助手楼层必须携带结算后的权威状态，刷新和切楼后结果一致。
4. 对旧聊天提供一次性兼容恢复：检测“助手已回复 + 事务仍 settling + 可证明的操作意图”，执行幂等补结算；证据不足时进入可见的人工重试状态，不静默猜测。

## 8. 追加缺陷：设施邻近封锁与宴会到期触发

> 2026-07-26 追加；本节已获准进入修复实施。

### 8.1 三设施换型被任意在场角色全局封锁

聊天存档中的权威在场快照为：灵梦位于 `central_courtyard`。原实现只检查
`present_character_ids.length > 0`，因此庭园中只要存在任何角色，妖精花园、月见温泉和宴会广场全部无法换型。

修正规则：

1. 地图渲染与业务判断共用同一份区域坐标。
2. 每名在场角色按当前位置计算距离最近的一个后续设施。
3. 角色只封锁该最近设施的换型；其他设施不受影响。
4. 角色移动后立即按新位置重算，不保存第二份“封锁设施”状态。
5. 中央庭院按现有地图坐标最近宴会广场，因此灵梦停留中央庭院时只阻止宴会广场换型。

验收：

- [ ] 灵梦在中央庭院：宴会广场不可换型，妖精花园和月见温泉可换型。
- [ ] 灵梦移动到妖精花园：只禁止妖精花园换型。
- [ ] 多名角色分别靠近不同设施：只封锁各自最近设施。
- [ ] 角色离场或移动后，不残留旧封锁。

### 8.2 排期宴会跨过开始时段却未触发

聊天文件显示两次副本结算已把时间从第 1 日清晨推进到第 1 日黄昏，`battle.run_count=2`；但副本结算入口只推进时间和发奖，没有调用统一的 M2 时间派生协调器。因此设施解锁、异变、访客及宴会到期检查没有随副本时间结算执行。

修正规则：

1. 副本纯结算仍只负责可信结果、奖励和推进一个标准时段。
2. bridge 写回前必须以结算前后状态调用 `reconcileM2Runtime()`。
3. 到达 `scheduled_banquet.start_period_serial` 时，在同一安全结算点把 scheduled 原子转为 active。
4. 离线预览桥与真实运行桥必须采用相同协调流程。

验收：

- [ ] 安排两时段后开始的公开宴会，第一次副本结算后仍为 scheduled。
- [ ] 第二次副本结算到达目标时段后，scheduled 清空且 banquet 变为 active。
- [ ] 宴会只启动一次，不重复生成活动 UID。
- [ ] 同一协调流程继续正确处理设施解锁、异变到期和访客调度。
