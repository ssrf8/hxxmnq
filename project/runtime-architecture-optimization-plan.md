# 运行时架构优化计划：事件精确投影、状态护栏与镜头审计

> 计划状态：O0～O3 已于 2026-07-25 完成维护源实施与离线门禁；O5 已随 R35 完成维护源与离线门禁；O4 已完成只读探测但等待有角色上下文的真实运行证据
>
> 编制日期：2026-07-25
>
> 当前已验收运行基线：`0.2.0-r32-extra-model-binding`；当前维护源：R34 后、R35 前的架构基线
>
> 排期关系：本计划不占用新的检查点编号；R34 成品保持冻结，优化结果最早由新的 R35 候选吸收。

## 1. 结论

本轮优化不适合重写现有系统。项目已经形成了可靠的三层所有权：

- `stat_data` 保存正式游戏状态；
- bridge 负责资源、事件、在场、UID、会话和幂等结算；
- 主剧情模型与额外变量模型只获得受控输入，并分别负责叙事和开放语义字段。

当前真正需要收口的是“配置已经数据化，但运行时仍有重复硬编码和过量投影”。推荐依次完成：

1. 统一事件登记表的数据契约；
2. 只向模型投影当前事件所需的最小信息；
3. 增加时间单调性和区域白名单护栏；
4. 在真实 Luker 中审计角色档案是否被意外激活；
5. 三种温室方案齐备后，再实现显式选择回执与路线锁；
6. 最后补充证据楼层和“镜头影子审计”。

参考卡 v0.43 中值得采用的是“显式路由、时间单调、角色状态分层”的思想，不复制它按日期自动推进、由模型判断主事件完成或每轮重算正式在场的做法。

## 2. 已确认的问题与证据

### 2.1 整份事件配置被打入关键词世界书

`scripts/package-checkpoint.mjs` 当前把 `src/lorebook/events/greenhouse-vertical-slice.json` 作为一个整体世界书条目打包，并以温室相关通用词触发。结果是普通温室对话也可能把多条未来事件、大纲、固定结局和禁止事项一起送入上下文。

这与项目契约中的“只投影当前事件最小信息”不一致，也是本计划的最高优先级问题。

### 2.2 事件登记表还不是唯一事实源

- `src/ui/event-registry.ts` 对 `allowed_results` 的类型声明与 JSON 实际形态不一致；
- loader 只检查少数字段后直接断言完整类型；
- `src/ui/event-settlement.ts` 又维护了一份允许结果和默认结果；
- `src/ui/target-actions.ts` 仍硬编码部分叙事意图；
- `narrative_outline`、`required_beats`、`forbidden_deviations`、`projection_keys` 等配置尚未形成统一运行时消费链。

这会使新增事件时必须同步修改多个位置，容易出现“配置写了、运行时没用”或“运行时允许了、配置没登记”的漂移。

### 2.3 在场快照可靠，但输入验证仍有缺口

`presence_snapshot` 目前是持久化权威状态，固定事件通过登记表迁移，自由剧情通过 `GensokyoPresence` 回执迁移。这一设计应保留。

现有回执对角色 ID 和朝向做了限制，但 `area_id` 尚未绑定登记区域白名单；主剧情漏写必要离场回执时，也没有只读诊断信号。后者不能通过自然语言猜测并直接改状态。

### 2.4 角色档案可能被非预期关键词激活

当前叙事上下文会列出不在场角色姓名，完整 `stat_data` 也包含角色名，而角色世界书以姓名作为关键词。是否会递归激活角色档案取决于实际 SillyTavern / Tavern Helper / 世界书扫描设置，不能仅凭静态代码定论。

因此本项必须先做真实运行审计，再决定是否需要显式角色投影器；禁止在证据不足时直接重构世界书。

### 2.5 时间字段合法，但缺少单调性

Schema 能保证日期和时段格式正确，却不能阻止额外变量模型把时间写回更早的日期或时段。应由本地护栏拒绝倒退，而不是依赖提示词劝阻。

## 3. 优化边界

### 3.1 必须保持的所有权

| 数据 | 唯一写入者 | 模型权限 |
|---|---|---|
| 资源、设施、商店、事件完成、结算 ID | bridge / 本地规则 | 只读 |
| `presence_snapshot` | bridge 的登记迁移或合法 `GensokyoPresence` 回执 | 主模型只可提议回执 |
| 会话 UID、计数器、关闭与幂等记录 | bridge | 只读 |
| 当前会话摘要、焦点、具体关系事实 | 额外变量模型 | 只写已开放字段 |
| 正文叙事 | 主剧情模型 | 不直接结算正式状态 |

### 3.2 明确不做

- 不引入第二份正式游戏状态；
- 不让模型决定主事件是否完成、奖励多少或路线是否解锁；
- 不以日期自动替玩家推进剧情；
- 不用每轮推断出的 `present/absent` 覆盖 `presence_snapshot`；
- 不新增泛化的 `current_chapter` 或 `current_route` 字段；
- 不把所有逻辑合并为单体脚本；
- 不在本计划阶段修改 `dist/`、版本号、manifest 或已验收检查点；
- 不覆盖当前工作区中已有的未提交修改。

- 记录当前构建产物中事件世界书条目的数量、关键词和内容大小，作为 O2 的前后对照；
- 记录目标环境版本：SillyTavern、Tavern Helper、MagVarUpdate 与关键世界书扫描设置。

### 预计范围

- 优先只改 `tests/` 和测试夹具；
- 不改业务行为；
- 单轮建议不超过 120 行有效变更。

### 门禁

- `npm run check:ui`
- `npm test`
- `npm run build:ui`
- `npm run package:checkpoint:dry`

## 6. O1：统一事件登记表契约

### 目标行为

事件 JSON 成为事件定义的唯一维护源；运行时代码只实现通用机制和已登记的本地处理器，不再复制事件级允许结果与叙事说明。

### 实施切片

#### O1-A：类型与加载校验

- 以现有 JSON 为准，将 `allowed_results` 统一为稳定的字符串 ID 数组；
- 完整校验事件类型、轮次、前置、阻断、固定结局、允许结果、投影键和在场迁移；
- 未知字段形态、重复事件 ID、空结果、固定结局不在允许结果中时构建失败；
- loader 返回经过验证的数据，不使用无条件类型断言掩盖错误。

#### O1-B：消除结算双写

- `event-settlement` 从登记表查询允许结果和固定结局；
- 仅保留通用兜底错误，不保留另一份事件级 `allowedResults/defaultResults`；
- 本地 effect handler 仍使用白名单 ID 映射，JSON 不得携带可执行代码。

#### O1-C：消除目标行动双写

- 行动入口只选择 `event_id` 和玩家已确认的参数；
- 叙事大纲、必经节拍、禁止偏离、允许结局由统一投影器读取；
- 非事件日常行动继续使用独立的安全提示模板，不强行塞入事件登记表。

### 风险与回滚

- 风险：旧事件存在不一致配置，严格校验会让构建失败；
- 处理：逐条修正维护源，不通过放宽校验绕过；
- 回滚：O1-A、O1-B、O1-C 分开提交/检查点吸收，任一切片可独立撤回；
- 停止条件：发现运行时实际依赖未登记结果时，先补契约决策，不继续迁移。

### 验收

- 新增一个合法事件只需改登记 JSON、对应本地 effect handler 和测试；
- 修改固定结局后，不需要同步修改第二份事件表；
- 非法或重复配置在构建期报出具体事件 ID 与字段；
- 现有固定事件、自由支线和夜间观察行为保持不变。

## 7. O2：当前事件最小投影

### 目标行为

模型只看到本次行动所需的信息。普通温室闲聊不能读到未来方案、固定结局或尚未解锁的事件；固定事件只看到自己的定义和被允许的状态切片。

### 实施切片

#### O2-A：纯函数投影器

新增独立的事件投影模块，输入为：

- 已验证的 `event_id`；
- 当前正式状态；
- 当前在场快照；
- 玩家已确认的本地选择。

输出只包含：

- 当前事件标题、类型和轮次边界；
- `narrative_outline`、`required_beats`、`forbidden_deviations`；
- 固定结局与允许结果 ID；
- `projection_keys` 指定的状态字段；
- 与本次事件有关的角色和当前在场信息。

找不到事件、前置不满足或投影键未知时拒绝开始事务，不降级为投影全量配置。

#### O2-B：接入行动消息

- `target-actions` 只调用统一投影器；
- 输出使用清晰分区，区分“事实”“叙事约束”“本地结算边界”；
- 不再列出所有不在场角色姓名；
- 不把完整 `stat_data` 重复拼入事件提示，状态只按键选择。

#### O2-C：调整打包边界

- 停止以通用温室关键词打包整份事件配置正文；
- 世界书只保留稳定规则、术语或必要索引；
- 具体事件定义由受信任脚本在事件启动时精确注入；
- dry-run 增加断言：产物不得包含“一个关键词条目承载全部事件配置”的旧结构。

### 建议范围控制

- O2-A：新增模块与单元测试，建议少于 180 行；
- O2-B：只改行动消息组装和测试，建议少于 140 行；
- O2-C：只改打包脚本、契约断言和 API 来源记录；
- 任一切片若超过 3 个核心模块或 250 行有效变更，继续拆分，不一次跨层混改。

### 验收

- 自由温室聊天的最终提示中不存在未开始事件的大纲与固定结局；
- 触发 `greenhouse_free_growth_proposal` 时，只出现该事件配置；
- 触发爱丽丝或荷取事件时，前置、人物和投影字段正确隔离；
- 未解锁事件无法通过伪造 `event_id` 启动；
- 主模型文本偏离时，本地仍只接受登记结果；
- 现有零 LLM 商店、副本、设施结算不受影响。

## 8. O3：时间与区域状态护栏

### O3-A：时间单调性

建立唯一的时段顺序表，例如：

```text
清晨 < 上午 < 中午 < 下午 < 傍晚 < 夜晚 < 深夜
```

更新进入正式状态前，比较旧值与候选值：

- 日期减少：拒绝；
- 同一天时段倒退：拒绝；
- 跨日但时段回到清晨：允许；
- 怀表“暂停五分钟”只写专用痕迹，不回退日期或时段；
- 本地登记的时间推进继续由 bridge 完成，模型不得绕过。

具体时段枚举以当前 Schema 为准，实施时不得凭本计划示例新增枚举。

### O3-B：区域白名单

- `GensokyoPresence.area_id` 必须来自区域登记表；
- 未知区域、空字符串和超长值都拒绝整条角色迁移；
- 对合法角色逐条应用，单个非法角色条目不得污染其他合法迁移；
- 错误进入诊断日志，不从正文猜测替代区域。

### 验收

- 合法的同日推进和跨日推进通过；
- 同日倒退、日期倒退和未知时段被拒绝且保留旧值；
- 未知区域不能写入 `presence_snapshot`；
- 固定事件的登记迁移、自由剧情抵达、换区和离场继续正常；
- 每项为独立 Local Fix，可单独回滚。

## 9. O4：角色档案激活实机审计

### 为什么先审计

世界书的递归扫描、排除递归和注入顺序具有版本与配置敏感性。静态代码只能证明“存在触发可能”，不能证明真实运行时一定加载。

### 探针矩阵

在固定的新聊天中记录实际激活条目或最终提示：

1. 无角色名的普通庭园行动；
2. `stat_data` 中存在所有角色，但正文只涉及灵梦；
3. 在场上下文包含一名角色和多名不在场角色；
4. 温室自由聊天；
5. 单一固定事件；
6. Swipe、重新生成和刷新后的同一行动。

同时记录：

- SillyTavern、Tavern Helper、MagVarUpdate 精确版本；
- 世界书 recursion / prevent recursion / scan depth 相关配置；
- 实际激活的角色条目和事件条目；
- 最终提示中是否出现不在场角色档案或未来事件。

### 决策门

- 若未出现误激活：保留现有角色世界书，只收紧不在场姓名投影；
- 若由姓名列表触发：删除通用不在场姓名列表，改为当前角色 ID 的显式投影；
- 若由完整状态递归触发：将模型可见状态改为字段选择器，不改正式 `stat_data`；
- 若扫描设置无法稳定约束：由受信任脚本注入当前角色档案，关键词世界书仅保留轻量索引；
- 没有真实证据时，不实施角色档案大迁移。

## 10. O5：温室显式选择回执与路线锁

本阶段并入 R35，不提前创建通用路线系统。

### 目标行为

- 三项方案的完成标记与 `unlocked_forms` 一致时，才开放选择；
- 玩家必须在本地比较页明确选择并二次确认；
- bridge 在生成前冻结 `selected_form_id`、`action_id`、事务 ID 和成本预览；
- 模型只演绎已选方案，不能在正文中切换为另一方案；
- 完整回复和变量复读成功后，bridge 以冻结回执完成一次性结算；
- 刷新、重试、Swipe 或重复点击不能改变已冻结选择，也不能二次扣费。

### 不新增 `current_route`

现有 `unlocked_forms`、`current_form`、固定 action/result 映射和结算 ID 已能表达路线。只有出现无法由这些字段表示的新需求时，才重新评估 Schema 扩展。

### 验收

- 三方案未齐备时拒绝选择并指出缺失项；
- 模型写了另一方案名称也不改变本地选型；
- 失败重试沿用同一选择回执；
- 首次选择与后续换型分别使用登记成本和幂等 ID；
- 历史方案、关系事实和完成事件不因换型丢失。

## 11. O6：镜头影子审计与证据引用

此阶段属于非阻塞 backlog。

### 11.1 镜头影子审计

可借鉴参考卡的四态语义，但只能作为诊断层：

- `present`：与 `presence_snapshot` 一致且正文明确在镜头中；
- `focus`：当前叙事焦点；
- `absent`：正式快照不在场；
- `uncertain`：正文暗示移动或离场，但缺少合法回执。

影子审计可以报警“正文已离场但快照仍在场”，不得直接写回正式状态。用户确认、重新生成或后续合法回执才可消除诊断。

### 11.2 关系事实证据引用

额外变量模型写入长期关系事实或会话摘要时，可附来源 assistant 楼层 ID / swipe ID。用途是：

- Swipe 后识别失效事实；
- 审计某条关系结论来自哪次互动；
- 避免只有抽象判断、没有可追溯证据。

该能力涉及迁移和 Swipe 语义，应在会话所有权收口稳定后单独设计，不与 O1/O2 混改。

## 12. 统一验证矩阵

### 自动门禁

## 13. 回滚与停止条件

### 回滚原则

- 每个阶段使用独立、未占用的检查点吸收，不覆盖 R32 或已有交付目录；
- 优先回滚调用接线，保留无副作用的校验器和测试；
- 新投影器若失败，回到上一已验收投影路径，不回退为“注入全部事件配置”；
- 不通过删除用户存档字段解决迁移问题。

### 必须停止并重新决策的情况

- 新设计产生第二个正式状态写入者；
- 必须让模型创建 UID、结算 ID、资源或事件完成标记才能工作；
- 事件配置无法在不携带可执行代码的情况下表达；
- 实际世界书扫描行为与 API 来源记录冲突；
- 单切片跨越超过 3 个核心模块且无法独立验证；
- 当前未提交改动与目标文件重叠，且无法确认其所有者意图；
- 自动门禁或真实运行出现状态丢失、重复结算、跨聊天污染。
